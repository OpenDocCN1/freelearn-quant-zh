
Redundancy should be assessed at the failure-domain level. Multiple pods on one node do not protect against node failure; multiple nodes in one rack do not protect against a rack or power-domain event. Priority and admission-control policies should prevent exploratory jobs from consuming capacity reserved for critical inference. Service meshes can add encryption and observability, but each proxy hop must be tested against the latency budget.

## 10.4 Performance monitoring and optimization

Once a financial LLM system is deployed, performance monitoring becomes an ongoing control process rather than a one-time validation exercise. Monitoring should connect infrastructure health, data quality, model behavior, user outcomes, cost, and governance evidence.

### 10.4.1 Comprehensive monitoring framework

Production monitoring extends beyond application uptime to model behavior, data quality, latency, reliability, and task-level outcomes. The monitoring architecture must provide real-time alerts and retain sufficient historical evidence for incident analysis, model-risk review, and regulatory reporting.

#### Infrastructure, latency, and cost metrics

Infrastructure monitoring should include accelerator utilization, memory occupancy, key-value-cache utilization, batch size, queue depth, tokenization time, network throughput, storage latency, and model-loading time. For latency-sensitive applications, p50, p95, p99, and p99.9 should be tracked separately. The system should distinguish queueing delay, retrieval delay, prefill time, generation time, and downstream post-processing so that optimization targets the actual bottleneck.

Time-of-day and market-regime segmentation is important. A system that satisfies its p99 objective during normal conditions may fail during the market open, major announcements, or correlated upstream retries. Failure-mode tests should measure behavior during replica loss, index failover, network degradation, and regional recovery rather than only during healthy steady state.

Cost should be monitored as an operational metric. Useful measures include cost per thousand classified documents, cost per million input tokens, cost per generated token, cost per successful task, cloud egress, idle accelerator hours, reserved-capacity utilization, engineering on-call load, and disaster-recovery overhead. Unit costs should be reported together with quality and latency because an apparently cheaper configuration may create more human-review work.

#### Model and retrieval performance metrics

Production model metrics should include task accuracy, precision and recall for material error classes, calibration, abstention rate, robustness, and performance across document types, products, jurisdictions, and market regimes. Numerical extraction deserves separate validation because a model can be linguistically plausible while altering a sign, decimal, currency, or unit.

RAG monitoring should track retrieval recall on judged queries, source freshness, entitlement violations, duplicate evidence, citation coverage, no-answer behavior, and the frequency with which generated statements are unsupported by retrieved material. Drift detection can compare input, embedding, retrieval, confidence, and output distributions, but a statistical alert should trigger investigation rather than automatically imply retraining.

### 10.4.2 Continuous optimization processes

Continuous optimization keeps a deployed system aligned with changing workloads, infrastructure conditions, and business requirements. In financial settings, these processes must be controlled carefully because optimization choices can affect latency, cost, model quality, compliance, and user-facing decisions.

#### Controlled experimentation

A/B testing can support deployment decisions, but financial experiments require controls for market conditions, temporal dependence, user heterogeneity, and information leakage. Randomization units should be chosen so that treatment and control do not contaminate one another. Where live experimentation is inappropriate, shadow deployment and replay on timestamped data can compare latency, errors, and decisions without affecting users or trades.

Multi-armed bandits can allocate traffic adaptively, but their changing assignment probabilities complicate inference and governance. For high-impact applications, a pre-specified experiment with clear stopping rules may be preferable. Any strategy-level comparison should include transaction costs, turnover, capacity, and a common market window; infrastructure improvements should not be credited for economic gains that arise from a changed signal or risk policy.

#### Automated performance tuning

Automated systems can adjust batch sizes, replica counts, routing, quantization, or cache allocation, but only within approved safety and cost envelopes. A multi-objective tuning problem can be written as

min_{θ ∈ Θ} (L_{99}(θ), -C_{throughput}(θ), C_{TCO}(θ), E_{quality}(θ)), \quad (10.3)

subject to availability, compliance, and minimum-quality constraints. Here θ denotes the serving configuration, L_{99} is p99 latency, and E_{quality} is a task-specific error measure. Tuning should use held-out workloads and canary limits because optimizing against recent production traffic can overfit to a temporary regime.

## 10.5 Illustrative case study: Low-latency trading support

This section is a worked architecture and capacity-planning example. All numerical results are illustrative, not audited production measurements, and should not be interpreted as investment-performance evidence. The workflow supports analysts and downstream signal systems; a generative LLM is not placed directly in the order-execution path.

### 10.5.1 System requirements and constraints

The scenario ingests timestamped news and alternative-text events, enriches them with market context, and produces a low-latency sentiment and relevance score. A separate generative service produces explanations and retrieves supporting documents asynchronously.

- **Fast-path latency**: p99 end-to-end classification latency below 10 ms at the declared burst load;
- **Slow-path generation**: p95 time-to-first-token below 250 ms for asynchronous explanations, with no dependency from order routing on this service;
- **Throughput**: sustain 10,000 normalized text events per second during synthetic stress periods after upstream filtering;
- **Quality**: macro-F1 of at least 0.94 on a frozen, time-separated sentiment and relevance test set, with calibration error below the approved threshold;
- **Reliability**: at least 99.95% availability during defined market hours, with replayable inputs and no unreconciled event loss;
- **Compliance**: immutable lineage for source events, transformations, model and prompt versions, retrieved evidence, scores, generated explanations, and downstream use; and
- **Cost**: annualized run-rate at or below 70% of the defined cloud-only baseline, including development, deployment, hardware or cloud spend, power, cooling, engineering, monitoring, maintenance, scaling, and disaster recovery.

### 10.5.2 Architecture decisions and trade-offs

The architecture combines edge filtering, event-stream processing, on-premises inference, optimized serving, custom retrieval, and limited cloud use. Each choice reflects a trade-off among latency, cost, data control, operational complexity, and resilience. The following decisions explain why each component is included in the design and what constraints it introduces.

#### Edge filtering and quantized DistilBERT

Small, quantized DistilBERT classifiers are deployed at three regional edge sites for language identification, duplicate detection, coarse relevance scoring, and fast sentiment classification. This choice is justified because the edge task is bounded classification rather than open-ended generation. INT8 execution reduces memory and improves throughput on supported hardware, while confidence thresholds route uncertain or out-of-distribution cases to the central service. The trade-off is lower contextual capacity and the operational burden of keeping regional models, tokenizers, calibration sets, and thresholds synchronized.

#### Kafka and Flink for replayable event processing

Kafka is used as the durable event log, while Flink performs event-time normalization, joins, entity resolution, and feature enrichment. The combination was selected because replay and checkpointed state are important for historical reconstruction. Exactly-once behavior is claimed only for the configured Kafka-to-Flink-to-transactional-sink path. External APIs and databases that cannot participate transactionally use idempotency keys and reconciliation. The cost is additional operational complexity and checkpoint-related latency; the fast path therefore uses bounded state and avoids unnecessary synchronous sinks.

#### On-premises core inference cluster

The core cluster uses 32 already-owned NVIDIA A100 GPUs in four failure-domain-aware nodes. Retaining A100 rather than purchasing H100 or B200 is an economic decision: the installed base satisfies the fast- and slow-path service objectives after optimization, and its remaining book value is included in Equation (10.1). On-premises placement keeps sensitive signals and proprietary retrieval data within the controlled network and reduces wide-area-network variance. The disadvantages are fixed capacity, lower burst elasticity, and the need to reserve spare capacity for node failure.

#### TensorRT and TensorRT-LLM

The fast classifier is compiled with TensorRT INT8 after calibration on time-separated financial text. The central generative model uses TensorRT-LLM with a validated low-precision configuration because the institution already operates NVIDIA hardware and requires in-flight batching, paged key-value caching, and detailed Triton metrics. The generative service is kept outside the sub-10-ms path. Quantization is rejected automatically if it breaches calibration, factuality, or rare-event-recall thresholds. The main trade-offs are engine-build complexity, NVIDIA dependency, and revalidation after software-stack changes.
