
## 15.3.2 Architectural comparison for financial applications

| Feature | BERT (encoder-only) | GPT (decoder-only) | T5 (encoder-decoder) |
| :--- | :--- | :--- | :--- |
| **Architecture** | Uses only the encoder stack of the Transformer. Processes the entire sequence bidirectionally. | Uses only the decoder stack with causal masking. Processes the sequence autoregressively. | Uses both encoder and decoder stacks, like the original Transformer. |
| **Key feature** | Bidirectional context for understanding relationships between all tokens. | Autoregressive generation optimized for next-token prediction. | Sequence-to-sequence formulation treating every task as text transformation. |
| **Pre-training objective** | Original BERT uses masked language modeling (MLM) and next sentence prediction (NSP). Later BERT-style encoder models may omit, replace, or modify NSP. | Causal language modeling (CLM): predict the next token given previous context. | Text-to-text denoising or span corruption, depending on the encoder-decoder model family. |
| **Financial use cases** | NLU tasks: sentiment analysis, NER, document classification, entity extraction, compliance triage, and sentence-embedding models such as FinEAS. | Generative tasks: report drafting, summarization, scenario generation, code generation, multi-step reasoning. | Complex transformations: document translation, abstractive summarization, structured Q&A, data extraction. |

Table 15.1: Comparison of common Transformer architecture types for finance

The reference to next sentence prediction applies to the original BERT pre-training recipe [Devlin et al., 2019]. Later BERT-style models may remove or replace NSP, so the objective should be understood as architecture-family dependent rather than as a universal property of all encoder-only models.

In finance, model choice depends on the task, available data, integration constraints, latency requirements, and governance needs rather than on abstract architectural superiority. Each architecture offers specific advantages for different financial workflows.

## 15.3.3 FinEAS as a sentence-embedding specialization

FinEAS, short for Financial Embedding Analysis of Sentiment, is a financial sentiment model based on supervised, fine-tuned sentence embeddings [Gutiérrez-Fandiño et al., 2021]. It should be treated as an encoder-style specialization for sentence-level sentiment and semantic representation rather than as a general-purpose conversational LLM. Its relevance for this chapter is that it illustrates a different design point from large decoder-only systems: instead of optimizing mainly for open-ended generation, it optimizes the geometry of financial text embeddings for sentiment-sensitive comparison, classification, and downstream analysis.

A FinEAS-style component can be useful in larger financial LLM systems in at least four ways. First, it can provide a domain-specific sentiment score for news, filings, earnings-call excerpts, or analyst commentary. Second, it can produce embeddings for semantic search over sentiment-bearing financial sentences. Third, it can support clustering and monitoring of changes in the language used around firms, sectors, events, or market regimes. Fourth, it can act as a specialized signal inside agentic workflows, where a broader LLM agent uses a narrow sentiment encoder as one audited tool rather than relying only on free-form generation.

The main limitations are also instructive. FinEAS-style models require careful control of the training distribution, label definitions, temporal splits, and source coverage. Their outputs should be recalibrated when financial language changes, when the news source changes, or when the model is moved from research data to production data. Viewed through the sufficiency–concentration–structure lens, the objective is not merely to assign sentiment labels, but to learn a stable representation that preserves sentiment-relevant information, concentrates similar financial meanings, and separates economically different statements in embedding space. For this reason, FinEAS is best understood as a compact financial-sentiment and sentence-embedding module that complements, rather than replaces, retrieval systems, generative models, and governance layers.

### 15.4.1 Fine-tuning FinBERT and FinEAS-style sentiment models

Fine-tuning adapts a pre-trained model to a specific financial task, such as sentiment analysis, document classification, entity extraction, or risk categorization. The example below uses a FinBERT-style model for financial sentiment classification. The same workflow also clarifies where a FinEAS-style sentence-embedding model fits: FinBERT-style models are often used as direct classifiers, while FinEAS-style models emphasize sentence-level financial embeddings and the sentiment geometry.

The code is illustrative. It shows the main steps in a supervised fine-tuning workflow: loading a tokenizer and model, preprocessing the dataset, configuring training arguments, initializing a trainer, and saving the fine-tuned model. Production deployments should add authentication, logging, validation, observability, access controls, model cards, and rollback procedures.

Listing 15.1: Supervised fine-tuning workflow for financial sentiment analysis

```python
from datasets import load_dataset, DatasetDict
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    Trainer,
    TrainingArguments,
)
from sklearn.metrics import accuracy_score, f1_score
import numpy as np

class FinancialSentimentTrainer:
    """
    Illustrative fine-tuning pipeline for financial sentiment analysis.
    The example is simplified for exposition and should be hardened before
    production use.
    """
    def __init__(
        self,
        model_name="ProsusAI/finbert",
        dataset_name="financial_phrasebank",
        dataset_config="sentences_75agree",
        output_dir="./finbert-financial-sentiment",
        max_length=128,
    ):
        self.model_name = model_name
        self.dataset_name = dataset_name
        self.dataset_config = dataset_config
        self.output_dir = output_dir
        self.max_length = max_length

        self.tokenizer = AutoTokenizer.from_pretrained(model_name)
        self.model = AutoModelForSequenceClassification.from_pretrained(
            model_name,
            num_labels=3,
        )

    def tokenize_batch(self, batch):
        return self.tokenizer(
            batch["sentence"],
            padding="max_length",
            truncation=True,
            max_length=self.max_length,
        )

    @staticmethod
    def compute_metrics(eval_pred):
        logits, labels = eval_pred
        predictions = np.argmax(logits, axis=-1)
        return {
            "accuracy": accuracy_score(labels, predictions),
            "macro_f1": f1_score(labels, predictions, average="macro"),
        }

    def load_and_prepare_data(self):
        raw = load_dataset(
            self.dataset_name,
            self.dataset_config,
            split="train",
        )
        # NOTE ON THE SPLIT -- read this before reporting any number.
        # Financial PhraseBank ships without timestamps, so a chronological
        # split is not available for this dataset. The random split below is
        # therefore forced, and it is precisely the protocol this book
        # criticises elsewhere (Chapters 1 and 13). It is kept because it
        # demonstrates the training loop, not because it produces a
        # trustworthy result. Any score obtained this way is a smoke test of
        # the pipeline, NOT evidence of deployable performance.
        # For a model that will inform a decision, use a timestamped corpus
        # and the chronological split in temporal.py.
        # THREE-way split. The previous version made ONE split and then
        # passed dataset["test"] to the Trainer as eval_dataset with
        # load_best_model_at_end=True -- i.e. it selected the checkpoint on
        # the test set. That is selection on the test partition, and this
        # book spends a chapter explaining why it invalidates the number.
        # Validation selects; test is touched once, after selection.
        tmp = raw.train_test_split(test_size=0.2, seed=42)
        held = tmp["test"].train_test_split(test_size=0.5, seed=42)
        split = DatasetDict({
            "train": tmp["train"],
            "validation": held["train"],
        })
```
