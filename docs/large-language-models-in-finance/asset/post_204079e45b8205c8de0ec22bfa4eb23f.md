
the same test period, the final result is overfit even if every individual run was temporally clean. This is prompt overfitting, the LLM version of strategy data mining.

The remedy is research accounting. Maintain a development set, a validation set, and a final untouched test set. Log all prompt variants and model-selection decisions. Use nested validation when selecting prompts or adapters. Report the number of trials or use multiple-testing corrections where appropriate. Most importantly, do not let the final test set become part of the creative loop.

### 13.4.10 Hallucinated numerical signals and false precision

LLMs can generate fluent explanations around weak or nonexistent signals. A model may infer a causal story from noise, invent a ratio, misread a table, or report a precise expected return unsupported by the data. In financial forecasting, false precision is dangerous because small numerical differences can drive large position changes.

Production systems should separate language generation from numerical computation. Let the LLM propose hypotheses, retrieve context, or explain model outputs, but let audited numerical code compute returns, volatilities, correlations, drawdowns, and portfolio weights. A forecast report should include confidence intervals, calibration diagnostics, and explicit uncertainty. If the model cannot cite the data and computation behind a number, the number should not enter the investment process.

### 13.4.11 A leakage-aware evaluation protocol

A robust protocol for LLM financial forecasting and backtesting should include the following controls:

- First, define the information set $\mathcal{F}_t$ for every forecast origin, including data, documents, tools, prompts, and memory.
- Second, build all features from availability timestamps rather than economic-period timestamps.
- Third, use rolling-origin splits with embargoes for overlapping labels.
- Fourth, freeze or time-index all retrieval stores and tool APIs.
- Fifth, reset memory unless online learning is explicitly modeled.
- Sixth, evaluate against simple baselines and strong non-LLM baselines.
- Seventh, report statistical and economic metrics after transaction costs.
- Eighth, run contamination probes for pretrained and retrieved knowledge.
- Ninth, reserve a final untouched test period.
- Tenth, archive prompts, code, data hashes, model versions, and tool outputs so the backtest can be audited.

Algorithm 18 summarizes the protocol.

```
Algorithm 18 Leakage-aware LLM backtest
1: Input: forecast origins {tj }, horizon H, point-in-time data store, time-indexed retrieval store, model M
2: for each forecast origin tj do
3: Freeze numerical data, documents, tools, prompts, and memory to Ftj
4: Construct features and context using availability timestamps only
5: Reset memory or load only state that would have existed at tj
6: Generate forecast distribution p̃j(ytj +1:tj +H)
7: Convert forecast to positions using pre-specified risk and cost model
8: Store prompt, retrieved documents, data hashes, model version, and forecast
9: end for
10: Reveal outcomes only after all forecasts are locked
11: Compute statistical metrics, economic metrics after costs, and paired significance tests
12: Run contamination probes and document any suspected overlap
13: Output: audited performance report and leakage diagnostics
```

### Practitioner implementation note

The protocol can be enforced with ordinary engineering components if each component is time-indexed. A practical stack contains five layers:

- First, a point-in-time feature store, for example a Feast-style or in-house feature store, performs as-of joins and rejects features whose availability timestamp is later than the forecast origin.
- Second, an append-only lakehouse or immutable data-versioning layer, for example a Delta Lake, Apache Iceberg, lakeFS, or hash-chain design, stores raw vendor drops and corrected versions without overwriting history.
- Third, a time-indexed retrieval store rebuilds the vector index so that retrieved documents are measurable with respect to $\mathcal{F}_{t_j}$.
- Fourth, a model and prompt registry records the base model, adapter, temperature, system prompt, tool permissions, and post-processing rule used for each run.
- Fifth, an audit ledger stores the forecast origin, data hashes, retrieved document IDs, model version, prompt version, memory policy, forecast, and locked timestamp. The precise vendor choice is less important than the invariant: every object consumed by the LLM must be reconstructible as it existed at the historical decision time.

### Minimal implementation pattern

The following Python-style sketch illustrates the practical control flow behind Algorithm 18. It is intentionally library-neutral; the important feature is the time-travel boundary at each forecast origin.

```
for origin in forecast_origins:
    X = feature_store.asof(entity_ids, features, as_of=origin)
    docs = retrieval_index.snapshot(as_of=origin).search(query(origin))

    if online_learning:
        memory = memory_store.load_state(as_of=origin)
    else:
        memory = None

    forecast = model.predict(
        features=X,
        documents=docs,
        memory=memory,
        prompt_version="locked_v3",
        tools="historical_only",
    )

    audit_log.write(
        forecast_origin=origin,
        data_hash=X.hash(),
        document_ids=[d.id for d in docs],
        model_version=model.version,
        prompt_version="locked_v3",
        memory_policy="online" if online_learning else "reset",
        forecast=forecast,
        locked_before_outcome=True,
    )

# Outcomes are joined only after every forecast has been locked.
performance = evaluate_locked_forecasts(audit_log, realized_outcomes)
```

The main lesson is methodological. Time-series LLMs may become valuable components of financial forecasting systems, but their evaluation must be stricter than ordinary machine-learning evaluation, not looser. The more capable the model, the larger the surface area for hidden leakage. Robustness comes from treating the entire LLM system—base model, prompt, tools, retrieval, memory, data, and researcher workflow—as part of the backtest.

## 13.5 Point-in-time text signals: auditing the complete scoring artifact

The timestamp on a text record does not timestamp the model that reads it. A 2008 headline is historical, yet the instrument used to score it may have been trained, calibrated, prompted, or retrieval-augmented with information from 2012 or 2026. The apparent historical signal then mixes two information sets: what was available when the text arrived, and what was embedded later in the measurement apparatus. A backtest can be chronologically sorted and still be impossible to have traded. The preceding section catalogued these leakage channels qualitatively and gave an operational protocol for closing them. This section sharpens that protocol into a measurement standard: a formal admissibility condition for the complete scoring artifact, a proposition stating exactly what a clean pipeline guarantees, controlled evidence on how large each violation is, and an artifact-level checklist that an auditor can apply object by object.

### 13.5.1 The complete scoring artifact and its vintage

A text signal is a composition,

```
X_j \longrightarrow \mathcal{A}_{v(j)} \longrightarrow s_j \longrightarrow S_{a,d} \longrightarrow z_{a,d} \longrightarrow \pi_d, \quad (13.1)
```

where X_j is the as-available article, $\mathcal{A}_{v(j)}$ is the scoring artifact deployed at vintage v(j), s_j is an article score, S_{a,d} an asset-day aggregate, z_{a,d} a transformed signal, and $\pi_d$ the decision executed at the close of day d. Any data-dependent arrow can import the future. For a sparse lexicon the vulnerable object is visibly a table of word weights. For a modern system it is much larger. At build vintage t, define

```
\mathcal{A}_t = (\text{tokenizer}_t, \text{vocabulary}_t, \text{base}_t, \text{head}_t, \text{calibrator}_t, \text{prompt}_t, \text{retrieval}_t, \text{code}_t, \text{config}_t, \xi_t), \quad (13.2)
```

where $\xi_t$ records all stochastic state needed for replay and unused components are null. For a dictionary, the vocabulary and weights carry the substance; for a retrieval-augmented LLM, every entry can matter.

Admissibility is not a training-data cutoff. Let $\rho(\mathcal{A}_t)$ be the earliest time at which the assembled artifact is built, released or licensed, deployed, and operationally available. In practice,

```
\rho(\mathcal{A}_t) = \max\{c_t^{\text{data}}, c_t^{\text{tune}}, c_t^{\text{build}}, c_t^{\text{release}}, c_t^{\text{deploy}}, c_t^{\text{avail}}\}, \quad (13.3)
```

the six stamps being the source-data cutoff, the fine-tuning cutoff, build completion, release or licensing, deployment into the scoring path, and operational availability to the process that will consume the score. The last two are the ones most often dropped, and they are the ones that bite: a model released in March but not wired into the research pipeline until June was not admissible artifact in April, whatever its weights knew. A model trained on data through 2010 but first released in 2012 is not an admissible 2011 artifact.
