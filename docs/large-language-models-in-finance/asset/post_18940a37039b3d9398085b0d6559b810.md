
## 4.4.2 Contrastive learning for embeddings

Modern embedding models employ contrastive learning objectives [Gao et al., 2021, Chen et al., 2020]. Given a batch of training examples $(q_i, d_i^+, \{d_i^{-,j}\}_{j=1}^m)$ where $q_i$ is a query, $d_i^+$ is a relevant document, and $\{d_i^{-,j}\}$ are negative (irrelevant) documents:

The InfoNCE (Noise Contrastive Estimation) loss is defined as:

```
$$\mathcal{L} = - \log \frac{\exp(\text{sim}(f(q_i), f(d_i^+))/\tau)}{\exp(\text{sim}(f(q_i), f(d_i^+))/\tau) + \sum_{j=1}^m \exp(\text{sim}(f(q_i), f(d_i^{-,j}))/\tau)}$$
```

where $\tau$ is a temperature parameter controlling the sharpness of the distribution.

The temperature parameter $\tau$ plays a crucial role: smaller $\tau$ creates sharper distributions, while larger $\tau$ smooths the distribution. Typical values range from $\tau = 0.05$ to $\tau = 0.1$.

## 4.4.3 Financial embedding models

The choice of embedding model directly affects retrieval accuracy, particularly when working with domain-specific finance terminology and structured disclosures. We distinguish here, therefore, between general-purpose and domain-specific models.

In practice, practitioners typically begin with general-purpose models such as:

- OpenAI text-embedding-3-large (3072-dim)
- Cohere embed-english-v3.0 (1024-dim)
- sentence-transformers/all-mpnet-base-v2 (768-dim)

However, as retrieval requirements become more specialized, especially when dealing with financial filings, research reports, or internal documents, domain-specific models such as:

- retrieval-trained sentence encoders (for example the E5, GTE, and BGE families, or sentence-transformers models), further fine-tuned on financial corpora with contrastive pairs drawn from the target document type
- custom encoders fine-tuned on proprietary filings, memos, or transcripts, evaluated on retrieval metrics rather than on classification accuracy

Two clarifications are worth making because the field is careless about them. **A classifier is not an embedding model.** ProsusAI/finbert is a financial *sentiment classifier*; its hidden states can be pooled into vectors, but it was never trained with a retrieval objective and it will underperform a purpose-trained encoder on nearest-neighbour search. **BloombergGPT is not an embedding service.** It is a proprietary generative model [Wu et al., 2023b]; there is no publicly released checkpoint and no deployable embedding endpoint, so it cannot appear in a retrieval stack a reader can actually build. Naming a model that cannot be obtained is not a design recommendation. In practice, many systems begin with general-purpose retrieval encoders and progressively incorporate domain-specific fine-tuning as requirements become more specialized.

## 4.4.4 Matryoshka embeddings

From a system design perspective, being able to work with lower-dimensional versions of the same embedding makes it easier to balance retrieval quality against computational and storage costs, especially in large-scale financial systems. Recent advances enable Matryoshka Representation Learning (MRL) [Kusupati et al., 2022], where a single model produces embeddings of variable dimensionality:

$f(x) = [f_1(x), f_2(x), ..., f_d(x)]$ (4.9)

We can truncate to any \(d' < d\) while maintaining semantic properties. This allows:

- High-dimensional embeddings (e.g., 1024-dim) for precision
- Low-dimensional embeddings (e.g., 256-dim) for efficiency
- Dynamic adjustment based on computational budget

In practice, this can be implemented by generating a full embedding once and selectively truncating it to a lower-dimensional representation, as shown below.

```
import numpy as np

# Full 1024-dimensional embedding
full_embedding = embed_model.encode(text) # shape: (1024,)

# Truncate to 256 dimensions for faster search
truncated = full_embedding[:256] # shape: (256,)

# Both preserve semantic properties with appropriate scaling
```

## 4.5 Vector databases and indexing

Once embeddings have been computed, we need infrastructure that can store them at scale and retrieve the nearest neighbors of a query embedding in milliseconds. This is the role of the vector database. In a financial RAG system, the index typically holds millions of chunk embeddings drawn from filings, transcripts, research, and internal documents, and is queried tens or hundreds of times per user request once re-ranking, multi-query retrieval, and metadata filtering are taken into account. The choice of indexing algorithm, therefore, directly affects latency, memory footprint, recall, and ultimately the quality of the answers the system can produce.

In this section, we discuss the core algorithmic ideas behind modern vector indexes, the FAISS library that implements most of them in production, and hybrid search, which combines semantic and lexical signals.

## 4.5.1 Approximate nearest neighbor search

Exact nearest neighbor search in high dimensions has O(Nd) complexity, where N is the corpus size and d is the embedding dimension. As a result, for large corpora (N > 10^6), exact search becomes computationally expensive, and we instead rely on approximate methods that trade a small amount of accuracy for significant speed improvements.

### Inverted File Index (IVF)

One commonly used approach is the **Inverted File Index (IVF)** algorithm, which partitions [Jégou et al., 2011] the embedding space into clusters and restricts search to a subset of those clusters at query time.

Algorithm 6: IVF index construction and search

| Step | Description |
|------|-------------|
| 1 | Training phase: |
| 2 | Cluster embeddings into m centroids using k-means: {c1, ..., cm} |
| 3 | Assign each embedding ei to nearest centroid cluster |
| 4 | Query phase: |
| 5 | Given query embedding q |
| 6 | Find n_probe nearest centroids to q |
| 7 | Search only embeddings in these n_probe clusters |
| 8 | Return top-k results |

In practice, this approach reduces the number of comparisons required at query time by focusing only on the most relevant regions of the embedding space.

In terms of computational complexity, the IVF approach exhibits the following characteristics:

- Training: O(Nmd · iterations)
- Query: O(n_probe · (N/m) · d)
- For n_probe << m, we achieve significant speedup

### Hierarchical Navigable Small World (HNSW)

Another widely used approach is **Hierarchical Navigable Small World (HNSW)** [Malkov and Yashunin, 2020], which constructs a graph-based index with a skip-list structure characterized by the following properties:

- The index is organized as a multi-layer graph, where higher layers are progressively sparser
- Search begins at the top layer and navigates down to the lower layers
- This results in approximately O(log N) search complexity with high recall
- The trade-off is higher memory usage compared to IVF

### Product quantization

**Product quantization (PQ)** [Jégou et al., 2011] addresses a different challenge by focusing on memory efficiency rather than solely on search speed. It compresses embeddings by decomposing $d$-dimensional space into $s$ subspaces of dimension $d/s$:

$\mathbb{R}^d = \mathbb{R}^{d/s} \times \mathbb{R}^{d/s} \times \cdots \times \mathbb{R}^{d/s}$

Each subspace is then quantized independently using $k$ centroids. This allows the embedding to be represented in a compressed form requiring only $s \cdot \log_2(k)$ bits, compared to $32d$ bits for a standard float32.

While these indexing methods define how similarity search is performed, we rely on specialized libraries to implement them efficiently at scale.

## 4.5.2 Facebook AI Similarity Search (FAISS)

**Facebook AI Similarity Search (FAISS)** [Johnson et al., 2019, Douze et al., 2024] provides optimized implementations of a wide range of vector indexing and similarity search methods, making it a common choice for building production-grade retrieval systems. A typical workflow for constructing and querying an index is shown below:

```
import faiss
import numpy as np

# Index parameters
d = 768 # embedding dimension
nlist = 100 # number of clusters for IVF
m = 8 # number of subquantizers for PQ
nbits = 8 # bits per subquantizer

# Create IVF-PQ index
quantizer = faiss.IndexFlatL2(d)
index = faiss.IndexIVFPQ(quantizer, d, nlist, m, nbits)

# Train on sample embeddings
embeddings = np.random.randn(10000, d).astype('float32')
index.train(embeddings)
index.add(embeddings)

# Search
query = np.random.randn(1, d).astype('float32')
k = 5
distances, indices = index.search(query, k)
```
