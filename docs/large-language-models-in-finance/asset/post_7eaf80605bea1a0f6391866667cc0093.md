
else:
    graph = build_document_graph(expanded)
    evidence = graph.select_evidence_subgraph(question)
    mode = "retrieval_plus_document_graph"

consistency = check_cross_document_consistency(evidence)
response = model.synthesize(
    question=question,
    evidence=evidence,
    require_citations=True,
    report_conflicts=consistency.conflicts,
)

return {
    "answer": response.text,
    "citations": response.citations,
    "conflicts": consistency.conflicts,
    "architecture": mode,
    "corpus_snapshot": permitted.snapshot_id,
}

The output should disclose unresolved conflicts rather than silently selecting one source. Evaluation should separately measure retrieval recall, evidence precision, citation correctness, temporal alignment, contradiction detection, and final-answer accuracy. This decomposition reveals whether a failure comes from document selection, relationship construction, or generation.

## 8.3 Client services and advisory

Client-facing LLM systems may improve response consistency, make explanations available outside normal service hours, and reduce the marginal effort required for selected routine interactions. These benefits are conditional rather than universal: implementation, validation, supervision, data protection, and exception handling can be expensive, and high-stakes advice remains subject to professional and regulatory responsibilities.

### 8.3.1 Intelligent advisory systems for investment advice

Conversational interfaces can help gather client information, explain portfolio concepts, summarize alternatives, and prepare materials for an advisor. They do not remove the need for a valid client profile, product governance, suitability or appropriateness controls, disclosures, and accountable approval.

**Suitability, disclosure, and human approval.** Before a system drafts any personalized investment recommendation, it should confirm that required client information is current, including objectives, time horizon, liquidity needs, financial capacity, risk tolerance, tax context, knowledge and experience, and relevant restrictions. A jurisdiction-specific policy engine must determine which products, disclosures, conflicts, fees, assumptions, and warnings apply. The recommendation, evidence, optimizer inputs, and generated explanation should then be reviewed and approved by an authorized human advisor whenever the activity constitutes regulated advice. The LLM may support information gathering and explanation, but it should not make the final suitability determination, suppress required disclosures, or submit a transaction on its own [U.S. Securities and Exchange Commission, 2019].

A clean division of labor is shown below:

- validated data services maintain the client profile and entitlements;
- deterministic rules enforce jurisdictional and product constraints;
- tested quantitative models produce portfolio analytics;
- the LLM drafts a plain-language explanation grounded in those inputs;
- an authorized professional approves, modifies, or rejects the draft; and
- a separate transaction system executes only an approved instruction.

The workflow in Listing 8.4 makes the approval boundary explicit.

### Listing 8.4: Bounded advisory workflow with human approval

```
def prepare_advisory_draft(client_id, request, services):
    profile = services.client_profile.get_validated(client_id)
    policy = services.policy_engine.resolve(
        jurisdiction=profile.jurisdiction,
        activity="investment_advice",
    )

    suitability = services.suitability.evaluate(profile, request, policy)
    if not suitability.eligible:
        return route_to_advisor(suitability.reasons)

    analytics = services.portfolio_model.evaluate(
        holdings=profile.holdings,
        objectives=profile.objectives,
        constraints=suitability.constraints,
    )

    explanation = services.llm.draft_explanation(
        approved_facts=analytics,
        required_disclosures=policy.disclosures,
        prohibited_claims=policy.prohibited_claims,
    )

    return {
        "status": "pending_human_approval",
        "analytics": analytics,
        "explanation": explanation,
        "disclosures": policy.disclosures,
        "execution_authorized": False,
    }
```

The model does not create the client facts, select the applicable jurisdiction, or authorize execution. Its task is narrower: transform approved analytical objects into a reviewable explanation.

### Behavioral-finance-aware communication

Behavioral-finance concepts can help an advisor identify possible framing effects, loss aversion, overconfidence, present bias, or panic-driven changes in stated preferences. They may also help adapt the order, wording, or visual presentation of information [Schwarm et al., 2023]. However, a behavioral nudge does not automatically make advice psychologically appropriate. A model can misclassify emotion, reinforce stereotypes, exploit vulnerability, or steer a client toward the institution's preferred outcome.

Accordingly, behavioral interventions should be transparent, non-manipulative, validated for the intended population, and subject to consent or opt-out where appropriate. The system should preserve the client's autonomy, disclose material alternatives, avoid inferring sensitive traits without a lawful and necessary basis, and escalate signs of distress or impaired decision-making to a trained human. Behavioral analysis should influence communication support, not silently override suitability rules or the client's stated objectives.

### 8.3.2 Customer service automation and chatbots

Not all client-facing uses constitute investment advice. Many interactions concern account information, document requests, product explanations, service status, complaints, or routing. In these settings, the most important design requirements are factual accuracy, identity and access management, privacy, transaction boundaries, context retention, and timely escalation.

### Enterprise identity and privacy boundary

An LLM should never authenticate a customer, receive passwords or one-time codes, decide entitlements, or directly access raw personally identifiable information (PII). Authentication and authorization must occur through a deterministic enterprise identity and access management (IAM) gateway before an LLM session begins. The model should receive only the minimum redacted or tokenized context required for the approved task. Transaction initiation and execution should likewise remain behind deterministic APIs with explicit confirmation and policy checks [National Institute of Standards and Technology, 2025].

### Listing 8.5: Opening a privacy-minimized LLM service session

```
def open_service_session(request, session_cookie, services):
    # Authentication and authorization occur outside the LLM boundary.
    principal = services.iam.verify_session(session_cookie)
    permissions = services.iam.authorize(
        principal=principal,
        requested_action=request.action,
    )
    if not permissions.allowed:
        raise PermissionError("Action not authorized")

    # Remove secrets and direct identifiers before prompt construction.
    redacted_text = services.dlp.redact(request.text)
    safe_context = services.customer_data.minimized_view(
        principal=principal,
        fields=permissions.allowed_fields,
        tokenize_identifiers=True,
    )

    response = services.llm.respond(
        user_message=redacted_text,
        approved_context=safe_context,
        allowed_tools=permissions.allowed_tools,
    )

    return services.output_guard.validate_and_log(
        principal=principal,
        request=request,
        response=response,
    )
```

This design prevents the model from becoming an identity provider or a general query interface to the customer database. It also creates a single place to enforce data minimization, tool permissions, output inspection, and audit logging.
