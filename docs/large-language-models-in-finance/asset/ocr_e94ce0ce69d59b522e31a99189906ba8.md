# 5.1.3 The agent contract: stochastic reasoning, deterministic execution

The safest way to design financial agents is to separate two roles that are often blurred. The LLM may propose a plan, summarize evidence, rank alternatives, or draft a response. It should not be the component that decides whether a tool call is authorized, whether an order may be routed, whether client information may be disclosed, or whether a regulatory statement is final. Those decisions belong to deterministic policy components.

Formally, write an agent proposal as

$$a_t \sim \pi_\theta(\cdot \mid s_t),$$

where $s_t$ is the observed state and $a_t$ may be a tool call. The execution layer applies an authorization oracle

$$\Gamma(a_t, s_t, u_t) \in \{0, 1\},$$

where $u_t$ is the authenticated user or service identity. The executed action is then

$$\tilde{a}_t = \begin{cases} a_t, & \Gamma(a_t, s_t, u_t) = 1, \\ \text{escalate/reject,} & \Gamma(a_t, s_t, u_t) = 0. \end{cases}$$

The key design choice is that $\Gamma$ is not a prompt. It is a deterministic software and policy layer that can be tested independently of the LLM.

**Proposition 5.1.1** (Guarded execution invariant). If every external action proposed by an LLM agent is executed only through the guarded map above, and the guard $\Gamma$ is sound with respect to the institution’s authorization policy, then no unauthorized external action can be executed by the agent workflow, regardless of the distribution of LLM proposals.

Proof. Consider any proposed action $a_t$. If it is authorized, the guard permits it. If it is unauthorized, soundness of $\Gamma$ implies $\Gamma(a_t, s_t, u_t) = 0$, so the executed action is not $a_t$ but the reject or escalation action. This argument is pointwise in $a_t$ and therefore does not depend on how the LLM proposal was generated. \(\square\)
