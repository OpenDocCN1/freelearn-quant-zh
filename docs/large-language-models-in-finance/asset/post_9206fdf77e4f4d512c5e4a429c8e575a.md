## 3.8.2 Financial-specific validation

Standard NLP evaluation metrics, even when applied carefully, do not catch the failure modes that matter most in financial applications. A model can achieve high F1 on a held-out test set while still computing growth rates in the wrong direction, confusing quarterly and annual figures, or generating statements that cannot be verified against any source document. The three validation checks below address these failure modes directly and should be applied as a matter of course before any financial model is moved to production.

When evaluating **numerical accuracy**, financial outputs must be held to a higher standard of precision than general language generation. A model that rounds $1.401B to $1.4B may be acceptable in some contexts; one that reports revenue growth of +8% when the correct figure is –8% is not. The validation function below implements a relative-tolerance check that can be applied programmatically across a large test set, flagging outputs where the predicted value deviates from the ground truth by more than a specified threshold:

```
import math

def validate_calculation(prediction, ground_truth,
                         rel_tol=0.01, abs_tol=1e-8):
    """Check numerical agreement without dividing by zero."""
    if math.isclose(ground_truth, 0.0, abs_tol=abs_tol):
        return math.isclose(prediction, ground_truth, abs_tol=abs_tol)
    return math.isclose(
        prediction,
        ground_truth,
        rel_tol=rel_tol,
        abs_tol=abs_tol,
    )
```

The absolute-tolerance branch is essential when the ground truth is zero or economically close to zero, such as a spread change of 0 bps, a flat quarter-over-quarter growth rate, or a normalized exposure that should be exactly neutral. Manually dividing by `ground_truth` in these cases either fails numerically or turns small rounding noise into an artificially large relative error.

When assessing **temporal consistency**, the key concern is whether the model correctly handles directional comparisons across time periods. Many financial questions involve directional comparisons across time periods, and models frequently get the direction of subtraction wrong—computing _Q_<sub>1</sub> – _Q_<sub>2</sub> when asked for _Q_<sub>2</sub> – _Q_<sub>1</sub> growth. This is a systematic error that standard accuracy metrics may miss if the magnitudes happen to be similar. The test below illustrates the pattern to check: the correct answer is not just the right number, but the right number computed in the right direction:

```
Test: "What was revenue growth from Q1 2023 to Q2 2023?"
Model Output: "Revenue grew 8% QoQ"
Validation: Verify model extracted Q2 – Q1, not Q1 – Q2
```

When evaluating **factual grounding**, model outputs must be supported by the underlying source documents. Generative models can produce fluent, plausible-sounding statements that are not supported by the source documents provided. In financial applications this is a serious risk—a hallucinated revenue figure or a misattributed earnings beat can propagate into downstream analysis or client communications. The factual grounding check below verifies that every numerical claim in the model's output can be traced to an explicit calculation from the source data:

```
Claim: "Apple's iPhone revenue grew 12% in Q3 FY2024"
Source Document: "iPhone revenue: Q3 FY2024: $39.30B, Q3 FY2023: $39.67B"
Calculation: ($39.30B - $39.67B) / $39.67B = -0.9%
Validation: FAIL -- the claim asserts growth; the source shows a small decline. The output is not grounded. Block and escalate rather than passing the figure downstream.
```

Even with these domain-specific checks in place, evaluation remains incomplete if it only reflects the conditions captured in the test set.

## 3.8.3 Robustness testing

A model that performs well on the held-out test set may still fail in production when it encounters inputs that differ from the training distribution. Financial text is particularly prone to distribution shift: vocabulary, framing conventions, and the mix of entity types all vary across sectors, geographies, and market regimes. Robustness testing proactively exposes these failure modes before deployment by deliberately constructing challenging inputs that go beyond what the standard test set covers.

A common approach is to use **adversarial examples** to probe whether the model has learned the underlying semantics of financial language or merely memorized surface patterns from training data. A model that correctly labels "revenue declined" as negative but fails on “top-line performance came in below expectations” has learned lexical cues rather than meaning. Systematic paraphrasing, negation testing, and out-of-distribution inputs reveal this brittleness:

- Paraphrased queries (test semantic understanding)
- Negations and edge cases
- Out-of-distribution inputs

A complementary approach is to use **stress testing** to evaluate how the model behaves under more demanding or complex input conditions. Stress tests expose the model to the most demanding inputs it is likely to encounter in production—very long filings, documents with multiple entities sharing similar names (e.g., multiple subsidiaries of the same parent), and queries that are genuinely ambiguous or that draw on contradictory information from different sections of the same document:

- Very long documents
- Multiple entities with similar names
- Ambiguous or underspecified queries
- Contradictory information from multiple sources

Failures under stress testing do not necessarily mean a model should not be deployed; they define the boundary conditions under which it operates reliably and those under which it requires human oversight. Documenting these boundaries explicitly is itself a governance deliverable.

The final step is to observe how the model behaves not in controlled tests, but in real usage.

## 3.8.4 A/B testing in production

Offline evaluation on a held-out test set measures potential; A/B testing in production measures actual impact. The two are often surprisingly different. A model that scores several percentage points higher on a benchmark may produce outputs that real users find less useful, trust less, or override more frequently—signals that only become visible when the model is interacting with genuine tasks and genuine users.

The standard approach routes a small fraction of live traffic—typically 5–10%—to the new model while continuing to serve the baseline model to the remainder. Crucially, every request and response is logged alongside any available signal of user satisfaction (explicit feedback, override rates, follow-up queries). This creates the evidence base needed to determine whether the benchmark improvement translates into a real-world improvement before a full rollout is committed:

```
import hashlib

def stable_bucket(session_id):
    digest = hashlib.sha256(str(session_id).encode()).hexdigest()
    return int(digest[:8], 16) / 0xFFFFFFFF

# Route 10% of sessions, not individual queries, to the new model.
if stable_bucket(user_session_id) < 0.10:
    model_version = "new"
    response = new_fine_tuned_model(query)
else:
    model_version = "baseline"
    response = baseline_model(query)

# Log metrics with the sticky session assignment.
log_metrics(model_version, user_session_id, query, response, user_feedback)
```

The session-level assignment is intentional. Routing each query with `random.random()` can switch the same user between model variants during a single conversation, contaminating the experiment and degrading user experience. Production A/B tests should keep each user, account, or session consistently assigned to the same model variant for the full experiment window, while still allowing immediate rollback if safety or compliance thresholds are breached.

In regulated financial environments, A/B testing also serves a governance function: it provides documented evidence that a model was validated in production conditions before being granted full operational status, and it creates a natural rollback point if the new model behaves unexpectedly. The metrics to monitor span both technical and business dimensions:

- User satisfaction scores
- Task completion rates
- Error reports
- Latency and cost

Latency and cost are especially relevant for PEFT-based models. Although adapter-based approaches generally add minimal inference overhead, 4-bit quantized models may exhibit throughput differences on certain hardware configurations that are only observable at production traffic volumes.

## 3.8.5 Finance-specific evaluation checklist

Standard NLP metrics (accuracy, F1, BLEU, ROUGE) are necessary but insufficient in financial applications. Even with careful offline evaluation and robustness testing, there remains a gap between scoring well on benchmarks and behaving reliably in real financial workflows. The checklist below makes that gap explicit by focusing on the domain-specific risks that standard NLP metrics tend to overlook, and that often determine whether a model is truly fit for production:

- **Numerical accuracy**: Verify that the model preserves and correctly manipulates numerical quantities (rates, spreads, amounts), with unit checks and consistency across the output.
- **Faithfulness and hallucination control**: Use retrieval-augmented setups where possible and measure whether answers are grounded in the provided context (citations, span overlap, factuality scores).
- **Temporal leakage**: When evaluating on historical data, ensure that the model cannot access future information (documents, prices, labels) that would not have been available at decision time.
- **Distributional robustness**: Test performance across market regimes (calm vs. crisis), asset classes, regions, and languages; monitor degradation during regime shifts.
- **Bias and fairness**: Analyse systematic differences in errors across issuers, sectors, rating buckets, or geographies that could create unwanted bias in credit decisions or coverage.
