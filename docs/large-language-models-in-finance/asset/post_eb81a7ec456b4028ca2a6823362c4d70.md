
- 5. require explicit human sign-off before any memo is sent externally or translated into a trading decision.

### Step 8: Evaluate the prototype before expanding scope

Evaluation should begin before the workstation is connected to live data. A useful test set should include normal requests, ambiguous requests, missing-data scenarios, prompt-injection attempts, contradictory evidence, and policy-edge cases. Each test case should define the expected behavior of the whole workflow, not merely the expected text of the final memo.

The team can score each run using both deterministic checks and human review. Useful measures include whether all material claims are cited, whether numerical claims match the data snapshot, whether stale inputs are surfaced, whether policy flags are preserved in the final memo, and whether the workflow escalates when expected. This evaluation set then becomes a regression suite: any new model, prompt, tool, or retrieval index must be run against it before deployment.

### Step 10: Add a human review workflow and deployment modes

A minimal prototype may simply return the final memo to the user. A deployable workflow should instead return a review packet. The reviewer should see the memo, the material claims, the evidence behind each claim, the computed metrics, and the risk annotations in one place. This encourages review of the reasoning path rather than passive acceptance of the final prose.

```
class ReviewPacket:
    def __init__(self, state):
        self.memo = state.final_memo
        self.claims = extract_material_claims(state.final_memo)
        self.evidence_map = link_claims_to_sources(
            claims=self.claims,
            research_notes=state.research_notes
        )
        self.metric_checks = validate_metrics(state.data_metrics)
        self.risk_annotations = state.risk_annotations
        self.audit_log = state.audit_log
        self.allowed_actions = [
            "approve_for_internal_use",
            "request_revision",
            "escalate_to_compliance",
            "reject_output"
        ]
```

The review workbench should make the conservative action easy. If the packet contains a restricted-list flag, a missing critical document, or an unresolved numerical inconsistency, approval should either be disabled or routed through an escalation path. This design choice matters because human-in-the-loop systems can still fail if the human is presented with a polished answer but no practical way to inspect or challenge it.

The same workstation can also be deployed at different levels of autonomy:

- 1. **Advisory mode**: the system drafts internal notes, all tools are read-only, and all outputs are reviewed before use.
- 2. **Assisted workflow mode**: the system prepares review packets, routes flagged cases, and records approvals, but humans still approve all material outputs and portfolio actions.
- 3. **Controlled automation mode**: the system may perform low-risk, reversible operational actions under predefined limits, while investment, client, and regulatory decisions remain subject to approval.

For the research workstation, the appropriate initial deployment is advisory or assisted workflow mode. The system should improve the quality and speed of research preparation, not remove accountability from analysts, portfolio managers, or control functions.

This guided build makes the earlier conceptual architecture tangible: the workstation is not a vague collection of agents, but a controlled workflow in which specialist agents produce inspectable intermediate artifacts that a human decision-maker can review.

## 5.4 Design patterns for governed agentic workflows

To make agentic systems robust and maintainable in financial environments, it is useful to adopt design patterns that encode lessons learned and common requirements. We highlight several patterns that recur across successful deployments.

### 5.4.1 Tool-centric agents

In many applications, the primary value of an agent comes from its ability to orchestrate tools and data sources. A _tool-centric agent_ is designed around a set of tools, with the LLM acting as a controller that decides which tools to call, with what inputs, and how to interpret the outputs.

The research literature converges on the same starting point. Schick et al. [2023] showed that tool use can be acquired in a self-supervised way; Qin et al. [2024] scaled tool use to a large real-world API surface; and Patil et al. [2024] demonstrated the failure mode that matters most for finance, namely that models confidently hallucinate API calls — inventing arguments, endpoints, and semantics that do not exist. In a research assistant, a hallucinated call is a broken demo. Behind a trading or entitlements API it is an incident. A schema is therefore not documentation; it is the last place the error is cheap.

Key principles for tool-centric agents include:

- tools should have clear, machine-readable schemas for inputs and outputs;
- tool calls should be logged and monitored;
- agents should handle tool errors gracefully, providing fallbacks or meaningful error messages;
- tools should enforce access control and data minimization.

In the research workstation, the tool-centric pattern means that retrieval, market-data access, portfolio-limit checks, and policy lookup are not hidden inside a free-form prompt. They are exposed as separate tools with explicit permissions and auditable call records. This makes it possible to answer questions such as: Which documents supported this memo? Which market data snapshot was used? Which policy rules generated the risk flags? Without this tool boundary, the final output may look polished but remain hard to govern.

### 5.4.2 Role-based prompts

Prompt design is central to agent behavior. Role-based prompts are prompts that explicitly assign a role to the agent, describe its objectives and constraints, and provide examples. For example:

> “You are a senior equity research analyst at an investment firm. Your task is to analyze company filings and earnings calls, and to produce concise, financially sound summaries for portfolio managers. You must avoid speculation, clearly distinguish between facts and judgments, and highlight key risks and assumptions.”

Role-based prompts help align the model's behavior with institutional expectations and can be used as part of model risk and compliance documentation. In practice, these prompts should be versioned and reviewed like other model artifacts. For the research workstation, the Research Analyst prompt should emphasize evidence and citations, the Data Analyst prompt should emphasize numerical consistency and data freshness, the Risk and Compliance prompt should emphasize conservative escalation, and the Orchestrator prompt should emphasize synthesis without inventing unsupported claims.
