### 4.9.1 Corrective RAG (CRAG)

The motivation behind Corrective RAG [Yan et al., 2024] is simple: in a real corpus, retrieval is often partially wrong, and a baseline RAG pipeline has no mechanism to notice. CRAG adds a lightweight quality assessment between retrieval and generation. If the retrieved set is judged Correct, generation proceeds as usual; if it is Ambiguous, the system supplements the retrieved set with additional evidence (typically web search); if it is Incorrect, the system reformulates the query and retries. The result is a pipeline that degrades gracefully on the kinds of noisy or under-covered queries that are common in regulatory and research corpora.

```
Algorithm 12 Corrective RAG
1: Input: Query q, RAG system R, LLM M
2: Retrieve documents: \( D \leftarrow \mathcal{R}.\text{retrieve}(q) \)
3: Assess quality: \( \text{quality} \leftarrow \mathcal{M}.\text{evaluate}(q, D) \)
4: if quality = CORRECT then
5: **return** \( \mathcal{M}.\text{generate}(q, D) \)
6: else if quality = AMBIGUOUS then
7: \( D_{\text{web}} \leftarrow \text{WebSearch}(q) \)
8: **return** \( \mathcal{M}.\text{generate}(q, D \cup D_{\text{web}}) \)
9: else
10: \( q' \leftarrow \mathcal{M}.\text{reformulate}(q) \)
11: \( D' \leftarrow \mathcal{R}.\text{retrieve}(q') \)
12: **return** \( \mathcal{M}.\text{generate}(q, D') \)
13: end if
```

### 4.9.2 Self-RAG: Self-reflective retrieval

Asai et al. [2023] propose self-RAG, which decides when to retrieve and critiques its own outputs, learning a policy over retrieval, generation, and self-critique to optimize downstream task performance.

The core idea is to recast retrieval as a decision the model makes rather than a fixed step in the pipeline. At each generation step the model first emits a control signal indicating whether retrieval is needed; if so, it retrieves, conditions on the retrieved passages, and generates. It then critiques its own draft along several dimensions—typically relevance, support by sources, and completeness—and either accepts the answer or loops back, retrieving more or rewriting. This structure lets the system avoid spurious retrievals on questions that the model already knows how to answer (where unnecessary retrieval often degrades quality), while applying retrieval more aggressively on questions whose grounding signal is initially weak.

```
Algorithm 13 Self-RAG generation
1: Input: Query q, max iterations T
2: Initialize context c ← ""
3: for t = 1 to T do
4: if ShouldRetrieve(q, c) then
5: D ← Retrieve(q, c)
6: c ← c ∪ D
7: end if
8: r ← Generate(q, c)
9: scores ← Critique(q, r, D)
10: if scores are sufficient then
11: return r
12: end if
13: c ← c ∪ r {Add to context for next iteration}
14: end for
15: return final r
```

Self-RAG evaluates responses on:

- Relevance: Does it answer the question?
- Support: Is it supported by sources?
- Completeness: Is the answer complete?

Each dimension can be scored on a 0–10 scale. A threshold such as ≥ 8 is useful for a prototype, but in regulated settings it should be calibrated against a labeled validation set and reviewed by domain experts rather than adopted as a universal rule.

### 4.9.3 Agentic RAG

Agentic RAG embeds retrieval inside a broader tool-using reasoning loop [Yao et al., 2023b, Shinn et al., 2023]. Where baseline RAG performs a single retrieve-then-generate step, an agentic system treats retrieval as one of several tools the model can call, alongside calculators, web search, and structured data sources. At each step, the model emits a thought, selects an action, observes a result, and updates its plan. This pattern is well-suited to financial tasks that genuinely require multi-step reasoning—computing a metric from retrieved figures, cross-referencing a regulation against an internal policy, or assembling a board-level briefing from heterogeneous sources—where no single retrieval call is enough.

```
Algorithm 14 Agentic RAG loop
1: Input: Query q, tools T = {retrieve, calculate, search_web, finish}
2: Initialize conversation C ← [q]
3: for step = 1 to max_steps do
4:   Generate thought: thought ← LLM(C)
5:   Parse action: (action, params) ← Parse(thought)
6:   if action = finish then
7:     return params["answer"]
8:   end if
9:   Execute: observation ← T[action](params)
10: C ← C ∪ [thought, observation]
11: end for
12: return error (max steps exceeded)
```

This approach allows the system to:

- Decide when retrieval is needed
- Combine multiple tools (retrieval, calculation, web search)
- Reason about intermediate results
- Iteratively refine answers

### 4.9.4 Choosing between advanced RAG patterns

The advanced patterns introduced in this section can be interpreted as targeted remedies for characteristic failure modes of basic RAG systems. Table 4.3 summarizes their core ideas, principal financial use cases, and the main trade-offs involved.

| Pattern | Core idea | When to use | Trade-offs |
|---|---|---|---|
| Corrective RAG (CRAG) | Assess and repair retrieval quality | Noisy corpora, mixed-quality disclosures, heterogeneous sources | Extra latency; requires reliable meta-evaluation. |
| Self-RAG | Let the model decide when and what to retrieve | Complex questions where information may or may not be in the corpus | More complex prompting and control flow. |
| Agentic / tool-augmented RAG | Combine retrieval with tools and multi-step reasoning | Scenario analysis, stress testing, and complex regulatory questions | Highest implementation complexity; requires orchestration and governance. |

Table 4.3: Comparison of advanced RAG patterns for financial applications

In practice, many production systems blend these patterns. A common design for regulated financial Q&A is a baseline RAG pipeline, augmented with a CRAG-style quality gate, and an agentic layer only for explicitly approved high-value workflows (for example, cross-regulation impact analysis or board-level briefing preparation).

## 4.10 RAG evaluation

Once a RAG system has been built, the next question is how to know whether it is good enough. In a financial setting, the question matters more than usual: a wrong answer about capital requirements, a fabricated quote from an earnings call, or a confidently stated but unsupported claim about a regulation can have direct legal and reputational consequences. Evaluation is therefore not an optional final step but the mechanism by which a RAG pipeline becomes deployable in a regulated environment.

We distinguish three layers of evaluation in this section. **Retrieval metrics** (Recall@k, Precision@k, MRR, NDCG) measure whether the right evidence is being surfaced and how well it is ranked. **Generation metrics** (faithfulness, answer relevancy, context relevancy) measure whether the model’s response actually uses that evidence and addresses the question. **End-to-end and protocol-level evaluation** ties these together with a reproducible pipeline and, for regulated use cases, expert review and explicit go/no-go criteria. The retrieval metrics in particular are familiar from classical information retrieval, but their role here is broader: in a RAG system, they are not just IR diagnostics but proxies for the upper bound on generation quality, since the model can only ground its answer in passages that retrieval has actually surfaced.

### 4.10.1 Retrieval metrics

The metrics in this subsection are deliberately compact, since they are standard in the IR literature. The point of restating them is to fix notation and to make explicit how each one is read in a RAG context.

**Recall@k** measures the proportion of relevant documents that appear in the top-_k_ retrieved results. In a RAG system it answers the question: “did retrieval at least give the model a chance to ground its answer?” A low Recall@k caps the achievable answer quality regardless of how good the generation step is.

$$ \text{Recall@}k = \frac{|\text{Relevant} \cap \text{Retrieved@}k|}{|\text{Relevant}|} \quad (4.15) $$

**Precision@k** measures the proportion of the top-_k_ retrieved documents that are actually relevant. It controls how much noise the model has to read through; low precision typically translates into longer prompts, higher cost, and a higher rate of distracted or hallucinated answers.

$$ \text{Precision@}k = \frac{|\text{Relevant} \cap \text{Retrieved@}k|}{k} \quad (4.16) $$
