
## 6.6.1 A dimensionally consistent capacity objective

Latency targets must be balanced against capacity and cost. Adding more workers can reduce queueing delay and failure probability, but it also increases infrastructure cost. A simple capacity objective should therefore keep all terms in the same unit.

Let H be a planning horizon in hours, c the number of server workers, λ the arrival rate in requests per hour, Cs the server cost per worker-hour, Cw the cost of one request-hour of delay, and Cf the expected cost of a failed or timed-out request. A simple objective is:

```
J(c) = HcCs + HλE[Wq(c)]Cw + Hλpf(c)Cf, (6.12)
```

where Wq(c) is queueing delay in hours and pf(c) is the failure probability. Every term is a monetary amount over the same horizon. The model is intentionally simple, but unlike an expression that adds monthly server cost to per-second delay, it is dimensionally coherent.

## 6.6.2 Latency classes

Different financial workflows require different latency paths. A research assistant, a case-investigation workflow, a human approval step, and a low-latency trading component should not be placed under the same performance target. Table 6.5 gives illustrative latency classes for MCP-assisted workflows.

| Class | Typical budget | Suitable examples and controls |
|---|---|---|
| Interactive research | Seconds to tens of seconds | Filing retrieval, research summarization, scenario drafting; visible citations and cancellation. |
| Operational assistance | Seconds to minutes | Case investigation, report preparation, covenant review; deterministic checks and queue monitoring. |
| Human approval | Minutes to hours | Client communication, limit exception, risk sign-off; reviewer evidence pack and expiry. |
| Low-latency execution | Milliseconds or less | LLMs should remain outside the critical execution loop; use precomputed signals and deterministic controls. |

A language model and remote tool chain are generally inappropriate inside a microsecond or millisecond trading decision loop. They may support research, configuration, surveillance, pre-trade explanation, or signal preparation outside that loop. The performance architecture should therefore match the workflow's risk, latency, and control requirements rather than forcing every use case into the same path.

> > “Produce the close-of-business market-risk summary for Portfolio P, explain the three largest changes, and prepare the report for risk-manager approval.”

This workflow should not be implemented as a single prompt with broad tool access. In a governed MCP design, it is decomposed into a sequence of controlled stages. The model helps interpret validated results and draft the narrative, but deterministic systems remain responsible for identity binding, evidence retrieval, numerical calculation, verification, approval, publication, and audit.

## 6.7.1 A governed six-stage workflow

- 1. **Bind identity, purpose, and decision time.** The host authenticates the user and binds the request to a declared purpose such as `daily-risk-reporting`, the relevant portfolio P, the legal entity, and the decision time _t_. It retrieves or requests a position-snapshot identifier whose availability time is no later than _t_, ensuring that later analysis is anchored to the correct point in time.

- 2. **Retrieve approved evidence.** A read-only MCP server returns the approved position snapshot, market-data snapshot identifiers, the previous approved report and snapshot, and the applicable limit and methodology versions. Before any of this content enters model-visible context, the host verifies permissions, content hashes, freshness, and revision lineage.

- 3. **Run deterministic risk tools.** A calculation server exposes narrow tools such as `calculate_var`, `calculate_stress`, and `explain_pnl_changes`. Each result includes units, as-of time, engine version, input snapshot identifiers, quality flags, and reconciliation totals. The LLM is therefore not asked to compute VaR from prose or infer totals from loosely structured evidence.

- 4. **Generate a cited narrative.** The model receives only validated outputs and controlled evidence summaries. It drafts a narrative explanation of the report, links material statements to evidence identifiers, and marks whether approval is required. A simplified structured output might look as follows:

### Listing 6.2: Structured narrative output for risk reporting

```
{
"summary": "Market VaR increased by 7.4% ...",
"material_claims": [
{
"claim": "Rates exposure was the largest contributor.",
"evidence_ids": ["pnl-attr-2026-07-13", "var-run-8841"],
"calculation_id": "attr-engine-v4.2/run-8841"
}
],
"unresolved_warnings": [],
"approval_required": true
}
```

A verification step then checks that each material claim is supported by admissible evidence and that every quoted number matches the deterministic result object.

- 5. **Approve the exact report artifact.** The reviewer sees the narrative, supporting tables, data freshness indicators, model and engine versions, exceptions, unresolved warnings, and the canonical request hash. Approval is bound to the exact artifact that will be published and must expire automatically if any material input changes.

- 6. Publish and reconcile. A separate publication tool distributes the approved report to the authorized recipient list. It records the artifact hash, delivery status, and execution identifier. A reconciliation process then confirms that exactly one approved report was published for the relevant portfolio and date, preventing duplication or drift between the approved and distributed versions.

## 6.8 Validation and adversarial testing

A deployment should not be approved merely because a demonstration succeeds. A material MCP-assisted workflow should pass a versioned test suite that covers protocol behavior, financial correctness, security, policy enforcement, and recovery. The goal is to test not only whether the workflow works under normal conditions, but also whether it fails safely under malformed inputs, stale data, adversarial content, unavailable services, and partial execution.

The test suite should include the following categories:

- • Protocol conformance tests: Test lifecycle negotiation, capability changes, malformed JSON-RPC, unsupported methods, pagination, cancellation, timeouts, session expiry, transport reconnects, and version mismatch. For Streamable HTTP, also test origin rejection, authentication failures, secure session handling, and replay behavior.

- **Policy tests:** For each tool, create allow, reject, and escalate cases across roles, portfolios, legal entities, jurisdictions, market states, restricted instruments, data classifications, amount limits, and approval states. Deny-by-default behavior should be tested directly.

- **Prompt-injection and data-exfiltration tests:** Place adversarial instructions in filings, emails, resource metadata, tool descriptions, tool results, and prior agent memory. Verify that the model cannot cause a call outside the allow-list, expose credentials, override the system purpose, or bypass approval.

- **Numerical and temporal tests:** Use known accounting identities, risk-engine fixtures, currency and unit changes, stale snapshots, revised filings, future-dated documents, missing prices, corporate actions, and daylight-saving boundaries. The system should reject unresolved ambiguity rather than produce a polished but invalid answer.

- **Reliability and recovery tests:** Inject server failure before and after execution, dropped responses, duplicated requests, delayed approvals, partial audit writes, rate limits, and network partitions. Confirm exactly-once business effects, reconciliation, and a recoverable final state.

The following release gate summarizes the minimum evidence expected before a material financial MCP workflow is approved for production use.

| Gate | Minimum evidence |
| :--- | :--- |
| Protocol | Conformance suite passes for the pinned protocol and transport versions. |
| Authorization | Complete role/attribute matrix; no unauthorized tool execution in negative tests. |
| Temporal integrity | No retrieved item after the decision time; revision and freshness tests pass. |
| Numerical integrity | Material values reconcile to deterministic engines within documented tolerances. |
| Security | Prompt-injection, confused-deputy, secret-leakage, origin, and egress tests pass. |
| Reliability | Retry, idempotency, timeout, cancellation, and disaster-recovery tests pass. |
| Human factors | Review screen supports informed approval; override, decline, and escalation are tested. |
| Audit | A sample decision can be reconstructed from identifiers, versions, evidence, and hashes. |
| Change control | Model, prompt, server, schema, policy, and dependency changes trigger appropriate revalidation. |
