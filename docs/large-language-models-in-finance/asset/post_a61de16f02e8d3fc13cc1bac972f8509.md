## 6.3.1 From threats to control ownership

The threat model should be read as a control-allocation exercise. Each threat identifies where the failure can enter the workflow, which component should prevent or detect it, and what evidence should be available during review. For example, prompt injection is not controlled by asking the model to ignore malicious instructions. It is controlled by treating retrieved content as untrusted data, separating instructions from evidence, restricting tools through an allow-list, and validating every proposed tool call outside the model. Similarly, duplicate execution is not controlled by a better prompt; it requires idempotency keys, execution ledgers, and reconciliation.

For each threat in Table 6.3, the implementation should answer four practical questions: where is the control enforced, who owns it, what evidence is logged, and what happens when the control fails. This makes the threat model actionable rather than merely descriptive.

## 6.3.2 Trust boundaries and tool metadata

Every deployment should draw explicit trust boundaries. These boundaries define where information, authority, or responsibility changes hands. At minimum, a financial MCP deployment should separate:

- user input from host policy;
- model-visible context from secrets;
- the host/client from each MCP server;
- an MCP server from the underlying financial system;
- an explanation presented to a reviewer from the exact object approved for execution.

These boundaries are useful only if they are reflected in implementation. Each boundary should have a clear enforcement mechanism, such as authentication, schema validation, network segmentation, purpose binding, entitlement checks, or approval hashing. It should also have a logged failure mode. If a server cannot prove its schema version, the host should reject or quarantine the tool. If an approval applies to one request hash, a changed payload should require a new approval.

A server is not trusted merely because it speaks MCP. Protocol compatibility says nothing about who operates the server, what code it runs, what data it records, or whether its tool description is accurate. The host should therefore treat server metadata as part of the attack surface.

Tool names and descriptions are especially important because they influence model selection. A tool described as “retrieve account summary” may in reality accept a broad account identifier and return protected data. The host should obtain tool metadata from an approved registry, pin a reviewed schema hash, and display the effective permission to users. Review must cover implementation, schema, authorization behavior, logging, and downstream side effects, not only the natural-language description.

## 6.3.3 Authorization, consent, and least privilege

After the threat model has identified where failures can enter the workflow, the authorization layer defines what each user, service, and tool is allowed to do. In finance, authorization must be evaluated at the level of the business action, not only at the level of protocol access.

A financial authorization decision is attribute-rich. A practical policy evaluates at least:

(principal, role, desk, legal entity, purpose, portfolio, product, jurisdiction, action, time).

Role-based access control alone is insufficient because the same analyst may be permitted to read one portfolio, prohibited from another, and able to create but not approve a client-facing report. Attribute-based and relationship-based policies are therefore often required.

## 6.3.4 Permission modes and business effects

Tool permissions should distinguish the business effect of an operation rather than grouping all operations under a generic “write” scope. A practical permission model separates at least five modes:

- Read: retrieve authorized, purpose-limited data.
- Calculate: run deterministic analytics without changing business state.
- Draft: create a non-binding artifact or proposed action.
- Approve: attest that a specific object may proceed.
- Execute: create an external or financially material side effect.

This distinction matters because the same tool interface may have very different risk depending on its effect. Reading a position snapshot, calculating value-at-risk, drafting a risk memo, approving that memo, and publishing it to a controlled recipient list are separate actions. They should not share the same authorization path.

The model should normally operate in the first three modes: read, calculate, and draft. Approval and execution require separate identities, explicit mandates, stronger monitoring, and, where appropriate, segregation of duties. A model-generated proposal should not become an executed action simply because the proposed tool call is syntactically valid.

## 6.3.5 Consent and human review

A human-in-the-loop control is meaningful only when the reviewer has enough information to make an informed decision. The review screen should show:

- which server and tool will be used;
- the exact normalized parameters;
- data sources and their availability times;
- deterministic calculations and reconciliation results;
- applicable limits, exceptions, and unresolved warnings;
- the business effect of approval;
- a stable request hash.

A generic confirmation such as “Allow this tool?” is not adequate for a material financial action. It encourages automation bias because the reviewer sees the model’s proposed action without enough evidence to challenge it. Review should be proportional to impact: a low-risk read request may need only routine logging, while a client communication, limit exception, trade-related action, or regulatory report may require evidence review, approval binding, and escalation.
