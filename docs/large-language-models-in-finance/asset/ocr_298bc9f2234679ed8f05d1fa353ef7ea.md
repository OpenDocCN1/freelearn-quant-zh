| Design criterion | Long-context prompting | RAG / document graph |
| :--- | :--- | :--- |
| Corpus size | Best when the full evidence set fits comfortably in the prompt. | Best when the corpus contains many filings, policies, transcripts, or research notes. |
| Freshness | Requires rebuilding or selecting the prompt whenever evidence changes. | Indexes can be refreshed incrementally and versioned. |
| Permissions | Harder to enforce fine-grained access once text enters the prompt. | Metadata filters can enforce user, desk, region, or document-level permissions before generation. |
| Citation and auditability | Possible, but attribution can degrade in very long prompts. | Retrieval logs, chunk identifiers, and source metadata create an explicit audit trail. |
| Latency and cost | Can be expensive when many irrelevant tokens are included. Useful for synthesis over a known bundle. | Adds retrieval latency but usually reduces generation tokens. Better when evidence must be discovered, deduplicated, ranked, and linked across documents. |
| Cross-document reasoning | Useful for synthesis over a known bundle. | Better when evidence must be discovered, deduplicated, ranked, and linked across documents. |

Table 4.2: Choosing between long-context prompting and RAG/document-graph architectures

For financial tasks, the practical rule is simple: use long-context prompting when the analyst already knows which documents matter and wants synthesis; use RAG when the system must find the documents, enforce permissions, keep evidence fresh, and explain why a passage was used. A document graph becomes valuable when the answer depends on relationships among documents—for example, comparing a current 10-Q with prior 10-K risk factors, linking a covenant definition to its amendment, or reconciling a regulatory rule with an internal policy.

# 4.8 RAG implementation: Financial Q&A system

We have so far covered embedding models, vector indexes, chunking, and advanced retrieval techniques in isolation. We now bring these pieces together in a compact financial document Q&A system. The objective of this section is to show how the abstract pipeline of Section 4.2 maps onto compact, readable code, and to give the reader a reference implementation that can be adapted to a corpus, embedding provider, and vector store. The example is intentionally not a full production system: it leaves enterprise IAM, PII controls, secrets management, logging, queueing, cost governance, and formal compliance review outside the listing so that the core RAG mechanics remain visible.
