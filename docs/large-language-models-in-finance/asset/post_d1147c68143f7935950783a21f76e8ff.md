

### 12.6.1 Evidence-status taxonomy

To make the matrix operational, this book uses four evidence statuses.

**Status A** – independently reproducible. Public data or a legally shareable frozen sample, executable code, exact environment, model and prompt versions, temporal protocol, and results reproduced by a party independent of the original claim.

**Status B** – primary study with auditable artifacts. The original authors provide sufficient methodological and artifact detail for a technically informed reader to reconstruct the experiment, but independent reproduction is absent or incomplete.

**Status C** – reported result with incomplete audit path. A paper, vendor, or project reports a number, but one or more of the dataset, point-in-time protocol, model version, prompt, code, uncertainty interval, or failure set is unavailable.

**Status D** – illustrative or synthetic. The example demonstrates a mechanism or calculation and makes no empirical performance claim.

The status applies to a particular claim, not permanently to a model family. A FinBERT classifier may be Status A on a released temporal benchmark and Status C in a proprietary deployment claim. Likewise, an open repository can remain Status C when the exact checkpoint, data snapshot, or evaluation path is missing.

### 12.6.2 Minimum comparison record

Any table that compares financial LLM systems should disclose the following record for each row:

$\mathcal{R} = (D, \tau, M, P, R, T, C, G, U, A)$

where $D$ is the dataset and license, $\tau$ the temporal protocol, $M$ the model and tokenizer version, $P$ the prompt or adaptation configuration, $R$ the retrieval and tool environment, $T$ the task definition, $C$ the cost and market-friction assumptions, $G$ the governance controls, $U$ the uncertainty analysis, and $A$ the artifact location. A blank field is itself information: it limits what can be inferred from the reported result.

## 12.7 From illustrative examples to audited empirical evidence

The empirical standard for financial LLMs should be higher than “the model produced a plausible answer.” A result becomes credible only when the information set, benchmark, metric, and failure analysis are explicit. This book therefore distinguishes four levels of empirical evidence.

- 1. **Illustrative example:** a single example used to explain a method. It may be useful pedagogically but should not be cited as evidence of performance.
- 2. **Reproducible smoke test:** a deterministic script with fixed inputs and expected outputs. It catches broken code paths but does not establish financial value.
- 3. **Benchmark experiment:** a documented dataset, temporal split, model version, prompt version, and metric suite. It supports comparative claims within the benchmark’s scope.
- 4. **Audited deployment evidence:** production or pilot evidence with logged decisions, review outcomes, confidence intervals, failure cases, human overrides, and post-deployment monitoring.

A strong empirical table should therefore report not only accuracy or F1, but also the maturity level of the evidence. For example, a RAG experiment over filings should state the filing universe, timestamp cutoff, retrieval index hash, chunking policy, citation-faithfulness metric, number of expert-reviewed answers, confidence interval, and number of high-severity failures. A time-series LLM experiment should state the walk-forward split, rebalancing schedule, transaction-cost assumptions, survivorship policy, hyperparameter-selection window, and whether benchmark contamination checks were run.

**Proposition 12.7.1** (Minimum evidence condition for performance claims). A financial LLM performance claim is auditable only if a reviewer can reconstruct the tuple

```
(D_{<=t}, f_\theta, p, r, m, \ell, \mathcal{A}),
```

where \(\mathcal{D}_{\le t}\) is the admissible data, \(f_\theta\) is the model, p is the prompt or policy template, r is the retrieval index and corpus version, m is the metric, \(\ell\) is the loss or scoring rule, and \(\mathcal{A}\) is the audit log. Without this tuple, the claim may still be a useful illustration, but it is not reproducible evidence.

**Proof.** Changing any component of the tuple can change the measured result: the data determine what information was available; the model and prompt determine the mapping from information to output; the retrieval version determines the evidence visible to the generator; the metric and loss determine what is being rewarded; and the audit log determines whether the run can be reconstructed. If any component is missing, two reviewers cannot determine whether they are evaluating the same experiment.

- **4 Audited deployment evidence:** Logged decisions, CIs, failure cases, human overrides, monitoring.
- **3 Benchmark experiment:** Dataset, temporal split, model + prompt version, metric suite.
- **2 Reproducible smoke test:** Fixed inputs, expected outputs. Catches broken code, not value.
- **1 Illustrative example:** Explains a method. **Never** evidence of performance.

*Most published financial-LLM results are level 1 or 2, reported in the language of level 3 or 4.*

## 12.8 Summary

This chapter reviewed how large language models are being specialized, assembled, and evaluated for financial applications. The first lesson is that domain specialization matters. BloombergGPT, FinBERT, FinEAS, FinGPT, and related systems show that financial corpora, financial terminology, and financial task definitions change the behavior of otherwise familiar transformer architectures. The relevant design choice is not only which base model to use, but also how to allocate data, adaptation budget, retrieval infrastructure, and evaluation effort.

The second lesson is that financial LLMs increasingly appear as components of larger systems rather than as isolated chat models. Memory-augmented trading agents, debate-based multi-agent systems, portfolio-level agents, and LLM-assisted risk workflows all reflect the same architectural shift: financial work is sequential, evidence-driven, role-based, and governed. This makes explicit memory, tool access, audit logs, and human review as important as raw language-model accuracy.

The third lesson is that empirical claims must be interpreted carefully. Many reported results are promising, but they are often early, narrow, or sensitive to backtest design. Multi-task benchmarks, numerical reasoning datasets, case-triage workflows, and cost-aware simulations each illuminate only part of the problem. For practical deployment, capability has to be assessed jointly with robustness, governance, privacy, explainability, and operational risk. The central message is therefore one of disciplined integration: financial LLMs are most useful when they are embedded in transparent, validated, and auditable systems rather than treated as standalone sources of financial truth.

## 12.9 Open questions and research directions

Several research questions remain open before financial LLM systems can be understood as mature production infrastructure. The first concerns robustness across regimes, asset classes, institutions, and structural breaks. Many reported experiments are encouraging, but they are often conducted on narrow asset universes, short windows, or static document collections. A stronger research program would evaluate whether an LLM-based agent that works in one market environment continues to behave sensibly when liquidity, volatility, macro conditions, or regulatory constraints change.

A second question concerns evaluation under realistic frictions. Financial benchmarks must eventually incorporate transaction costs, market impact, latency, adversarial behavior, stale documents, missing data, and changing portfolio constraints. A model that is accurate on static financial NLP tasks is not automatically reliable in a workflow where an incorrect retrieval, a hidden prompt injection, or a small numerical error can propagate into a costly decision. This motivates benchmark designs that combine task accuracy with evidence faithfulness, numerical validation, cost-aware simulation, and human escalation rules.

A third question is mathematical. We still need better abstractions connecting the statistical learning properties of LLMs with the economic and game-theoretic structure of markets. Memory, tool use, and multi-agent debate are promising engineering devices, but their stability properties remain incompletely understood. Finally, fairness, privacy, explainability, and auditability must be embedded into the architecture itself rather than appended as after-the-fact controls. These issues link the empirical material of this chapter to the broader governance framework of Chapter 11.
