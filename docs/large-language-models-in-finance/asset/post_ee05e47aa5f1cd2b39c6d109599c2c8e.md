Once the data sources have been identified, the next step is to transform this raw, heterogeneous data into a form suitable for training through careful preprocessing and quality control.

## Data preprocessing and quality control

Raw financial text arrives in a wide variety of formats (HTML-stripped filings, OCR'd PDFs, newsfeeds with inconsistent encoding) and requires careful normalization before it can be fed to a tokenizer. The cleaning operations that matter most for financial text differ from those in general NLP. Currency symbols, percentage signs, and decimal separators must be preserved and standardized rather than stripped, because numerical context is often the primary signal the model needs to learn from. Removing a dollar sign before a figure, or collapsing whitespace around a percentage, can cause the tokenizer to merge tokens in ways that obscure meaning.

To make these considerations concrete, the following function illustrates a simple preprocessing routine designed for financial text. In practice, this text cleaning step is less about aggressively cleaning the input but about preserving key numerical and symbolic information while standardizing formatting in a way that is compatible with downstream tokenization:

```
import re
import unicodedata

def clean_financial_text(text):
    # Normalize Unicode and whitespace without changing financial semantics.
    text = unicodedata.normalize("NFKC", text)
    text = re.sub(r'\s+', ' ', text)
    # Standardize currency symbols while preserving signed numbers.
    text = re.sub(r'([$€£¥])\s*([+-]?\d)', r'\1 \2', text)

    # Handle percentages without destroying decimals or signs: -8.5% -> -8.5 %.
    text = re.sub(r'([+-]?\d+(?:\.\d+)?)\s*%', r'\1 %', text)

    # Remove only control characters. Do not strip punctuation wholesale: it may
    # encode dates (2024-03-31), times (14:30), decimals (3.25), ratios,
    # credit ratings (A-), tickers (BRK.B), or signed values (-8 %, +12 bps).
    text = re.sub(r'[\x00-\x1f\x7f]', '', text)

    return re.sub(r'\s+', ' ', text).strip()
```

This example is deliberately conservative. Production cleaning should be validated with a small regression suite containing dates, times, decimals, ticker symbols, credit ratings, legal references, and signed values. A regex that improves general text cleanliness can still damage financial meaning; for instance, removing colons can corrupt times, removing hyphens can corrupt dates and ratings, and removing plus/minus signs can reverse the interpretation of growth or spread changes.

Once the text is clean, a second pass of **quality filtering** removes examples that would degrade training. In financial NLP, this step is particularly consequential: a mislabeled credit opinion or a duplicated earnings sentence with contradictory annotations teaches the model the wrong mapping and is difficult to recover from later. The four checks below address the most common failure modes:

- Remove duplicates and near-duplicates (MinHash, SimHash)
- Filter low-quality content (length filters, readability scores)
- Validate annotations (inter-annotator agreement, expert review)
- Balance class distributions (oversample minorities, undersample majorities)

With clean, filtered data in hand, the final preparation step is constructing the train, validation, and test splits. How these **data splits** are performed is especially consequential in finance: a random split applied to time-stamped financial data can leak future information into the training set, producing inflated evaluation metrics that do not reflect real deployment performance.

In most cases, practitioners allocate approximately 70–80% of the data for training, 10–15% for validation, and 10–15% for testing, with the test set kept strictly separate from model development. For time-series financial data, use temporal splits to prevent lookahead bias.

The snippet below shows a typical temporal split setup: the model sees only data from years prior to the validation and test periods, mirroring the constraint that exists in production, where the model is always predicting into the future:

```
# Temporal split: Train on 2018-2021, validate on 2022, test on 2023
train_data = data[data['year'] <= 2021]
val_data = data[data['year'] == 2022]
test_data = data[data['year'] == 2023]
```

With a well-constructed dataset in place, covering sourcing and preprocessing, we can now turn to how this data is actually used during training, including the choice of hyperparameters and optimization strategy.

## 3.4.2 Training configuration

With a well-prepared dataset in place, the next step is to determine how the model will be updated during fine-tuning. Training configuration translates the dataset into learning dynamics: it defines how quickly the model adapts, how stable the optimization process remains, and how well the resulting model generalizes beyond the training data.

This subsection focuses on two aspects of this process. We begin with hyperparameter selection, where we examine the key controls that govern optimization behavior. We then turn to the training procedure itself, outlining how these choices come together in a standard fine-tuning loop.

### Hyperparameter selection

Choosing the right hyperparameters for fine-tuning is as much art as science, and financial NLP settings have well-established defaults that provide a reliable starting point. Let’s look at the four parameters that most directly determine whether fine-tuning converges stably and generalizes beyond the training set.

The learning rate is the most sensitive hyperparameter. Fine-tuning uses rates in the range 1e-5 to 5e-5—roughly 10 to 100 times smaller than those used during pre-training—because the goal is to adjust the model’s already-useful representations, not overwrite them. A learning rate warm-up ramp is used to protect the model during the first few hundred steps, when the newly initialized classification head is producing large, noisy gradients that could destabilize the pre-trained weights if applied at full strength immediately. The schedule below linearly increases the rate during warm-up, then linearly decays it for the remainder of training:

\[
\eta_t = \begin{cases} \eta_{max} \cdot \frac{t}{T_{warmup}} & \text{if } t \le T_{warmup} \\ \eta_{max} \cdot \frac{T_{total}-t}{T_{total}-T_{warmup}} & \text{otherwise} \end{cases} (3.6)
\]

When talking about batch sizes, larger batches produce more stable gradient estimates and generally lead to smoother convergence, but they consume proportionally more GPU memory because the activations saved for back-propagation scale approximately linearly with the micro-batch size and the sequence length. A useful way to read the commonly used range of 16–32 examples per GPU is therefore not as a theoretical constant, but as a practical starting point for encoder-style fine-tuning with moderate sequence lengths, such as BERT-class models with inputs up to 512 tokens. The range comes from a simple engineering compromise: choose the largest per-device micro-batch that fits in memory without out-of-memory errors; then adjust gradient accumulation so that the optimizer sees a sufficiently stable effective batch.

Formally, if \( B_{dev} \) is the per-device micro-batch, \( G \) is the number of GPUs, and \( A \) is the number of gradient-accumulation steps, then the optimizer behaves as if it had received

\( B_{eff} = B_{dev} G A \quad (3.7) \)

examples per update. Thus, a single-GPU run with \( B_{dev} = 16 \) and \( A = 4 \) has an effective batch of 64, while a four-GPU run with \( B_{dev} = 16 \) and \( A = 2 \) has an effective batch of 128. This is the reason the text recommends 16–32 per GPU as an initial micro-batch range rather than a final effective-batch prescription.

```
effective_batch_size = batch_size_per_gpu * num_gpus * grad_accum_steps
```

The same rule should be scaled down for larger decoder-only models, longer context windows, or QLoRA settings. In those cases, the 4-bit base model reduces parameter memory, but activation memory can still dominate, so the feasible per-device micro-batch may be only 1–4 examples. Gradient accumulation is then used to recover an effective batch in the 32–128 range without exceeding GPU memory.

The **number of epochs** is another important consideration. Financial datasets are often small, which means each training epoch cycles through the data quickly, and overfitting can set in fast. The usual 3–5 epoch range for encoder-based classification is best understood through the number of optimizer updates:

\( U = E \left\lceil \frac{N_{train}}{B_{eff}} \right\rceil, \quad (3.8) \)

where \( E \) is the number of epochs and \( N_{train} \) is the number of training examples. For example, with \( N_{train} \approx 4,000 \) and \( B_{eff} = 32 \), three to five epochs produce roughly 375–625 optimizer updates, which is usually enough to adapt the classification head and upper transformer layers without repeatedly memorizing a small dataset. Generative SFT may need fewer epochs (1–3) because each example contributes many token-level loss terms. In practice, the epoch count should be treated as an early-stopping upper bound rather than a fixed target: monitor validation performance after each epoch and halt as soon as improvement stalls rather than training to the preset maximum.

The final parameter to consider is **weight decay**, which controls how strongly the model is regularized during training. In AdamW the decay is *decoupled*: it is applied directly to the parameters as a multiplicative shrinkage \( \theta \leftarrow (1 - \alpha\lambda)\theta \) after the adaptive step, and is *not* an L2 penalty added to the loss. The distinction is not pedantic — an L2 term added to the gradient is rescaled by Adam’s adaptive denominator, so the two methods behave differently
