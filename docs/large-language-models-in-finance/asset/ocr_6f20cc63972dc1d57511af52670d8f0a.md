# 15.7.2 Production deployment stack

The following stack components are examples of common infrastructure categories. Actual choices should follow the institution's security, compliance, latency, reliability, and operational requirements.

+   - **Model serving:** Triton inference server, TorchServe, TensorFlow serving
+   - **Orchestration:** Kubernetes, Airflow, Prefect
+   - **Monitoring:** Prometheus, Grafana, MLflow
+   - **Data storage:** PostgreSQL, MongoDB, S3-compatible object storage
+   - **Message queuing:** Kafka, RabbitMQ, Redis
+   - **API gateway:** Kong, Traefik, AWS API gateway

# 15.8 Reproducibility protocol for empirical financial LLM studies

A financial LLM study should be reproducible at the level of data provenance, temporal splits, model versions, prompt versions, retrieval-corpus versions, and evaluation scripts. The following protocol is the minimum standard assumed by the empirical examples in this book.

+   1. **Data card.** State the data source, license, timestamp, survivorship policy, document universe, preprocessing rules, and any exclusion criteria.
+   2. **Temporal split.** Use walk-forward or strictly chronological train/validation/test partitions. No document, label, embedding, prompt example, or retrieval chunk dated after the decision time may enter the model context.
+   3. **Model card.** Record the base model, tokenizer, fine-tuning method, quantization, context window, inference parameters, and safety filters.
+   4. **Prompt and retrieval versioning.** Hash prompt templates, tool schemas, vector indexes, chunking policies, rerankers, and retrieved evidence bundles.
+   5. **Metrics.** Report task metrics and governance metrics: accuracy or F1, calibration, citation faithfulness, numerical consistency, refusal accuracy, escalation precision, latency, cost, and failure examples.
+   6. **Uncertainty.** Provide confidence intervals or bootstrap intervals where sampling variation matters, and separate illustrative examples from audited empirical results.
+   7. **Audit log.** Store the model version, prompt version, retrieved document identifiers, tool-call parameters, human approvals, and final output hash for every material run.
