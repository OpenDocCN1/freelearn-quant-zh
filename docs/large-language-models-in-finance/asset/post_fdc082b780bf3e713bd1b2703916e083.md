
which is not CQL: Q is a function of (s, a), and the conservative term is a log-sum-exp over actions *at each state in the batch*, minus the value the dataset's own action achieved at that same state. Averaging Q over a bag of sampled actions with the states thrown away penalizes nothing in particular.

Discrete action set below. For continuous actions, replace the exact log-sum-exp with the importance-sampled estimate of Kumar et al.

```
def __init__(self, q_network, dataset, alpha=5.0, n_actions=None):
    self.q_network = q_network        # Q(s, .) -> [B, n_actions]
    self.dataset = dataset
    self.alpha = alpha
    self.n_actions = n_actions
def cql_loss(self, states, actions, rewards, next_states, dones):
    # 1. The ordinary TD / Bellman term.
    td_loss = self.standard_q_loss(
        states, actions, rewards, next_states, dones)
    # 2. The conservative term, evaluated AT EACH STATE.
    q_all = self.q_network(states)        # [B, n_actions]
    logsumexp_q = torch.logsumexp(q_all, dim=1)    # [B]
    q_data = q_all.gather(
        1, actions.unsqueeze(1)).squeeze(1)    # [B]
    # Push down the soft-max over ALL actions at s; hold up the
    # value of the action actually taken in the data at s.
    conservative = (logsumexp_q - q_data).mean()
    return td_loss + self.alpha * conservative
```

## Constitutional AI for financial safety

Constitutional AI uses a set of written principles to critique, revise, and guide model outputs [Bai et al., 2022]. In financial contexts, these principles can reflect requirements such as risk disclosure, privacy protection, suitability, and avoidance of misleading or prohibited advice. The constitution is not itself a legal control: its principles must be versioned, tested against concrete policies, and paired with deterministic validation and human escalation.

The following illustrative example shows how a model response can be generated, checked against financial safety principles, revised, and then used as part of training.

### Listing 9.13: Constitutional training loop for financial AI responses

```python
class ConstitutionalFinancialAI:
    def __init__(self):
        self.principles = [
            "Never provide advice that could lead to illegal activities",
            "Always disclose risks associated with investments",
            "Do not make guarantees about future returns",
            "Respect client confidentiality and data privacy",
            "Provide advice suitable for client's risk tolerance"
        ]

    def constitutional_training(
        self, model, dataset, num_epochs=1, learning_rate=1e-6
    ):
        """
        Train on critique-and-revision targets.
        """
        optimizer = torch.optim.AdamW(
            model.parameters(), lr=learning_rate)
        total_loss = 0.0
        num_updates = 0

        for _ in range(num_epochs):
            for batch in dataset:
                # Generate an initial response without retaining a graph.
                with torch.no_grad():
                    response = model.generate(batch['prompt'])
                    critique = model.critique(
                        response, self.principles)
                    revised_response, critique = model.revise(
                        response, critique)

                # Train on the revised target.
                optimizer.zero_grad()
                loss = model.compute_loss(
                    batch['prompt'], revised_response)
                loss.backward()
                torch.nn.utils.clip_grad_norm_(
                    model.parameters(), 1.0)
                optimizer.step()

                total_loss += loss.item()
                num_updates += 1

        return total_loss / max(num_updates, 1)
```

## 9.7 Summary

This chapter introduced reinforcement learning (RL) as a framework for aligning LLM behavior with feedback, preferences, and longer-term objectives. It explained how RL differs from supervised learning by optimizing model behavior through reward signals rather than only learning from fixed input-output examples.

The chapter covered the basic RL formulation for language models, including states, actions, policies, rewards, and trajectories. It then discussed reward modeling and human feedback collection, showing how preference data can be used to train models toward more useful, accurate, compliant, and risk-aware outputs.

We also examined modern alignment methods such as PPO, GRPO, and DPO. PPO uses clipped policy updates to improve stability, GRPO compares groups of responses to estimate relative advantages, and DPO optimizes directly from preferred and rejected responses without requiring a separate reward model.

The financial examples showed how RL concepts can be applied to trading research, risk management, hedging, and portfolio optimization. These examples should be understood as conceptual decision-support architectures rather than production-ready systems. In real financial settings, such systems require extensive validation, backtesting, stress testing, risk controls, compliance review, and human oversight.

Finally, the chapter discussed advanced techniques and future directions, including hierarchical RL, multi-agent RL, offline RL, and constitutional AI. These approaches may help make financial LLM systems more adaptive and better governed, but they also introduce challenges around reward design, distribution shift, non-stationarity, interpretability, safety, and regulatory accountability [Daníelsson et al., 2022]. The practical conclusion is that alignment objectives and code-level safeguards must be evaluated together: neither a sophisticated loss function nor a fluent model substitutes for independent validation, deterministic controls, and accountable human oversight.

## 10 Infrastructure and Performance

Deploying large language models (LLMs) in financial services requires more than acquiring accelerator capacity. A production design must balance latency, throughput, model quality, security, compliance, auditability, reliability, recoverability, and cost. These objectives frequently conflict: larger batches improve accelerator utilization but can worsen tail latency; stronger durability guarantees can add processing delay; and moving workloads closer to users can reduce network latency while increasing operational and governance complexity.

Financial workloads also differ materially from one another. A trading-support classifier may require predictable millisecond-scale responses, whereas a regulatory assistant may tolerate slower generation but demand complete lineage, reproducibility, and human review. Client-facing systems add privacy, availability, and conduct-risk constraints. Consequently, there is no single “financial LLM stack.” Infrastructure should instead be selected from an explicit service-level specification covering at least the median and tail-latency percentiles, sustained and burst throughput, availability, recovery-point and recovery-time objectives, task quality, and total cost of ownership.

The infrastructure requirements therefore extend beyond computation alone. Institutions need secure ingestion from market and enterprise sources, deterministic data transformations, controlled retrieval, versioned prompts and models, traceable outputs, and evidence that the deployed configuration continues to satisfy its service-level objectives. The transition from conventional analytical systems to LLM-enabled workflows changes the data, serving, monitoring, and governance layers together rather than merely replacing one model endpoint.

This chapter examines the main infrastructure layers required for production financial LLMs. It covers hardware and deployment choices, data pipelines, vector databases for retrieval-augmented generation (RAG), model optimization, inference serving, orchestration, monitoring, and performance tuning. It concludes with an explicitly illustrative case study for a latency-sensitive trading-support workflow; the scenario is a capacity-planning example rather than a report of an audited production deployment.
