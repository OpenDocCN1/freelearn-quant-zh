# 4.4.4 Matryoshka embeddings

From a system design perspective, being able to work with lower-dimensional versions of the same embedding makes it easier to balance retrieval quality against computational and storage costs, especially in large-scale financial systems. Recent advances enable Matryoshka Representation Learning (MRL) [Kusupati et al., 2022], where a single model produces embeddings of variable dimensionality:

$f(x) = [f_1(x), f_2(x), ..., f_d(x)]$ (4.9)

We can truncate to any \(d' < d\) while maintaining semantic properties. This allows:

+   * High-dimensional embeddings (e.g., 1024-dim) for precision
+   * Low-dimensional embeddings (e.g., 256-dim) for efficiency
+   * Dynamic adjustment based on computational budget

In practice, this can be implemented by generating a full embedding once and selectively truncating it to a lower-dimensional representation, as shown below.

```
import numpy as np

# Full 1024-dimensional embedding
full_embedding = embed_model.encode(text) # shape: (1024,)

# Truncate to 256 dimensions for faster search
truncated = full_embedding[:256] # shape: (256,)

# Both preserve semantic properties with appropriate scaling
```

# 4.5 Vector databases and indexing

Once embeddings have been computed, we need infrastructure that can store them at scale and retrieve the nearest neighbors of a query embedding in milliseconds. This is the role of the vector database. In a financial RAG system, the index typically holds millions of chunk embeddings drawn from filings, transcripts, research, and internal documents, and is queried tens or hundreds of times per user request once re-ranking, multi-query retrieval, and metadata filtering are taken into account. The choice of indexing algorithm, therefore, directly affects latency, memory footprint, recall, and ultimately the quality of the answers the system can produce.
