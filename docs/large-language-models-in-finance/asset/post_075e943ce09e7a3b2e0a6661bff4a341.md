**Why this listing violates the protocol on the next page, deliberately.** The reproducibility protocol stated later in this chapter requires a walk-forward or strictly chronological split. The listing above does not use one. The reason is worth stating plainly rather than hiding, because it is the most common trap in applied financial NLP and this book would be dishonest to step around it.

Financial PhraseBank carries no timestamps [Malo et al., 2014]. There is no document date, no publication time, and no availability stamp on any sentence in it. A chronological split is therefore not merely inconvenient for this dataset; it is _impossible_. The random split is forced by the data, and it is exactly the evaluation defect this book criticises in Chapter 13 and, by name, in the FinEAS discussion of Chapter 1.

Two conclusions follow, and only the second one is optional. First: the number this pipeline produces is a smoke test of the training loop. It is not evidence that the model would have worked, and it must never be reported as though it were. Any accuracy or F1 obtained from an untimestamped benchmark inherits the benchmark's inability to answer the only question a deployed system faces — would this have worked on data the model had not seen _yet_? Second: if the task actually matters, the benchmark must be replaced rather than the split repaired. Use a timestamped corpus, apply the chronological partition in `temporal.py`, and accept the lower headline score that honestly costs.

The listing is retained in this form because a book that showed only clean examples would teach the reader nothing about the situation they will actually meet, which is a dataset that does not support the evaluation they need.

## Listing 15.2: FinEAS-style sentiment scoring wrapper

```python
from transformers import AutoTokenizer, AutoModelForSequenceClassification
import torch

class FineasSentimentScorer:
    """Illustrative FinEAS-style sentiment scoring wrapper."""

    def __init__(self, model_name="LHF/FinEAS"):
        self.tokenizer = AutoTokenizer.from_pretrained(model_name)
        self.model = AutoModelForSequenceClassification.from_pretrained(model_name)
        self.labels = self.model.config.id2label
        self.model.eval()
```

```python
@torch.no_grad()
def score(self, texts, max_length=128):
    inputs = self.tokenizer(
        texts,
        padding=True,
        truncation=True,
        max_length=max_length,
        return_tensors="pt",
    )
    outputs = self.model(**inputs)

    # FinEAS is a REGRESSION head: config.num_labels == 1. Applying
    # softmax over a single logit returns 1.0 for every input, which is
    # the silent failure this method previously shipped. Return the
    # scalar sentiment score and say what it means.
    n_out = self.model.config.num_labels
    if n_out == 1:
        scores = outputs.logits.squeeze(-1)      # shape: (batch,)
        return [
            # NO range assumed. The published FinEAS objective uses a tanh
            # head, but the deployed checkpoint exposes a generic one-label
            # regression head, and its model card documents a different
            # scale. Pin the revision and calibrate against documented
            # examples; do not assert a range the config does not establish.
            {"sentiment_raw": float(v)}          # by the tanh head
            for v in scores
        ]

    # A genuine classifier head (e.g. FinBERT, 3 classes) does take softmax.
    probabilities = torch.softmax(outputs.logits, dim=-1)
    return [
        {self.labels[i]: float(row[i]) for i in range(len(row))}
        for row in probabilities
    ]

if __name__ == "__main__":
    scorer = FineasSentimentScorer()
    examples = [
        "The company raised its full-year guidance after strong earnings.",
        "Credit losses increased sharply as funding conditions tightened.",
    ]
    print(scorer.score(examples))
```

## 15.4.2 Model monitoring and retraining

Fine-tuning is only the first step. Once a financial model is deployed, its performance must be monitored because market conditions, terminology, document formats, user behavior, and data distributions can change over time.

Production models require ongoing monitoring for data drift, concept drift, performance degradation, latency, operational failures, and changes in the business or regulatory environment. Useful monitoring dimensions include:

- **Validation performance:** Track accuracy, macro-F1, class-specific precision and recall, calibration error, and confusion matrices on fresh validation samples.
- **Prediction-confidence drift:** Monitor changes in the distribution of predicted probabilities, entropy, margins, and abstention rates.
- **Input-distribution drift:** Track changes in token distributions, embedding distributions, document length, language mix, entity frequency, and financial terminology.
- **Operational metrics:** Monitor latency, throughput, error rates, timeout rates, failed API calls, and memory or GPU utilization.
- **Segmented performance:** Evaluate performance by document type, market regime, geography, asset class, counterparty type, business line, and data vendor.
- **Human-review metrics:** Track override rates, escalation rates, reviewer disagreement, and recurring error categories.

For FinEAS-style sentiment and sentence-embedding models, additional monitoring is useful:

- **Embedding drift:** Monitor the distance between current sentence embeddings and a reference distribution from the validation period.
- **Sentiment-score stability:** Track the mean, variance, and tail behavior of positive, neutral, and negative scores by source and regime.
- **Entity-level consistency:** Check whether repeated references to the same issuer, sector, or event type receive stable sentiment labels when the surrounding text is comparable.
- **Market-regime breakdown:** Report performance separately in calm, stressed, high-volatility, and crisis periods.

Retraining strategies should be tied to these metrics rather than to calendar time alone:

- **Scheduled retraining:** Monthly or quarterly refreshes when the task is stable and data arrives regularly.
- **Triggered retraining:** Retraining when F1, calibration, latency, drift statistics, embedding drift, or human-review disagreement cross predefined thresholds.
- **Incremental learning:** Controlled updates using newly labeled examples, with validation, approval, rollback control, and audit trails.

In regulated financial environments, retraining should also be documented through versioned datasets, model cards, validation reports, approval records, and post-deployment monitoring logs.
