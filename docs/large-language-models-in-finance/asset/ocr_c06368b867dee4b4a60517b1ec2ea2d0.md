# Embedding generation and management

Embedding quality is affected by model choice, chunk boundaries, document parsing, tables, metadata, and domain adaptation. Financial PDFs require layout-aware extraction; XBRL filings require the reconciliation of structured facts and narrative context; and earnings-call transcripts require speaker and timestamp preservation. Embedding pipelines should therefore be versioned as data products rather than treated as a one-time preprocessing script.

Runtime estimates must state their assumptions. Let N_d be the number of documents, c the average number of chunks per document, G the number of GPUs, and q the sustained number of chunks embedded per second per GPU after tokenization and input overhead. An approximate wall-clock time is

```
T_embed \approx \frac{N_d c}{Gq}. (10.2)
```

For an illustrative corpus of N_d = 10 million documents, c = 4 chunks per document, G = 8 V100 GPUs, and q = 20–30 chunks per second per GPU, Equation (10.2) gives approximately 46–69 hours of embedding inference. Modest orchestration and write overhead produces a planning estimate of roughly 48–72 hours. This estimate assumes 256-token chunks, mixed-precision inference, a batch size near 64 where memory permits, cached tokenization, and balanced input partitions. PDF parsing, optical character recognition, index construction, retries, and quality validation are excluded and can dominate the total pipeline time. Sentence-BERT is one representative encoder family, not a required choice [Reimers and Gurevych, 2019].

Incremental updates introduce additional constraints. New documents must become searchable without corrupting active queries or mixing incompatible embedding versions. Blue-green index deployment, immutable index manifests, and atomic alias changes provide safer release patterns than in-place mutation for high-criticality corpora. Online updates remain useful for news, but they should be reconciled periodically against a reproducible batch-built index.

# Indexing strategies for financial data

HNSW is a graph-based approximate-nearest-neighbor method with strong empirical recall-latency performance [Malkov and Yashunin, 2020]. Parameters such as graph connectivity, construction effort, and search effort should be tuned using the institution's embedding distribution and relevance judgments. Increasing connectivity can improve recall but also increases memory, construction time, and update cost. Metadata filters can reduce the search space, but poorly selective post-filtering can erase the apparent latency advantage of the vector index.
