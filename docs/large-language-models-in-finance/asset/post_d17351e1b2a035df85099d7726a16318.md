
To guide index selection in practice, the following heuristics are commonly used:

- Flat (Exact): \( N < 10^6 \), maximum accuracy required
- IVF-Flat: \( 10^6 < N < 10^7 \), balance of speed and accuracy
- IVF-PQ: \( N > 10^7 \), memory constraints
- HNSW: High-recall applications with sufficient memory

## 4.5.3 Hybrid search

Purely semantic retrieval can miss exact keyword matches, particularly for structured queries, entity names, or regulatory terms. To address this limitation, hybrid search combines dense (semantic) and sparse (term-based) retrieval methods [Robertson and Zaragoza, 2009].

In this setting, dense retrieval captures semantic similarity between queries and documents, while sparse retrieval (e.g., BM25) emphasizes exact term matching and frequency-based relevance. These signals can be combined into a single scoring function as follows:

```
\text{score}_{\text{dense}}(q, d) = \text{sim}(f(q), f(d)) \tag{4.11}
```

```
\text{score}_{\text{BM25}}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t, d) \cdot (k_1 + 1)}{f(t, d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)} \tag{4.12}
```

```
\text{score}(q, d) = \alpha \cdot \text{score}_{\text{dense}}(q, d) + (1 - \alpha) \cdot \text{score}_{\text{BM25}}(q, d) \tag{4.13}
```

where \(\alpha \in [0, 1]\) is a weighting parameter, typically \(\alpha = 0.5\).

A 400-token window knows nothing about Note 7 and cuts it in half, and the two halves are individually useless: the definition without the number cannot answer a compliance question, and the number without the definition cannot either — worse, it looks like it can. The chunk boundary is not a tuning parameter here, it is a semantic decision, and the only safe rule in a filing is to let the document’s own structure decide where the cuts fall. Embeddings and indexes operate on chunks, not on full documents, and the way a document is split into chunks determines what evidence the retriever can ever surface. A 10-K is too long to embed as a single unit, but if we naively cut it every N tokens, we are likely to break tables across boundaries, separate definitions from their usages, and merge unrelated risk factors into a single passage. The chunking stage, therefore, plays a much larger role in retrieval quality than its conceptual simplicity suggests, and it is the place where domain knowledge about financial documents pays the highest dividend.

In what follows, we begin with the trade-offs that any chunking strategy must navigate, then progress from the simplest fixed-size approach to recursive and semantic methods, and finally discuss chunking patterns tailored to specific financial document types.

### 4.6.1 The chunking problem

LLM context windows are finite and expensive to fill. Even when a model exposes a very long window, documents often still need to be split into smaller units so that retrieval remains auditable, permission-aware, and cost-efficient. These chunks should satisfy several competing requirements:

- They must fit within context limits
- They should preserve semantic coherence
- They must contain sufficient context for understanding
- They should optimize retrieval relevance

These requirements introduce trade-offs:

- **Small chunks** (128–256 tokens) improve precision but may lack sufficient context
- **Large chunks** (512–1024 tokens) provide more context but can dilute relevance

### 4.6.2 Fixed-size chunking

The simplest approach is to divide documents into fixed-size windows with a predefined overlap between adjacent chunks

```
Algorithm 7 Fixed-size chunking with overlap
1: Input: text T, chunk size s, overlap o
2: Output: List of chunks {c1, ..., cn}
3: Tokenize T into tokens {t1, ..., tN}
4: for i = 0, s - o, 2(s - o), ... do
5:   c_{i/(s-o)+1} <- {t_{i+1}, ..., t_{min(i+s, N)}}
6: end for
7: return {c1, ..., cn}
```

This method is easy to implement and produces predictable chunk sizes. However, it does not account for the structure of the underlying text and may split meaningful semantic units such as sentences or paragraphs.

To address these limitations, more structure-aware approaches are often used.

### 4.6.3 Recursive character splitting

Recursive splitting improves on fixed-size chunking by respecting natural text boundaries, such as paragraphs, sentences, and whitespace.

```
Algorithm 8 Recursive character splitting
1: Input: text T, chunk size s, separators S = ["\n\n", "\n", ".", " ", ""]
2: if |T| <= s then
3:   return [T]
4: end if
5: for each separator σ ∈ S do
6:   if σ in T then
7:     Split T by σ into {T1, ..., Tm}
8:     Merge adjacent splits to form chunks ≤ s
9:     return chunks
10:   end if
11: end for
```

Instead of applying a fixed window, this approach attempts to split the text using progressively finer separators, preserving coherence wherever possible while still respecting chunk size constraints.

While this method improves semantic consistency, it still relies on surface-level structure. In many cases, deeper semantic relationships between sentences must be considered.

### 4.6.4 Semantic chunking

To better capture meaning, semantic chunking uses embedding models to identify boundaries based on changes in content rather than formatting [Kamradt, 2023].

```
Algorithm 9 Semantic chunking
1: Input: sentences \(\{s_1, \dots, s_n\}\), embedding function \(f\), threshold \(\tau\)
2: Compute embeddings: \(e_i = f(s_i)\) for all \(i\)
3: Compute similarities: \(\text{sim}_i = \text{sim}_{\cos}(e_i, e_{i+1})\) for \(i = 1, \dots, n - 1\)
4: Initialize chunks \(\leftarrow [[s_1]]\)
5: for \(i = 2\) to \(n\) do
6:   if \(\text{sim}_{i-1} < \tau\) then
7:     Start new chunk: chunks.append([\(s_i\)])
8:   else
9:     Add to current chunk: chunks[-1].append(\(s_i\))
10: end if
11: end for
12: return chunks
```

By grouping sentences with high semantic similarity and splitting where similarity drops below a threshold, this approach produces chunks that more closely align with the underlying meaning of the text.

However, this added flexibility comes at the cost of increased computational complexity and reliance on embedding quality.

### 4.6.5 Financial document chunking

Financial documents exhibit well-defined structures, and effective chunking strategies should take advantage of these patterns.

For example, in **10-K and 10-Q reports**, chunking is typically aligned with section boundaries (such as Item 1, Item 1A, or Item 7), ensuring that related disclosures remain grouped together and that tables are preserved alongside their explanatory text.

In **research reports**, chunking is often performed at the level of logical sections such as executive summaries, analysis, and recommendations, with care taken to keep charts and quantitative metrics within their surrounding context.

Similarly, in **regulatory filings and legal documents**, it is important to respect paragraph boundaries, preserve definitions alongside their usage, and maintain cross-references between clauses.

The table below summarizes recommended chunking parameters for common financial document types:

| Document type | Chunk size | Overlap | Notes |
|---|---|---|---|
| 10-K / 10-Q filings | 300–500 | 50–100 | Anchor chunks to section and subsection headings (“Item 1A”, “Risk Factors”, etc.); keep tables with their explanatory text. |
| Earnings call transcripts | 256–384 | 64 | Split by speaker turns; preserve question–answer pairs where possible. |
| Research reports | 256–512 | 64–96 | Use headings and bullet boundaries; keep charts and their captions together. |
| Prospectuses / term sheets | 256–400 | 64 | Respect article and paragraph boundaries; avoid mixing legal definitions from different sections. |
| Legal contracts and ISDAs | 256–400 | 64–96 | Maintain clause integrity; keep definitions close to their usage; avoid splitting cross-referenced sections. |
| Internal emails and chat logs | 128–256 | 32–64 | Split by conversation turns; consider keeping short threads as a single chunk. |

## 4.7 Advanced retrieval techniques

The basic retrieval pipeline introduced earlier—embed the query, search the index, return the top-_k_ chunks—is a strong baseline but is not always sufficient. Real user queries can be ambiguous, terse, or phrased very differently from the relevant passages; the most relevant document is not always the most similar in embedding space; and structured metadata, such as filing dates or document types, is often the single most discriminating signal available. Each of the techniques in this section addresses one of these failure modes.

We organize the discussion around three families. **Query expansion** (HyDE, multi-query retrieval) rewrites or enriches the query before it ever touches the index, with the goal of improving recall when the original phrasing is poorly matched to the corpus. **Re-ranking** (cross-encoders, LLM-based scoring) is applied after an initial retrieval and exists to improve precision: it spends more compute on a small candidate set in order to push the truly relevant passages to the top. **Metadata filtering** and **parent document retrieval** act on the structure of the corpus itself, narrowing the search space using attributes such as company, filing date, or section, and reconciling the tension between focused retrieval and complete context. Throughout, keep the broader pipeline in mind: each technique is a refinement of one specific stage—query processing, ranking, or context assembly—rather than a replacement for the basic pipeline.
