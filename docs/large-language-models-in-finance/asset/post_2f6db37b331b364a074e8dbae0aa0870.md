
where the state space S aggregates the agent’s current observation, context, and memory, and the action space A includes tool invocations, messages to other agents, and final responses. The policy is instantiated via an LLM with parameters θ, possibly augmented by additional non-learned logic.

Crucially, the agent is defined not merely by the underlying LLM, but by the combination of *role*, *tools*, and *interaction patterns*. Two agents may use the same base model but differ in the tools they are allowed to call, the prompts they use, and the workflows they participate in; in such cases, they should be treated as distinct agents, as they implement different policies. In the research workstation, the Research Analyst agent and the Risk and Compliance agent could both be backed by the same foundation model, but the former is allowed to retrieve filings and research notes while the latter is allowed to query policy, restricted-list, and portfolio-limit tools. They are therefore different agents, not merely different prompt invocations.

In practice, this definition maps most directly to what is often called a **single-agent** setup. Single-agent architectures are often the simplest to implement and reason about. A single LLM agent receives user input, accesses tools and data sources, and produces a final response. This pattern is suitable for relatively constrained workflows, such as:

- a regulatory Q&A assistant that retrieves and summarizes relevant sections of regulations and internal policies;
- a portfolio overview assistant that aggregates positions, risk metrics, and performance for a given portfolio; or
- a document classification assistant that assigns categories or tags to documents.

In these settings, the agent’s responsibilities can be encapsulated in a single prompt template and a small set of tools. Memory can be kept minimal, typically limited to the current conversation and retrieved documents, while orchestration logic can be handled by a thin controller layer. Most of the work here lies in getting prompts, tool interfaces, and evaluation right rather than coordinating multiple components. A simplified version of the research workstation could begin this way: a single research assistant retrieves documents, summarizes them, and produces a memo draft. The need for a multi-agent design appears when the workflow must add independent data analysis, risk review, and compliance controls without turning one prompt into an unmanageable bundle of responsibilities.

## 5.1.2 Multi-agent system

A **multi-agent system** (**MAS**) is a collection of such agents that communicate and coordinate, often under the guidance of an orchestrator or higher-level policy, to support a broader workflow (such as research, risk management, or client service) and collectively achieve a set of global objectives.

$$
\mathcal{M} = \{\mathcal{A}_1, \mathcal{A}_2, \dots, \mathcal{A}_N\}
$$ (5.2)

## 5.1.3 The agent contract: stochastic reasoning, deterministic execution

The safest way to design financial agents is to separate two roles that are often blurred. The LLM may propose a plan, summarize evidence, rank alternatives, or draft a response. It should not be the component that decides whether a tool call is authorized, whether an order may be routed, whether client information may be disclosed, or whether a regulatory statement is final. Those decisions belong to deterministic policy components.

Formally, write an agent proposal as

$$a_t \sim \pi_\theta(\cdot \mid s_t),$$

where $s_t$ is the observed state and $a_t$ may be a tool call. The execution layer applies an authorization oracle

$$\Gamma(a_t, s_t, u_t) \in \{0, 1\},$$

where $u_t$ is the authenticated user or service identity. The executed action is then

$$\tilde{a}_t = \begin{cases} a_t, & \Gamma(a_t, s_t, u_t) = 1, \\ \text{escalate/reject,} & \Gamma(a_t, s_t, u_t) = 0. \end{cases}$$

The key design choice is that $\Gamma$ is not a prompt. It is a deterministic software and policy layer that can be tested independently of the LLM.

**Proposition 5.1.1** (Guarded execution invariant). If every external action proposed by an LLM agent is executed only through the guarded map above, and the guard $\Gamma$ is sound with respect to the institution’s authorization policy, then no unauthorized external action can be executed by the agent workflow, regardless of the distribution of LLM proposals.

Proof. Consider any proposed action $a_t$. If it is authorized, the guard permits it. If it is unauthorized, soundness of $\Gamma$ implies $\Gamma(a_t, s_t, u_t) = 0$, so the executed action is not $a_t$ but the reject or escalation action. This argument is pointwise in $a_t$ and therefore does not depend on how the LLM proposal was generated. \(\square\)

Listing 5.1: Guarded tool execution for financial agents

```
from __future__ import annotations
from dataclasses import dataclass
from typing import Any, Callable, Mapping

@dataclass(frozen=True)
class ToolCall:
    name: str
    arguments: Mapping[str, Any]
    requested_by: str
    run_id: str

@dataclass(frozen=True)
class ToolResult:
    status: str
    payload: Mapping[str, Any]
    audit_message: str

def guarded_tool_call(
    call: ToolCall,
    state: Mapping[str, Any],
    is_authorized: Callable[[ToolCall, Mapping[str, Any]], bool],
    execute: Callable[[ToolCall], Mapping[str, Any]],
) -> ToolResult:
    if not is_authorized(call, state):
        return ToolResult(
            status="escalated",
            payload={},
            audit_message=f"unauthorized tool call rejected: {call.name}",
        )
    try:
        result = execute(call)
    except Exception as exc:  # fail closed and preserve the audit trail
        return ToolResult(
            status="failed_closed",
            payload={},
            audit_message=f"tool execution failed: {type(exc).__name__}",
        )
    return ToolResult(status="ok", payload=dict(result),
                      audit_message="executed")
```

This pattern is deliberately simple: the guard is outside the model, the tool execution is inside a try/except boundary, and the return type always records a status. In a bank, asset manager, or broker-dealer, the same logic would be expanded with entitlements, restricted lists, client suitability, trade limits, data-classification rules, maker-checker approvals, and immutable audit logging.

## Final-phase update: Delegated financial agents

A compact refinement from the agentic-finance framework is to separate *proposal* from *institutional action*. The useful production object is not an unconstrained chatbot, but a delegated decision system whose stochastic component proposes and whose external controls decide whether the proposal can become an institutional commitment. A minimal controlled-evidence chain is

$$
H_t \xrightarrow{\rho_t} b_t \xrightarrow{\pi_t} A_t^e \xrightarrow{\Pi_t} A_t \xrightarrow{E_t} S_{t+1} \xrightarrow{M_t} H_{t+1}.
$$

Here $H_t$ is the replayable history, $\rho_t$ forms the controlled belief state, $\pi_t$ is the LLM-centered proposal policy, $A_t^e$ is the proposed action, $\Pi_t$ is the external admissibility projection or shield, $A_t$ is the accepted action, $E_t$ is the permissioned execution adapter, and $M_t$ writes memory and audit evidence. The projection $\Pi_t$ is not a prompt, a system message, or a politely worded instruction. It is a *shield* in the sense of Alshieikh et al. [2018]: a correct-by-construction filter evaluated outside the learned policy, which cannot be argued with by the policy, and which rejects an inadmissible proposal rather than asking the policy to reconsider it. This distinction is the difference between a system that is usually safe and a system whose safety does not depend on the model's mood.

Figure 5.1 draws the contract, and the important feature of that diagram is an absence: no arrow bypasses $\Pi_t$.

The practical rule is simple: the model may draft research, recommend a structured portfolio intent, or flag an exception, but market orders, client recommendations, limit changes, regulatory submissions, and entitlement changes require the appropriate shield, approval, and audit path before execution [Noguer i Alonso et al., 2026, Noguer i Alonso and Pacheco Aznar, 2026].

### A multi-agent system includes:

- a communication protocol, specifying how messages are routed and interpreted;
- an organizational structure (e.g., hierarchical, peer-to-peer, hub-and-spoke);
- shared or distributed memory components; and
- possibly external controllers or orchestrators that manage agent lifecycles and interactions.

For the running research workstation, the set $\mathcal{M}$ contains at least the Research Analyst, Data Analyst, Risk Compliance, and Orchestrator agents. The orchestrator is not just a convenience wrapper: it defines the order of work, decides when intermediate results are sufficient, determines which evidence is passed from one agent to another, and records the final handoff to the human portfolio manager.

In financial contexts, multi-agent systems arise naturally. For example, a research assistant may coordinate agents specialized in company fundamentals, macroeconomic conditions, and alternative data; a risk assistant may orchestrate agents that query limits, stress scenarios, and regulatory requirements. Here, no single agent has the full picture—the outcome depends on how these agents exchange information and build on each other's outputs.
