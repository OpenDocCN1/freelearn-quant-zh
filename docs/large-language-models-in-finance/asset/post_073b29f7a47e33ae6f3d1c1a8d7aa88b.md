
## 4.7.1 Query expansion

The goal of query expansion is to compensate for the fact that user queries are often short, underspecified, or phrased very differently from the relevant documents. Instead of matching the literal query against the index, we transform it into one or more richer surrogate queries that are more likely to retrieve the right passages.

### Hypothetical Document Embeddings (HyDE)

HyDE [Gao et al., 2023a] addresses the query–document mismatch by asking the language model to draft a plausible answer and then using that draft as the actual query. Because the hypothetical answer is written in the same register as the documents in the corpus, its embedding tends to land much closer to the relevant passages than the embedding of the original short user query.

```
Algorithm 10 HyDE retrieval
1: Input: Query q, LLM M, embedding function f, vector DB V
2: Generate hypothetical document: d_h <- M("Write answer to: q")
3: Embed hypothetical document: e_h <- f(d_h)
4: Retrieve: {d_1, ..., d_k} <- V.search(e_h, k)
5: return {d_1, ..., d_k}
```

### Multi-query retrieval

Where HyDE generates one synthetic answer, multi-query retrieval generates several reformulations of the original query and unions their results. The objective here is improved recall: even if the user phrasing fails to match a relevant passage, one of the variants is likely to. The cost is additional retrieval calls and a deduplication step at the end.

```
Algorithm 11 Multi-query retrieval
1: Input: Query q, LLM M, variants n_v
2: Generate variants: {q_1, ..., q_nv} <- M("Generate variants of: q")
3: Initialize results: R <- empty set
4: for each q_i in variants do
5:   R_i <- V.search(f(q_i), k)
6:   R <- R U R_i
7: end for
8: Deduplicate and rank by frequency
9: return top-k from R
```

## 4.7.2 Re-ranking

The retrieval stage is tuned for recall: we want to be reasonably sure that the relevant passage is somewhere in the top-k. Re-ranking is the complementary stage that targets precision. It takes the candidate set returned by the index and applies a more expensive scoring model to it, accepting higher latency in exchange for a much sharper ordering of the truly relevant passages [Nogueira and Cho, 2019].

### Cross-encoder re-ranking

Unlike bi-encoders that separately encode query and document, a cross-encoder computes:

score(q, d) = σ(CrossEncoder([q; d])) (4.14)

where [q; d] denotes concatenation and σ is a scoring function.

```python
from sentence_transformers import CrossEncoder

def rerank_documents(query: str, documents: list,
                   model: str = 'cross-encoder/ms-marco-MiniLM-L-6-v2',
                   top_k: int = 5):
    """Re-rank documents using cross-encoder."""
    model = CrossEncoder(model)

    # Score all query-document pairs
    pairs = [(query, doc) for doc in documents]
    scores = model.predict(pairs)

    # Sort and return top-k
    ranked = sorted(zip(documents, scores),
                    key=lambda x: x[1], reverse=True)
    return ranked[:top_k]
```

## 4.7.3 Metadata filtering

Embeddings capture semantic similarity but say nothing about whether a passage comes from a 10-K filed last quarter or a research note from five years ago. In financial applications, this distinction is often decisive. Metadata filtering complements semantic search with hard, structured constraints—company, document type, section, filing window—that narrow the candidate set before similarity is even computed.

### Metadata-filtered search

```python
import datetime

# Example filters for financial documents
filters = {
    "document_type": {"$in": ["10-K", "10-Q"]},
    "company": "AAPL",
    "filing_date": {

        "$lte": datetime.date(2024, 12, 31)

}

results = vector_db.search(
```

## 4.7.4 Parent document retrieval

Small chunks are easier to rank precisely, but often lack the context the language model needs to answer well. Parent document retrieval resolves this tension by indexing fine-grained chunks for matching, then returning the larger document or section to which each retrieved chunk belongs.

Let \( C = \{c_1, \dots, c_m\} \) be chunks derived from parent documents \( D = \{d_1, \dots, d_n\} \) with mapping \( \pi : C \rightarrow D \). Parent document retrieval:

- 1. Retrieves relevant chunks: \(\{c_{i_1}, \dots, c_{i_k}\} = \text{TopK}(q, C)\)
- 2. Returns parent documents: \(\{\pi(c_{i_1}), \dots, \pi(c_{i_k})\}\)

This strategy provides focused retrieval with comprehensive context.

## 4.7.5 Long-context prompting versus RAG/document-graph architectures

A recurring architectural question is whether a team should build a retrieval layer at all when modern language models can accept very large prompts. Long-context prompting and RAG solve overlapping but different problems. Long-context prompting is attractive when the relevant evidence set is small, static, and already known. RAG is preferable when the corpus is large, frequently updated, access-controlled, or must produce reproducible citations and audit trails. In practice, strong systems often combine both: retrieval narrows the candidate evidence set, and a long-context model synthesizes the selected passages.

| Design criterion | Long-context prompting | RAG / document graph |
| :--- | :--- | :--- |
| Corpus size | Best when the full evidence set fits comfortably in the prompt. | Best when the corpus contains many filings, policies, transcripts, or research notes. |
| Freshness | Requires rebuilding or selecting the prompt whenever evidence changes. | Indexes can be refreshed incrementally and versioned. |
| Permissions | Harder to enforce fine-grained access once text enters the prompt. | Metadata filters can enforce user, desk, region, or document-level permissions before generation. |
| Citation and auditability | Possible, but attribution can degrade in very long prompts. | Retrieval logs, chunk identifiers, and source metadata create an explicit audit trail. |
| Latency and cost | Can be expensive when many irrelevant tokens are included. Useful for synthesis over a known bundle. | Adds retrieval latency but usually reduces generation tokens. Better when evidence must be discovered, deduplicated, ranked, and linked across documents. |
| Cross-document reasoning | Useful for synthesis over a known bundle. | Better when evidence must be discovered, deduplicated, ranked, and linked across documents. |

Table 4.2: Choosing between long-context prompting and RAG/document-graph architectures

For financial tasks, the practical rule is simple: use long-context prompting when the analyst already knows which documents matter and wants synthesis; use RAG when the system must find the documents, enforce permissions, keep evidence fresh, and explain why a passage was used. A document graph becomes valuable when the answer depends on relationships among documents—for example, comparing a current 10-Q with prior 10-K risk factors, linking a covenant definition to its amendment, or reconciling a regulatory rule with an internal policy.
