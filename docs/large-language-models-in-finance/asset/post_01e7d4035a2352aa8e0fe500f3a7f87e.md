
The approval should attach to the exact request that will execute. If the parameters, evidence, model version, policy version, or destination change after review, the approval should expire and the request should return to review. This prevents a reviewer from approving one object while a materially different object is executed.

## 6.4 Typed tools, numerical integrity, and evidence validity

A hardened MCP workflow should not treat tool calls as free-form extensions of the model. Tools need typed contracts, evidence needs point-in-time validity, and material numbers need deterministic verification outside the LLM. This section explains how those controls work together: narrow tools limit what can be requested, deterministic code verifies calculations, and claim-level provenance links generated text back to admissible evidence.

### 6.4.1 Narrow tool contracts

A broad tool such as `run_sql(query)` or `execute_python(code)` is convenient in research, but dangerous in a production decision path. Such tools give the model too much freedom over data access, computation, and side effects. In controlled financial workflows, tools should be narrow, typed, and aligned with specific business operations. Prefer operations such as:

- `get_position_snapshot(portfolio_id, as_of);`
- `calculate_historical_var(snapshot_id, horizon, confidence);`
- `compare_covenant(actuals_id, covenant_id);`
- `create_review_case(subject_id, reason_code, evidence_ids).`

Each tool should declare units, currencies, temporal semantics, null behavior, maximum payload, allowed enumerations, required permissions, and side effects. The output schema should distinguish values, units, sources, timestamps, quality flags, and errors. This makes it possible for the host and policy layer to validate a tool call before execution and to inspect the result after execution.

### 6.4.2 Deterministic recomputation

Material financial numbers should not be validated by asking another model whether they look correct. Suppose, in a simplified example, a model extracts revenue _R_, cost _C_, and weighted average shares _N_ from a filing and states earnings per share. The system should recompute:

\(\widehat{\text{EPS}} = \frac{R - C}{N}\) (6.5)

and compare it with the reported value using a documented tolerance and accounting basis. In a real workflow, the exact formula may depend on whether the system is checking basic EPS, diluted EPS, adjusted EPS, or another institution-specific metric. The important point is that the arithmetic and accounting rule should be implemented in deterministic code, not inferred from model prose.

The same principle applies to duration, exposure, profit and loss (P&L), value-at-risk, capital ratios, fees, and suitability constraints. The correct division of labor is:

- the LLM extracts, classifies, explains, and proposes;
- deterministic code calculates, validates, authorizes, and records;
- an accountable human resolves material ambiguity.

### 6.4.3 Point-in-time evidence

Financial evidence is time-sensitive. A document may describe an earlier period, but only become available later; a revised filing may replace an earlier version; and a position snapshot may exist before it has been approved for use. For every evidence item \(d_j\), record at least:

```
\(d_j = (\text{id}_j, \text{source}_j, \tau_j^{\text{event}}, a_j, \text{version}_j, \text{hash}_j),\) (6.6)
```

where \(\tau_j^{\text{event}}\) is the event time and \(a_j\) is the availability time. For a principal \(u\) and purpose \(p\), the admissible evidence set at decision time \(t\) is:

```
\(\mathcal{D}_{\le t} = \{d_j : a_j \le t \land \text{permitted}(d_j, u, p)\}.\) (6.7)
```

Event time and availability time must not be confused. A financial statement may describe a quarter ending in December but become available only in February; a restatement may retain the original reporting period while being unavailable in the original backtest; and an internal position file may be generated at 16:00 but approved only later. Point-in-time evidence checks prevent the model from using information that was not actually available to the workflow at the decision time.

### 6.4.4 Claim-level provenance

A final answer should be decomposed into material claims \(A_1, \dots, A_m\). Each claim is linked to an evidence bundle \(E_i\) and, where applicable, a deterministic calculation identifier \(c_i\). A useful acceptance condition is:

```
\(\text{Accept}(A_i) = \text{Supported}(A_i, E_i) \land \text{Admissible}(E_i, t) \land \text{Reconciled}(A_i, c_i).\) (6.8)
```

Here, \(\text{Supported}(A_i, E_i)\) checks whether the evidence supports the claim, \(\text{Admissible}(E_i, t)\) checks whether the evidence was permitted and available at the decision time, and \(\text{Reconciled}(A_i, c_i)\) checks any material numerical claim against a deterministic calculation.

Unsupported claims are removed, qualified, or escalated. A citation that merely points to a long document is not enough when the statement is financially material; the system should identify the specific evidence and calculation that support the claim.

## 6.5 Execution semantics: idempotency, retries, and audit

Distributed systems routinely retry failed or timed-out requests. In financial systems, however, a retry must not duplicate the business effect. A repeated network message should not create two trades, two payments, two reports, or two review cases. The execution layer must therefore separate transport-level retry behavior from business-level execution.

For this reason, the execution layer should distinguish:

- a transport request identifier, which may change across network attempts;
- a stable business idempotency key, which identifies the intended business action;
- an execution identifier, which is created only when the underlying system accepts the action.

Before execution, the adapter checks whether the idempotency key has already been completed, rejected, cancelled, or left in an uncertain state. Completed and rejected actions should not be executed again. Uncertain outcomes require reconciliation against the execution ledger or target system, not blind retry.

### 6.5.1 Canonical request hashing

Approvals should attach to the exact request that will execute, not to a loose description of the request. Let canon(r) serialize the normalized request with stable field ordering, units, decimal precision, evidence identifiers, and version identifiers. The approval hash is:

h_r = H(canon(r)), (6.9)

where H is the approved hash function. The execution adapter verifies the same hash immediately before action. Any change to parameters, evidence, policy version, destination, amount, or execution target invalidates the approval and sends the request back for review.

### 6.5.2 The audit record

A material MCP-assisted workflow should produce an audit record that allows the institution to reconstruct what happened, which evidence was used, which controls were applied, who approved the action, and what was ultimately executed. A minimum audit record contains:

| Field group | Required content |
| --- | --- |
| Identity | User/service identity, workload identity, legal entity, desk, device/session, authentication strength |
| Protocol | MCP revision, transport, host/client/server versions, capability negotiation, schema hashes |
| Model | Base model, adapter, prompt hash, inference settings, safety-policy version |
| Evidence | Resource identifiers, source, availability time, revision, content hash, permissions |
| Decision | Proposed tool, normalized parameters, gate result, policy clauses, limit checks, reason codes |
| Calculation | Deterministic engine version, inputs, units, outputs, reconciliation status |
| Approval | Reviewer identity, timestamp, request hash, comments, expiry, delegation basis |
| Execution | Idempotency key, execution identifier, target system response, retries, final state |
| Output | Material claims, supporting evidence identifiers, final artifact hash, distribution list |

Table 6.4: Minimum audit fields for a material MCP-assisted workflow

Logs must not become a new source of leakage. Secrets and unnecessary personal data should be excluded, redacted, or tokenized. Retention should follow institutional policy, and access to audit data should itself be monitored. The goal is to preserve enough evidence for accountability and reconstruction without creating an uncontrolled repository of sensitive information.

## 6.6 Performance, reliability, and capacity planning

Performance planning for MCP-assisted financial workflows should be tied to measurable software stages rather than broad claims about speed. A service-level objective (SLO) should define the expected latency, availability, timeout, retry, and recovery behavior for a specific workflow. For one request, the total latency can be decomposed as:

```
T_total = T_auth + T_policy + T_serialize + T_network + T_model      (6.10)
      + T_tool + T_validate + T_approval + T_audit.                      (6.11)
```

Each term represents a measurable stage: authentication, policy evaluation, serialization, network transfer, model inference, tool execution, validation, human or automated approval, and audit logging. These terms should be measured as distributions, not only as averages. A production SLO reports percentiles such as p50, p95, and p99, along with timeout, cancellation, queue depth, error rate, and retry rate. The approval term is zero only for actions that are explicitly within an automated mandate.
