Stop conditions: Reject or escalate if data are stale, a security is restricted, a proposed position breaches a limit, liquidity assumptions are missing, claims lack evidence, or the model proposes an action outside the user's mandate.

# ## 7.4.5 A common release scorecard

The four cases differ in business objective but share a common release standard. Table 7.4.5 prevents a team from declaring success based on one semantic metric.

| Dimension | Representative measures | Release question |
| :--- | :--- | :--- |
| Task quality | Precision/recall, reviewer score, omission rate, correction rate | Does the system produce useful work on a deployment-like sample? |
| Evidence | Retrieval recall, claim support, source authority, availability-time validity | Can every material statement be traced to admissible evidence? |
| Numbers | Reconciliation rate, unit/currency checks, identity violations | Are all material quantities computed or verified deterministically? |
| Policy | Unauthorized-action rate, refusal accuracy, escalation precision/recall | Does the system fail closed and route judgment correctly? |
| Robustness | Regime, document, language, adversarial, and missing-data tests | Does performance survive realistic variation and attack? |
| Human factors | Active time, correction burden, automation bias, override behavior | Does the interface improve judgment rather than merely accelerate acceptance? |
| Operations | p50/p95 latency, cost, availability, retry and incident rate | Can the workflow meet an explicit service objective safely? |
| Change control | Regression results across model, prompt, data, tool, and policy versions | Is each material change revalidated before release? |

# ## 7.5 Cross-cutting blueprint: from data to decisions

The previous sections described individual applications, but financial institutions rarely build each use case as a completely separate system. In practice, they usually deploy shared platforms that support multiple workflows with common data, models, retrieval systems, tools, and governance services [Arnet et al., 2017, Feuerriegel et al., 2024]. The goal is not to create one monolithic application, but to build reusable layers that can support different business functions while preserving access control, auditability, and model-risk oversight.

A realistic data-to-decision blueprint combines the following layers:

+   - **Data layer:** Market data, fundamental data, documents, transactions, logs, and reference data, all with strong governance, quality controls, and lineage [Baesens et al., 2016].

+   - **Model layer:** Pretrained LLMs, fine-tuned financial LLMs, smaller task-specific models, time-series models, and graph models [Wu et al., 2023b, Liu et al., 2024c].
