
as a technical one: the workflow should make responsibility visible rather than allowing autonomy to blur accountability.

LLM agents and multi-agent systems represent a powerful new paradigm for building intelligent systems in finance. By combining the generalization capabilities of large language models with structured tools, data sources, and human oversight, financial institutions can automate complex workflows while maintaining control and accountability.

## 5.7 Formal safety contract for agent workflows

The safest way to build financial agents is to treat the LLM as a proposal generator, not as an authority. The authority belongs to typed tools, policy gates, audit logs, and human reviewers. This distinction is the difference between an impressive demo and a deployable workflow.

**Definition 5.7.1** (Governed tool call). A governed tool call is a tuple

$C = (u,r,T,p,s,v),$

where $u$ is the user identity, $r$ is the user's role, $T$ is the requested tool, $p$ is the proposed parameter object, $s$ is the workflow state, and $v$ is the relevant version vector containing model, prompt, tool-schema, corpus, and policy versions. A policy gate is a function

$\text{Gate}(C) \in \{\text{allow}, \text{reject}, \text{escalate}\}.$

A workflow is fail-closed if every missing permission, invalid schema, stale artifact, or failed verification maps to reject or escalate, never to allow.

**Proposition 5.7.1** (No unauthorized execution under a fail-closed gate). Assume every external action requested by an agent is represented as a governed tool call $C$, every tool adapter executes only after receiving allow from Gate, and the gate is sound in the sense that unauthorized calls never map to allow. Then no unauthorized external action is executed, regardless of the free-form text generated by the LLM.

Proof. Every external action must pass through a tool adapter. By assumption, the adapter has only one execution path: it runs the tool after the gate returns allow. If a call is unauthorized, gate soundness implies that the returned decision is either reject or escalate. In both cases the adapter does not execute the external action. Since the LLM has no direct access path around the adapter, generated text alone cannot execute an unauthorized action.

The proposition is intentionally modest. It does not say the agent will always make good recommendations, nor that authorized actions are economically wise. It says something narrower and operationally essential: if all action authority is concentrated in a sound fail-closed gate, a language model cannot bypass permissions by persuasion, prompt injection, or malformed text.

```
from dataclasses import dataclass
from typing import Any, Mapping

@dataclass(frozen=True)
class ToolCall:
    user: str
    role: str
    tool: str
    params: Mapping[str, Any]
    workflow_id: str
    version: Mapping[str, str]

@dataclass(frozen=True)
class GateDecision:
    status: str     # "allow", "reject", or "escalate"
    reason: str

class PolicyGate:
    def __init__(self, permissions: Mapping[str, set[str]]):
        self.permissions = permissions

    def decide(self, call: ToolCall) -> GateDecision:
        allowed_tools = self.permissions.get(call.role, set())
        if call.tool not in allowed_tools:
            return GateDecision("reject", "tool not permitted for role")
        if not call.version.get("policy"):
            return GateDecision("reject", "missing policy version")
        if call.tool == "submit_order":
            return GateDecision("escalate", "orders require human approval")
        if any(value is None for value in call.params.values()):
            return GateDecision("reject", "invalid null parameter")
        return GateDecision("allow", "policy checks passed")

def execute_tool(call: ToolCall, gate: PolicyGate, registry: Mapping[str, Any]):
    decision = gate.decide(call)
    audit_event = {"call": call, "decision": decision}
    if decision.status != "allow":
        return {"executed": False, "audit": audit_event}
    result = registry[call.tool](**call.params)
    return {"executed": True, "result": result, "audit": audit_event}
```

This reference pattern should be used even when the surrounding agent framework is more sophisticated. The framework may handle planning, memory, tool discovery, and dialogue; the gate handles authority. Separating those roles keeps the agent inspectable and prevents prompt changes from silently rewriting the institution's control policy.

## Model Context Protocol and Hardened Tool Invocation in Financial Systems

Large language models become operationally useful when they can retrieve evidence, call calculators, query approved databases, and pass structured work to downstream systems. Model Context Protocol (MCP) standardizes part of this integration problem. It defines a host-client-server architecture, JSON-RPC message exchange, capability negotiation, and primitives such as resources, prompts, and tools [Model Context Protocol, 2025c,a]. However, MCP does not by itself make a financial workflow safe, suitable, authorized, numerically correct, or auditable.

That boundary is the central idea of this chapter. MCP is an interoperability protocol, not a complete governance framework. A regulated institution must therefore place a separate financial control envelope around MCP-based tool use. This envelope includes identity, least-privilege authorization, typed tool contracts, point-in-time evidence checks, deterministic numerical recomputation, approval gates, idempotent execution, and tamper-evident audit records. The resulting design follows the book's recurring rule:

stochastic reasoning + deterministic execution and control.

This chapter first explains what the published protocol standardizes and what it leaves to implementers. It then develops a hardened reference architecture, a compact mathematical contract for authorization and evidence validity, a finance-specific threat model, a latency and reliability budget, and an end-to-end risk-reporting example. The formal statements are presented as *engineering invariants and conditional obligations*, not as claims that an LLM or an MCP deployment has been proved secure in the abstract.

## 6.1 What MCP standardizes and what it does not

The stable MCP specification describes a client–host–server architecture built on JSON-RPC. A host application coordinates one or more clients, each client maintains a stateful connection to a server, and servers expose focused capabilities such as resources, prompts, and tools [Model Context Protocol, 2025a]. The protocol is intentionally composable. For example, a financial research workstation might connect separately to a filing server, a market-data server, a risk-calculation server, and an internal-policy server rather than exposing every capability through one monolithic service.

### 6.1.1 Core protocol objects

The main protocol objects are useful only when they are mapped to concrete financial roles and controls. Table 6.1 separates the protocol object from its financial interpretation.

| Object | Protocol role | Financial interpretation |
|---|---|---|
| Host | Coordinates clients, permissions, context aggregation, user interaction, and model integration. | A governed application such as a research workstation, risk console, compliance assistant, or operations portal. |
| Client | Maintains an isolated stateful session with one server and negotiates capabilities. | A connector controlled by the host, with a specific identity, scope, version, and lifecycle. |
| Server | Exposes focused capabilities. | A boundary around a filing store, pricing service, portfolio database, policy engine, or approved calculation service. |
| Resource | Data exposed through a URI and associated metadata. | A filing, policy, position snapshot, term sheet, model card, or audit artifact. |
| Prompt | A reusable interaction template. | An institution-approved workflow template, not an access-control mechanism. |
| Tool | A named operation with an input schema and structured result. | A read query, calculation, ticket creation, report generation, or tightly controlled transaction request. |

Table 6.1: MCP objects and their financial interpretation

MCP tool definitions can include input and output schemas, but schema validity is not the same as business validity. A request may be valid JSON and still violate a trading limit, use stale market data, cross a restricted-list boundary, or calculate a metric from an unauthorized portfolio. The host must therefore interpret protocol messages within a richer policy context.

### 6.1.2 Messages and transports

MCP uses JSON-RPC 2.0 messages. The stable specification supports standard input/output for local subprocesses and Streamable HTTP for remote or multi-client services [Model Context Protocol, 2025e]. The choice of transport is operational rather than cosmetic:

- stdio is useful for a local, single-user tool launched as a subprocess. Credentials should come from the environment or an operating-system secret store, not from the model prompt.
