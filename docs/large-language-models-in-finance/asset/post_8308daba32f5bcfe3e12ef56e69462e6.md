## Cloud infrastructure advantages and limits

Cloud platforms provide rapid access to new accelerators without an initial hardware purchase, and they allow capacity to expand during training runs, stress tests, or temporary demand spikes. Managed identity, observability, model registries, and deployment services can shorten implementation time. Multi-region services can also simplify geographically distributed recovery designs.

Elasticity does not automatically imply lower cost. Savings depend on workload variability, minimum capacity, reserved or committed-use discounts, idle-time policy, storage and egress charges, and the engineering required to scale safely. A steady, highly utilized inference service can be cheaper on owned hardware, whereas an intermittent training workload can favor cloud capacity. Therefore, unsupported percentage reductions should be avoided; institutions should publish the utilization assumptions and unit economics behind any cloud-cost claim.

Cloud deployment also creates control dependencies. Institutions need contractually enforceable audit and incident-notification rights, visibility into subprocessors and data locations, customer-controlled encryption where required, tested exit procedures, and a plan for regional or provider failure. The ability to deploy a model in several regions does not by itself establish operational resilience if those regions share a control plane or if the application cannot fail over without inconsistent state.

## On-premises infrastructure considerations

On-premises infrastructure can provide stronger physical control, predictable internal networking, direct integration with hardware security modules, and the ability to isolate highly sensitive workloads. It can be attractive for stable, continuously utilized inference, for workloads close to market-data or execution systems, or when an institution already owns suitable accelerator capacity.

On-premises deployment does not guarantee low latency. End-to-end latency still includes queueing, tokenization, retrieval, model execution, post-processing, and network hops. Sub-millisecond performance may be feasible for narrowly scoped components such as routing, filtering, or in-memory approximate-nearest-neighbor search, but it is generally not a credible end-to-end target for generative LLM inference. Tail-latency objectives should be measured at the application boundary under burst load and failover conditions.

The principal disadvantages are capital commitment, power and cooling constraints, hardware refresh risk, spare-capacity requirements, and the need to operate the full platform. Capacity planning must include maintenance windows and failure domains: an eight-GPU server that meets average demand may not satisfy the service objective after a GPU, node, or network path fails.

## Hybrid and edge architecture strategies

Hybrid architectures are often appropriate because different stages of a financial workflow have different constraints [Daniëlsson et al., 2022]. Public or private cloud can support experimentation, large but temporary training runs, and non-sensitive batch jobs. Customer-controlled infrastructure can host sensitive inference, proprietary retrieval stores, and audit records. Edge nodes can execute narrowly scoped filtering or classification near users or data sources, while a centralized service handles complex generation and policy enforcement.

The practical design rule is to keep the latency-critical path as short and deterministic as possible. A small classifier or rules engine may execute at the edge, but a generative model whose response is not required for immediate action should run asynchronously. Sensitive data should not cross a wide-area network merely to save local compute. Conversely, duplicating the complete LLM stack at every edge site increases patching, monitoring, model-consistency, and incident-response burdens. A sound hybrid design therefore specifies which data can leave each zone, which decisions can be made locally, how models are updated, how confidence-based escalation works, and what fallback behavior applies when the cloud or central cluster is unavailable.

## 10.2 Data architecture and pipeline design

Financial LLM systems depend on pipelines that can ingest, clean, enrich, retrieve, and update information reliably. Production pipeline architecture must support both real-time streams, such as market events and news, and slower-moving sources, such as filings, research reports, policies, and internal documents. Data lineage should connect each generated output to source records, parsing versions, feature transformations, embedding versions, and retrieval results.

### 10.2.1 Real-time data ingestion systems

Market-data volumes vary substantially by asset class, venue coverage, normalization policy, and whether quote-book updates are retained. Rather than presenting one institution-specific figure as a universal benchmark, capacity planning should state an explicit workload profile. For example, an illustrative design point of 10 billion events per day corresponds to an average of approximately 116,000 events per second. A five-million-event-per-second burst would therefore represent a burst-to-average ratio of roughly 43. Such a profile is useful for stress testing, but it should not be described as typical without evidence from the institution’s subscribed feeds and retention policy.

The ingestion layer should distinguish raw transport rate from events that reach an LLM. Most market events do not require language-model inference. Filtering, deduplication, symbol normalization, event aggregation, and threshold logic should reduce the stream before expensive model calls. This separation prevents a burst in low-value events from saturating the model-serving tier.

### Message queue architectures

Apache Kafka is widely used as a durable event backbone. Its partitioned log supports replay, independent consumers, and horizontal scaling. Kafka can provide idempotent and transactional processing semantics, but “exactly once” is not an automatic end-to-end property. It depends on producer idempotence, acknowledgements, transaction configuration, consumer isolation, offset management, and the behavior of external sinks [Apache Software Foundation, 2026b].

In a financial LLM pipeline, Kafka can buffer bursts between data producers and downstream enrichment or inference. The persistent log supports replay for model validation and backtesting, provided that schemas, reference data, and event-time semantics are also versioned. Topic separation should follow data criticality and retention needs. Low-latency market events may use different replication and retention settings from regulatory filings or model-audit records; however, reducing replication for speed should be justified against the recovery objective rather than treated as a default.

Schema management is essential. Apache Avro and Protocol Buffers can support compatible schema evolution. Governance must still define which changes are allowed, how invalid messages are quarantined, and how consumers are upgraded. A technically valid schema change can still alter model behavior if a field’s economic meaning changes.

### Stream processing frameworks

Apache Flink and related stream processors provide stateful transformations, event-time windows, joins, enrichment, and checkpoint-based recovery [Apache Software Foundation, 2024]. Flink can preserve exactly-once state semantics, but end-to-end exactly-once delivery additionally requires sources and sinks that participate correctly in checkpointing or implement transactional or idempotent writes [Apache Software Foundation, 2026a]. For ultra-low-latency applications, an institution may deliberately choose at-least-once processing and perform downstream deduplication; the trade-off should be explicit and tested.

A typical financial enrichment job may normalize exchange formats, apply corporate actions, attach reference data, tag entities, calculate event-time features, and route only materially relevant events to a model. Event-time watermarks and late-data policies need particular attention because an apparently correct result can still be economically wrong if it incorporates information that was not available at the decision timestamp.
