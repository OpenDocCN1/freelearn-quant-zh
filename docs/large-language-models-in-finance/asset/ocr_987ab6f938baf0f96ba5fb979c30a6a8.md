# ## 6.1.1 Core protocol objects

The main protocol objects are useful only when they are mapped to concrete financial roles and controls. Table 6.1 separates the protocol object from its financial interpretation.

| Object | Protocol role | Financial interpretation |
|---|---|---|
| Host | Coordinates clients, permissions, context aggregation, user interaction, and model integration. | A governed application such as a research workstation, risk console, compliance assistant, or operations portal. |
| Client | Maintains an isolated stateful session with one server and negotiates capabilities. | A connector controlled by the host, with a specific identity, scope, version, and lifecycle. |
| Server | Exposes focused capabilities. | A boundary around a filing store, pricing service, portfolio database, policy engine, or approved calculation service. |
| Resource | Data exposed through a URI and associated metadata. | A filing, policy, position snapshot, term sheet, model card, or audit artifact. |
| Prompt | A reusable interaction template. | An institution-approved workflow template, not an access-control mechanism. |
| Tool | A named operation with an input schema and structured result. | A read query, calculation, ticket creation, report generation, or tightly controlled transaction request. |

Table 6.1: MCP objects and their financial interpretation

MCP tool definitions can include input and output schemas, but schema validity is not the same as business validity. A request may be valid JSON and still violate a trading limit, use stale market data, cross a restricted-list boundary, or calculate a metric from an unauthorized portfolio. The host must therefore interpret protocol messages within a richer policy context.

# ## 6.1.2 Messages and transports

MCP uses JSON-RPC 2.0 messages. The stable specification supports standard input/output for local subprocesses and Streamable HTTP for remote or multi-client services [Model Context Protocol, 2025e]. The choice of transport is operational rather than cosmetic:

+   • stdio is useful for a local, single-user tool launched as a subprocess. Credentials should come from the environment or an operating-system secret store, not from the model prompt.
