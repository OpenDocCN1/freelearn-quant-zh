## Embedding generation and management

Embedding quality is affected by model choice, chunk boundaries, document parsing, tables, metadata, and domain adaptation. Financial PDFs require layout-aware extraction; XBRL filings require the reconciliation of structured facts and narrative context; and earnings-call transcripts require speaker and timestamp preservation. Embedding pipelines should therefore be versioned as data products rather than treated as a one-time preprocessing script.

Runtime estimates must state their assumptions. Let N_d be the number of documents, c the average number of chunks per document, G the number of GPUs, and q the sustained number of chunks embedded per second per GPU after tokenization and input overhead. An approximate wall-clock time is

```
T_embed \approx \frac{N_d c}{Gq}. (10.2)
```

For an illustrative corpus of N_d = 10 million documents, c = 4 chunks per document, G = 8 V100 GPUs, and q = 20–30 chunks per second per GPU, Equation (10.2) gives approximately 46–69 hours of embedding inference. Modest orchestration and write overhead produces a planning estimate of roughly 48–72 hours. This estimate assumes 256-token chunks, mixed-precision inference, a batch size near 64 where memory permits, cached tokenization, and balanced input partitions. PDF parsing, optical character recognition, index construction, retries, and quality validation are excluded and can dominate the total pipeline time. Sentence-BERT is one representative encoder family, not a required choice [Reimers and Gurevych, 2019].

Incremental updates introduce additional constraints. New documents must become searchable without corrupting active queries or mixing incompatible embedding versions. Blue-green index deployment, immutable index manifests, and atomic alias changes provide safer release patterns than in-place mutation for high-criticality corpora. Online updates remain useful for news, but they should be reconciled periodically against a reproducible batch-built index.

## Indexing strategies for financial data

HNSW is a graph-based approximate-nearest-neighbor method with strong empirical recall-latency performance [Malkov and Yashunin, 2020]. Parameters such as graph connectivity, construction effort, and search effort should be tuned using the institution's embedding distribution and relevance judgments. Increasing connectivity can improve recall but also increases memory, construction time, and update cost. Metadata filters can reduce the search space, but poorly selective post-filtering can erase the apparent latency advantage of the vector index.

Inverted-file indices provide a different recall-speed-memory trade-off through the number of probed cells. Product quantization can reduce raw vector storage substantially: a 768-dimensional FP32 vector occupies about 3 KB, whereas a 64–128-byte code is much smaller before metadata and index overhead. Compression quality must be assessed on financial retrieval tasks because small numerical differences can change which evidence is presented to a model.

Claims of sub-millisecond RAG latency require qualification. An isolated, in-memory approximate-nearest-neighbor search can complete below one millisecond under favorable hardware, index size, and concurrency. Production RAG latency also includes request routing, entitlement checks, metadata filtering, network transport, reranking, document fetch, prompt assembly, and queueing. Institutions should therefore report end-to-end p50, p95, p99, and p99.9 latency under a declared concurrency and recall target rather than quoting only the fastest index kernel.

## 10.3 Deployment strategies for production systems

Deploying LLM systems in production requires more than selecting a capable base model. Financial institutions must balance accuracy, latency, cost, reliability, infrastructure constraints, and operational risk. This section discusses optimization techniques, inference frameworks, and deployment patterns that help move financial LLM systems from experimentation to controlled production use.

### 10.3.1 Model optimization techniques

Production optimization should be treated as a constrained validation problem rather than a race to minimize model size. The deployed model must satisfy task quality, calibration, robustness, and numerical-accuracy thresholds across relevant market regimes while meeting latency and cost objectives [Micikevicius et al., 2018].

#### Quantization strategies

Quantization stores weights and, in some designs, activations at lower precision. Moving from FP32 to INT8 reduces the raw weight payload by approximately fourfold, but end-to-end speedup depends on kernel support, memory bandwidth, batch size, and whether non-quantized operations dominate. Calibration data should cover numerical expressions, entity-rich documents, different document types, and stressed market conditions. A configuration that preserves aggregate accuracy can still damage calibration or rare-event recall.

Static quantization offers the greatest opportunity for optimized kernels when representative calibration data are available. Dynamic quantization can be easier to deploy for variable inputs but adds runtime work. Weight-only quantization is often useful for generative models because it reduces model memory while retaining higher-precision activations. Every choice should be evaluated with both task metrics and application-level latency percentiles.

#### Model pruning and distillation

Structured pruning removes complete components such as neurons or attention heads and is more likely than unstructured sparsity to produce hardware-visible speedups. Prior studies show that many attention heads can sometimes be removed with limited degradation, but the removable fraction is highly task-, layer-, and model-dependent [Michel et al., 2019, Voita et al., 2019]. It is therefore not defensible to assume that a fixed percentage of heads can be removed from a financial model. Pruning should be followed by fine-tuning and evaluation on in-domain accuracy, calibration, temporal stability, and rare-event slices.

Knowledge distillation trains a smaller student to imitate a larger teacher. In financial applications, the objective should preserve not only labels but also probability calibration, abstention behavior, and, where appropriate, intermediate representations. Multi-teacher distillation can combine specialized models, but conflicting teachers require an explicit resolution policy. A smaller student is operationally valuable only if its lower latency and cost are not offset by additional review or exception handling.

### 10.3.2 Inference optimization frameworks

After model-level optimization, the next concern is how the model is served under real production traffic. Inference frameworks affect throughput, latency, batching behavior, memory use, hardware utilization, and operational complexity.

#### TensorRT-LLM and vLLM

TensorRT-LLM provides optimized execution on NVIDIA GPUs with quantization, paged caching of keys and values, in-flight batching, multi-GPU execution, and other serving features [NVIDIA, 2026d]. It is a strong choice when an institution has standardized on NVIDIA hardware and is willing to build and validate hardware-specific engines. The trade-offs are tighter vendor coupling, engine-build complexity, and the need to retest after model, driver, CUDA, TensorRT, or firmware changes.

vLLM uses PagedAttention and request scheduling to reduce key-value-cache fragmentation. Its original evaluation reported two- to fourfold throughput gains over selected contemporary systems at comparable latency, with larger gains for longer sequences and more complex decoding workflows [Kwon et al., 2023]. Those results should not be transferred directly to a financial deployment: the institution should reproduce them using its model, prompts, output lengths, concurrency, and latency budget.

Serving benchmarks should publish enough information to be reproducible: accelerator model and count, power mode, interconnect, model and precision, context and output-length distributions, concurrency, batching policy, warm-up, cache state, software versions, and whether latency is time-to-first-token, inter-token latency, or end-to-end response time. Average latency alone is insufficient because queueing under burst load typically appears first in the upper percentiles.

#### Containerization and orchestration

Kubernetes can provide repeatable deployment, service discovery, rolling updates, and automated restart. It does not automatically solve GPU scheduling, stateful model loading, or low-latency networking. Production designs should specify node pools, GPU topology awareness, model-cache strategy, readiness criteria, disruption budgets, and how long a replacement replica takes to load weights and become healthy.
