## 8 Financial Documents and Advisory

This chapter continues the discussion of financial LLM applications by focusing on two text-intensive domains: financial-document intelligence and client-facing advisory workflows. The first part examines contract-term extraction, regulatory-document review, and reasoning across multiple filings. The second part considers advisory support, customer-service automation, and personalized financial planning.

Across both domains, the central design principle is the same: an LLM should support a bounded workflow rather than replace the systems and professionals that carry legal, regulatory, fiduciary, or transactional authority. Reliable deployment therefore requires source-grounded outputs, deterministic controls, privacy-preserving data access, calibrated alert thresholds, human approval, and complete audit trails [National Institute of Standards and Technology, 2023].

Document analysis comes first because many downstream activities depend on extracting, validating, and organizing information from long and internally cross-referenced materials. Once those information objects have been created, they can support compliance review, client explanations, service workflows, and planning conversations.

The following topics are covered in this chapter:

- financial-contract analysis and evidence-grounded term extraction;
- SEC- and FINRA-related compliance review;
- long-context, retrieval-augmented, and document-graph architectures;
- investment-advisory support under suitability and disclosure controls;
- secure customer-service automation and human escalation; and
- personalized planning and calibrated financial-risk indicators.

**How to read the listings.** The chapter distinguishes between two kinds of code. Listings explicitly identified as *architecture sketches* specify interfaces and control boundaries; names such as *extractor* or *policy_engine* denote institution-specific components and are not assumed to be off-the-shelf Python classes. Listings identified as *runnable cores* contain concrete scoring or orchestration logic that can be executed after installing the named libraries and connecting approved enterprise services. This distinction avoids presenting code scaffolding as a complete production system.

### 8.1 Document analysis and processing

Financial institutions process loan agreements, derivatives documentation, prospectuses, regulatory filings, policies, and client communications whose meaning depends on specialized terminology, numerical relationships, and cross-references. LLMs can help locate and normalize relevant information, but their outputs must remain tied to exact source passages and must be checked against deterministic rules whenever the task involves dates, amounts, identities, or arithmetic.

The pipeline is unremarkable; the band running through it is not. Every artifact carries the tuple (doc, page, span, $\tau$), and a sentence that reaches the memo without one is not a stylistic lapse but a broken audit trail. The chain almost always breaks in the same place. Table extraction is the step where a structured object is flattened into prose, and a number that has lost its row and column header has lost the only thing that made it checkable — it is now a plausible figure of unknown provenance sitting in a document that a committee will act on.

#### 8.1.1 Extracting key financial terms from contracts

Loan agreements, derivatives contracts, and investment prospectuses contain clauses that define the rights and obligations of the parties. An ISDA Master Agreement is the standardized bilateral framework commonly used to govern over-the-counter derivatives transactions between two counterparties. Manually extracting information from such documents is time-consuming, because the operative meaning of a term may depend on schedules, annexes, definitions, and cross-referenced clauses spread across more than one hundred pages [Wang et al., 2023].

#### Domain-specific entities and relations

A useful extraction schema should cover not only named entities but also their relations and conditions. Typical targets include:

- **Covenants**: obligations or restrictions, together with their measurement dates, thresholds, cure periods, and exceptions;
- **Events of default**: triggering conditions, grace periods, cross-default provisions, and available remedies;
- **Dates**: effective, maturity, payment, call, put, notice, and regulatory milestone dates;
- **Financial quantities**: principal, rates, spreads, fees, collateral values, and concentration limits;
- **Parties and roles**: borrower, guarantor, calculation agent, collateral agent, trustee, and participating lender; and
- **Legal context**: governing law, jurisdiction, dispute forum, amendment rules, and precedence among documents.

The extraction object should carry provenance. A normalized value such as a maturity date is incomplete unless it is accompanied by the source document, page or section, exact evidence span, model version, extraction time, and validation status. The compact architecture sketch in Listing 8.1 makes this requirement explicit.

Listing 8.1: Evidence-grounded contract extraction (architecture sketch)

```
from dataclasses import dataclass
from typing import Any

@dataclass(frozen=True)
class ExtractedTerm:
    name: str
    value: Any
    section: str
    evidence_text: str
    start_char: int
    end_char: int
    confidence: float
    validation_status: str = "pending"

def analyze_contract(text: str, extractor, rule_engine) -> dict:
    sections = segment_by_heading(text)
    candidates: list[ExtractedTerm] = []

    for section_name, section_text, offset in sections:
        proposed = extractor.extract(
            text=section_text,
            schema=CONTRACT_TERM_SCHEMA,
        )
        for item in proposed:
            term = attach_evidence_span(
                item=item,
                source_text=text,
                section=section_name,
                section_offset=offset,
            )
            if exact_span_matches_source(term, text):
                candidates.append(term)

    validated = rule_engine.validate(candidates, source_text=text)
    return {
        "terms": validated,
        "cross_references": resolve_cross_references(validated, text),
        "review_queue": [
            term for term in validated
            if term.validation_status != "validated"
        ],
    }
```

The generative component proposes candidate terms; deterministic functions then confirm that each quoted span exists in the source, normalize dates and currencies, check arithmetic relationships, and route ambiguous cases to a review queue. This design is more defensible than asking a model to return a single untraceable summary.

#### Structured-credit documents

A CLO indenture is the governing contract for a collateralized loan obligation. It specifies the rights of noteholders, the duties of the trustee and collateral manager, and the rules for distributing cash. Within such a document, the payment waterfall is the contractual priority order under which interest and principal proceeds are allocated. Coverage tests are contractual ratios—commonly overcollateralization and interest-coverage tests—that can redirect cash away from junior tranches when specified thresholds are breached.
