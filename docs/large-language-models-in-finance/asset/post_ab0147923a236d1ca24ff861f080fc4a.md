"""

## 9.3 Modern RL and preference-optimization algorithms for LLMs

Policy gradients provide the foundation for RL-based alignment, but practical LLM training requires methods that make updates more stable and easier to control. PPO, GRPO, and DPO address this problem in different ways: PPO constrains online policy updates, GRPO estimates relative advantages from groups of completions, and DPO optimizes directly from offline preference pairs. Table 9.1 summarizes the main distinctions.

| Method | Training signal | Additional learned components | Operational trade-off |
| :--- | :--- | :--- | :--- |
| PPO | Scalar rewards on newly sampled responses | Usually a reward model, a reference policy, and a learned value-function critic | Stable clipped updates, but a comparatively complex and memory-intensive online training loop |
| GRPO | Rewards normalized within a group of responses to the same prompt | Reward source and reference policy, but no separate value-function critic | Lower critic-related memory usage; performance depends on group sampling and the quality and dispersion of rewards |
| DPO | Preferred/rejected response pairs | Fixed reference policy; no explicit reward model or critic during DPO optimization | Simple offline objective, but learning is limited by the coverage and quality of the preference-pair dataset |

Table 9.1: Comparison of PPO, GRPO, and DPO for LLM post-training

### 9.3.1 Proximal policy optimization (PPO) for LLMs

Proximal policy optimization (PPO) is widely used in LLM alignment because it improves a model using reward feedback while limiting how far the updated policy can move from the earlier policy. This constraint helps prevent large policy updates that could make the model unstable or degrade previously learned behavior.

In simple terms, PPO compares the probability of an action under the old and new policies. If the update is too large, the clipped objective reduces the incentive for the model to move too far in one training step. This stability is especially important in financial applications, where small changes in model behavior can affect compliance, risk explanations, or decision-support outputs [Schulman et al., 2017, Ouyang et al., 2022].

A second control is the Kullback–Leibler (KL) divergence from a fixed reference policy. For a prompt _x_, it is

\( D_{\text{KL}}(\pi_\theta \| \pi_{\text{ref}}) = \mathbb{E}_{y \sim \pi_\theta(\cdot|x)} [\log \pi_\theta(y | x) - \log \pi_{\text{ref}}(y | x)] . \qquad (9.10) \)

A token-level average of current minus reference log probabilities on sampled responses is a Monte Carlo estimate of this quantity. Penalizing large KL divergence discourages the aligned policy from departing abruptly from the base model, although the coefficient must be tuned because an excessive penalty can suppress useful learning.

#### PPO implementation for financial LLMs

For actual experiments, a maintained post-training library should normally be preferred to an ad hoc trainer. For example, Hugging Face TRL exposes configured PPOTrainer and DPOTrainer interfaces. The listing below is retained to expose the reward, KL, clipping, and optimization components; it is a conceptual training-loop illustration, not a recommended production reimplementation.

The following illustrative example shows the main components of a PPO-style alignment loop for financial responses: a reward model, a reference model for the KL penalty, domain-specific financial penalties, and a clipped policy update.

Listing 9.4: PPO-style alignment loop for financial responses

```python
class FinancialPPO:
    def __init__(self, model, ref_model, reward_model, config):
        self.model = model
        self.ref_model = ref_model # Reference model for KL constraint
        self.reward_model = reward_model
        self.config = config
        self.optimizer = torch.optim.AdamW(
            model.parameters(), lr=config.learning_rate)

    def compute_rewards(self, prompts, responses):
        """
        Compute rewards with KL penalty from reference model.
        """
        rewards = []

        for prompt, response in zip(prompts, responses):
            # Base reward from reward model
            base_reward = self.reward_model(prompt, response)

            # KL penalty to prevent model from deviating too far
            kl_penalty = self.compute_kl_penalty(
                prompt, response)

            # Additional financial-specific rewards/penalties
            financial_penalties = self.compute_financial_penalties(response)

            total_reward = (base_reward - self.config.kl_coef * kl_penalty -
                            financial_penalties)
            rewards.append(total_reward)

        return torch.stack(rewards)

    def compute_kl_penalty(self, prompt, response):
        """
        Compute KL divergence between current and reference model.
        """
        with torch.no_grad():
            ref_logprobs = self.ref_model.get_logprobs(
                prompt, response)
            current_logprobs = self.model.get_logprobs(
                prompt, response)

        # Sample-based estimate of KL(current || reference)
        kl = (current_logprobs - ref_logprobs).mean()
        return kl

    def compute_financial_penalties(self, response):
        """
        Apply domain-specific penalties for financial responses.
        """
        penalties = 0.0

        # Penalize overconfident predictions
        if self.detect_overconfidence(response):
            penalties += 0.5

        # Penalize lack of risk disclosure
        if not self.has_risk_disclosure(response):
            penalties += 0.3

        # Penalize non-compliant advice
        compliance_score = self.check_regulatory_compliance(
            response)
        if compliance_score < 0.8:
            penalties += 0.7 * (1 - compliance_score)

        return penalties

    def update_policy(self, trajectories):
        """
        PPO policy update with clipping.
        """
        states, actions, old_log_probs, rewards, advantages = self.process_trajectories(trajectories)

        for _ in range(self.config.ppo_epochs):
            # Compute current log probabilities
            current_log_probs = self.model.get_log_probs(
                states, actions)

            # Compute probability ratio
            ratio = torch.exp(current_log_probs - old_log_probs)

            # Clipped surrogate objective
            surr1 = ratio * advantages
            surr2 = torch.clamp(ratio, 1 - self.config.clip_param, 1 + self.config.clip_param) * advantages

            # Policy loss
            policy_loss = -torch.min(surr1, surr2).mean()

            # Value function loss (if using actor-critic)
            if self.config.use_value_function:
                value_loss = self.compute_value_loss(
                    states, rewards)

            else:
                value_loss = 0

            # Entropy bonus for exploration
            entropy = self.model.get_entropy(states)
            entropy_loss = -self.config.entropy_coef * entropy.mean()

            # Total loss
            total_loss = policy_loss + self.config.value_coef * value_loss + entropy_loss

            # Optimization step
            self.optimizer.zero_grad()
            total_loss.backward()
            torch.nn.utils.clip_grad_norm_(
                self.model.parameters(),
                self.config.max_grad_norm)
            self.optimizer.step()

        return {
            'policy_loss': policy_loss.item(),
            'value_loss': value_loss.item()
            if self.config.use_value_function else 0.0,
            'entropy': entropy.mean().item()
        }
```

In actor–critic PPO, the value-function network \(V_\psi(s)\) is a learned critic that predicts the policy's expected future return from state \(s\). Subtracting this prediction from the observed return produces an advantage estimate, but the critic introduces its own parameters, optimizer state, forward activations, targets, and validation requirements. Newer methods try to remove that additional model while retaining a useful baseline.

### 9.3.2 Group relative policy optimization (GRPO)

Group Relative Policy Optimization (GRPO) is an RL method for LLMs introduced in the DeepSeekMath paper [Shao et al., 2024]. It replaces the separate value-function critic with a within-prompt baseline computed from a group of sampled responses. This reduces critic-related memory and implementation complexity, although it does not eliminate the need for reliable rewards or adequate response diversity.

#### GRPO mathematical framework

The key innovation of GRPO is using group-based relative advantage estimation. For each prompt \(q\), GRPO samples a group of \(G\) outputs \(\{o_1, o_2, ..., o_G\}\) from the current policy \(\pi_{\theta_{old}}\). The group-relative advantage for output \(i\) is computed as:

\(\hat{A}_i = \frac{r_i - \mu_r}{\sigma_r}\) (9.11)

where \(\mu_r = \frac{1}{G} \sum_{j=1}^G r_j\) is the mean reward and \(\sigma_r = \sqrt{\frac{1}{G} \sum_{j=1}^G (r_j - \mu_r)^2}\) is the standard deviation.

This means that a response is rewarded not only for having a high absolute score, but for scoring better than other responses generated for the same prompt.
