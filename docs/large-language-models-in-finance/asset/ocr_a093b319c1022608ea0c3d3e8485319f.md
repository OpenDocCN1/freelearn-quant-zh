# 6.6.1 A dimensionally consistent capacity objective

Latency targets must be balanced against capacity and cost. Adding more workers can reduce queueing delay and failure probability, but it also increases infrastructure cost. A simple capacity objective should therefore keep all terms in the same unit.

Let H be a planning horizon in hours, c the number of server workers, λ the arrival rate in requests per hour, Cs the server cost per worker-hour, Cw the cost of one request-hour of delay, and Cf the expected cost of a failed or timed-out request. A simple objective is:

```
J(c) = HcCs + HλE[Wq(c)]Cw + Hλpf(c)Cf, (6.12)
```

where Wq(c) is queueing delay in hours and pf(c) is the failure probability. Every term is a monetary amount over the same horizon. The model is intentionally simple, but unlike an expression that adds monthly server cost to per-second delay, it is dimensionally coherent.

# 6.6.2 Latency classes

Different financial workflows require different latency paths. A research assistant, a case-investigation workflow, a human approval step, and a low-latency trading component should not be placed under the same performance target. Table 6.5 gives illustrative latency classes for MCP-assisted workflows.

| Class | Typical budget | Suitable examples and controls |
|---|---|---|
| Interactive research | Seconds to tens of seconds | Filing retrieval, research summarization, scenario drafting; visible citations and cancellation. |
| Operational assistance | Seconds to minutes | Case investigation, report preparation, covenant review; deterministic checks and queue monitoring. |
| Human approval | Minutes to hours | Client communication, limit exception, risk sign-off; reviewer evidence pack and expiry. |
| Low-latency execution | Milliseconds or less | LLMs should remain outside the critical execution loop; use precomputed signals and deterministic controls. |

Table 6.5: Illustrative latency classes for MCP-assisted financial workflows

A language model and remote tool chain are generally inappropriate inside a microsecond or millisecond trading decision loop. They may support research, configuration, surveillance, pre-trade explanation, or signal preparation outside that loop. The performance architecture should therefore match the workflow's risk, latency, and control requirements rather than forcing every use case into the same path.
