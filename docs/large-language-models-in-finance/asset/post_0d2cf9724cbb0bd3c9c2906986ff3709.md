\(\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}\) (4.17)

where rank\(_i\) is the position of the first relevant document for query \(i\).

**Normalized Discounted Cumulative Gain (NDCG)** generalizes Precision@k and MRR by allowing graded relevance: a passage that fully answers a query contributes more than one that is merely related. This is well aligned with financial use cases, where multiple disclosures may all be relevant but to different degrees.

\(\text{DCG}@k = \sum_{i=1}^k \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}\) (4.18)

\(\text{NDCG}@k = \frac{\text{DCG}@k}{\text{IDCG}@k}\) (4.19)

where IDCG is the ideal DCG (perfect ranking).

## 4.10.2 Generation metrics

**Faithfulness** [Es et al., 2023]: Does the answer align with context? For \(m\) material claims, use the fail-closed piecewise definition

\(\text{Faithfulness} = \left\{ \begin{array}{ll} \frac{\text{Number of supported claims}}{m}, & m \ge 1, \\ \perp, & m = 0. \end{array} \right.\) (4.20)

The \(m=0\) branch is not scored as one: it is undefined and must be rejected unless the task explicitly permits a non-claim response such as a refusal or formatting operation.

**Answer relevancy**: Does the answer address the query?

\(\text{Relevancy} = \text{sim}_\text{cos}(f(q), f(a))\) (4.21)

where \(a\) is the generated answer.

**Context relevancy**: Are retrieved contexts relevant?

\(\text{Context Relevancy} = \frac{1}{k} \sum_{i=1}^k \text{relevance}(q, d_i)\) (4.22)

## 4.10.3 Claim-level faithfulness as a formal contract

Aggregate faithfulness scores are useful dashboards, but financial review often needs a stronger object: a claim-by-claim contract. A board memo, risk explanation, or regulatory answer is not acceptable merely because it sounds plausible; each material claim must be traceable to evidence that was available, authorized, and cited.

**Definition 4.10.1** (Atomic claim support). Let an answer $a$ be decomposed into material atomic claims $A_1, ..., A_m$. For each claim $A_i$, let $E_i \subset \mathcal{D}_{\le t}$ be an evidence bundle retrieved from the authorized corpus available at decision time $t$. A verifier $\mathcal{V}$ assigns $\mathcal{V}(A_i, E_i) = 1$ when the evidence entails or directly supports the claim under the task's review standard, and 0 otherwise. The claim-level score is the piecewise quantity in Definition 4.3.1: for $m \ge 1$ it is $m^{-1} \sum_{i=1}^m \mathcal{V}(A_i, E_i)$; for $m = 0$ it is $\perp$ and fails closed unless the task class explicitly permits a non-claim response.

**Proposition 4.10.1** (Verified-claim grounding). Assume a RAG renderer is constrained to output only claims from a verified set $\mathcal{A}^\star = \{A_i : \mathcal{V}(A_i, E_i) = 1\}$ together with citations to the corresponding evidence bundles $E_i$. Then every material claim in the rendered answer is supported relative to the verifier and the authorized corpus, so Faith$(a, E) = 1$ for the rendered material claims. The proposition is relative to the verifier; it does not imply that the corpus itself is true, complete, current, or legally sufficient.

**Proof.** By construction, each material claim emitted by the renderer belongs to $\mathcal{A}^\star$. Therefore, for every emitted claim $A_i$, the verifier has already returned $\mathcal{V}(A_i, E_i) = 1$. Substituting these ones into the definition of Faith gives a score of one. The final caveat follows because the support relation is evaluated against the selected corpus and verifier, not against all facts in the world.

A deterministic smoke-test implementation appears below. It is weaker than expert review, but it is valuable in continuous integration because it prevents uncited or unsupported claims from silently passing through a financial RAG pipeline.

```python
from dataclasses import dataclass
from typing import Iterable, Sequence

@dataclass(frozen=True)
class Claim:
    text: str
    material: bool = True

@dataclass(frozen=True)
class Evidence:
    document_id: str
    timestamp: str
    text: str

def token_set(text: str) -> set[str]:
    return {tok.lower() for tok in text.replace("/", " ").split()
            if len(tok) > 2}

def supports_claim(claim: Claim, evidence: Sequence[Evidence],
                   min_overlap: float = 0.35) -> bool:
    claim_tokens = token_set(claim.text)
    if not claim_tokens:
        return False
    evidence_tokens = set().union(*(token_set(e.text) for e in evidence))
    return len(claim_tokens & evidence_tokens) / len(claim_tokens) >= min_overlap

def faithfulness_score(claims: Iterable[Claim],
    evidence: dict[str, Sequence[Evidence]]) -> float:
    material = [c for c in claims if c.material]
    if not material:
        return 1.0
    supported = [supports_claim(c, evidence.get(c.text, [])) for c in material]
    return sum(supported) / len(supported)
```

The smoke test should not be oversold. Token overlap will miss paraphrase, numerical entailment, negation, and legal nuance. Its role is to enforce the interface: answers must be decomposed into claims, claims must have evidence bundles, and unsupported material claims must become visible before release. Stronger deployments replace supports_claim with a hybrid verifier combining exact citation checks, numerical consistency checks, embedding retrieval, and expert-labeled entailment tests.

## 4.10.4 Evaluation protocol for regulated financial Q&A

For regulated use cases—such as answering questions about capital requirements, market abuse rules, or internal policies—RAG evaluation must go beyond generic IR and QA metrics. A minimal but robust protocol typically includes the following steps:

- 1. **Define the evaluation scope:** Select one or more well-defined policy domains (e.g., MiFID II product governance, market manipulation, suitability) and assemble a corpus that matches the documents used in production (regulations, internal policies, FAQs, supervisory guidance).

- 2. **Create a gold-standard test set:** Draft queries that represent real user questions (from compliance, front office, operations) and have subject-matter experts write:
  - canonical answers,
  - lists of documents or passages that support each answer,
  - severity labels indicating the impact of an incorrect answer.

- 3. **Instrument the full pipeline:** Log retrieval results, selected contexts, generated answers, and all relevant metadata (model version, index version, prompt template) so that each test run is reproducible.

- 4. **Measure retrieval and generation jointly:** In addition to Recall@k, Precision@k, MRR, and nDCG, compute:
  - **Faithfulness:** whether claims in the answer are actually supported by retrieved passages.
  - Grounding rate: proportion of answers that include at least one citation to the relevant regulatory or policy document.
  - Critical error rate: proportion of answers that are both incorrect and high-severity according to experts.

- 5. Run expert review: Have compliance or legal reviewers audit a sample of system answers, focusing on high-severity queries. Capture both binary judgements (acceptable / unacceptable) and qualitative feedback on missing caveats or context.

- 6. Define go/no-go thresholds and monitoring: Set explicit acceptance criteria (for example, zero critical errors on the test set, faithfulness above a given threshold) and define how these metrics will be monitored in production (ongoing sampling, periodic re-evaluation when the corpus or model changes).

This protocol ties offline evaluation directly to an institution’s governance and model risk processes: test cases are aligned with real obligations, high-severity failures are explicitly tracked, and evaluation outputs feed into the broader framework on ethics, governance, and compliance.

## 4.10.5 End-to-end evaluation framework

Having defined what to measure and the protocol that gives those measurements meaning, we now turn to how the measurements are actually computed. The class below gathers all of the metrics introduced earlier—Recall@k, Precision@k, MRR, NDCG, faithfulness, answer relevancy, context relevancy, and latency—into a single evaluation harness that can be run against a labeled test set.

The implementation has two parts. EvaluationResult is a dataclass that bundles the full set of metrics into a single object, so that every test run produces a structured, comparable record rather than a loose collection of numbers. RAGEvaluator is the harness itself: its evaluate method iterates over test cases, queries the RAG system, computes per-query retrieval and generation metrics, and finally averages them across the set. In practice, this is the object that production teams wire into CI, into release gates, and into the periodic re-evaluation runs called out in the protocol above.
