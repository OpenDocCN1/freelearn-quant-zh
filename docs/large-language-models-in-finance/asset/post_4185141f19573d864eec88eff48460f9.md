
Streamable HTTP supports independent servers, HTTP POST/GET, optional server-sent events, and session identifiers. It requires standard web-security controls, including authentication, origin validation, secure session handling, and protection against DNS rebinding.

The protocol version must be negotiated and recorded. A production audit record should not merely state that “MCP” was used; it should state the negotiated revision, transport, client and server versions, declared capabilities, and schema hashes.

## 6.1.3 Authorization is optional at protocol level

For HTTP-based Model Context Protocol authorization transports, the MCP authorization specification defines an OAuth-based pattern in which a protected MCP server acts as a resource server and a client obtains scoped access tokens on behalf of a resource owner. Authorization remains optional for MCP implementations, and it is transport-level rather than a complete financial entitlement model [Model Context Protocol, 2025b].

This distinction has three consequences:

- 1. A valid access token proves that a client has a transport-level authorization context; it does not prove that a proposed trade, recommendation, data release, or client communication is permitted.
- 2. Scopes should identify narrow capabilities, but a second policy layer must evaluate financial attributes such as desk, legal entity, jurisdiction, portfolio, product, data classification, approval status, and current limits.
- 3. Credentials must never be passed through prompts, tool descriptions, logs, or model-visible context. Token passthrough creates confused-deputy and data-exfiltration risks.

## 6.1.4 Tools are model-controlled, not self-authorizing

The tools specification permits a model to discover and invoke tools, while recommending visible user control and the ability to deny invocations [Model Context Protocol, 2025d]. In finance, this recommendation should be strengthened into a design rule:

The model may propose a tool call. Only a deterministic policy component may authorize execution, and material actions require an accountable human or a pre-approved automated mandate.

MCP therefore solves interoperability, not accountability. Table 6.2 states this boundary explicitly.

| MCP can standardize | The institution must still provide |
|---|---|
| Message formats and lifecycle | Identity assurance, entitlement mapping, and segregation of duties |
| Capability discovery input and output schemas | Approved-tool inventory and server trust policy; business-rule validation and numerical reconciliation |
| Resources, prompts, and tools | Data classification, purpose limitation, and point-in-time admissibility |
| Transport-level authorization | Product, client, desk, jurisdiction, and action-level authorization |
| Structured errors and logs | Complete, immutable, privacy-aware audit evidence |
| Cancellation and progress messages | Idempotency, duplicate-execution prevention, recovery, and rollback |

A safe financial integration places every MCP exchange inside a control envelope that remains outside the language model. Figure 6.1 shows the reference pattern.

Blue denotes stochastic model behavior, amber denotes deterministic controls, teal denotes evidence or services, and gray denotes accountable human or audit functions. The envelope has nine separable functions:

- 1. authenticate the user, service, device, and workload;
- 2. bind the request to a declared purpose and decision time;

- 9. write a complete audit record before and after execution.

## 6.2.1 A typed request contract

Let a proposed tool request be

```
r = (u, w, p, t, s, a, x, v, e, \iota),
```

where:

- u is the authenticated principal;
- w is the workload and host identity;
- p is the declared purpose;
- t is the financial decision time;
- s is the server and negotiated protocol version;
- a is the requested tool action;
- x is the validated input object;
- v is the version bundle for model, prompt, schema, policy, and data;
- e is the evidence bundle supporting the request;
- \iota is an idempotency key.

The gate returns one of three states:

```
Gate(r, z) \in {allow, reject, escalate},
```

where z is the current institutional state: entitlements, limits, restricted lists, market status, approval records, and incident flags.

An allow decision requires the conjunction

```
Allow(r, z) = AuthN(u, w) \wedge AuthZ(u, p, s, a, z)   (6.1)
\wedge SchemaValid(x) \wedge PurposeBound(x, p)   (6.2)
\wedge PointInTime(e, t) \wedge ValueValid(x, e, z)   (6.3)
\wedge ApprovedVersion(v) \wedge ReplaySafe(\iota, z).   (6.4)
```

No language-model judgment appears in Equation (6.4). The model can help populate a and x, explain why the action is proposed, or summarize the evidence. It cannot decide that the predicate is true.

## 6.2.2 The minimum invariants

A production implementation should be able to demonstrate the following invariants through code, configuration, and tests.

- Capability containment. Every executable action belongs to an approved allow-list for the current principal, purpose, and environment.
- Point-in-time validity. Every evidence item $d_j$ used at decision time $t$ has availability time $a_j \le t$.
- Deterministic materiality. Every material monetary amount, ratio, risk measure, threshold, and identity is recomputed or reconciled outside the LLM.
- Approval binding. A human approval is bound to the exact request hash, values, evidence, and policy version that will execute.
- Exactly-once business effect. Retries may repeat transport messages but must not duplicate a financial action.
- Complete traceability. The final result can be reconstructed from immutable identifiers without relying on hidden model state or private chain-of-thought.
- Fail-closed behavior. Missing identity, evidence, permission, schema, timestamp, or validation data produces rejection or escalation, never silent execution.

These are testable obligations. They are stronger and more useful than an abstract claim that a protocol is “secure.”

## 6.2.3 A minimal deterministic gate

Listing 6.1 illustrates the separation between a model-proposed call and an executable request. The code is intentionally small; production implementations should use institution-approved policy engines and identity systems.

Listing 6.1: A deterministic pre-execution gate

```python
from dataclasses import dataclass
from datetime import datetime
from typing import Literal

Decision = Literal["allow", "reject", "escalate"]

@dataclass(frozen=True)
class ToolRequest:
    principal: str
    purpose: str
    tool: str
    decision_time: datetime
    evidence_times: tuple[datetime, ...]
    schema_valid: bool
    amount_usd: float | None
    idempotency_key: str

def decide(req: ToolRequest, allowed_tools: set[str],
           auto_limit_usd: float) -> Decision:
    if not req.schema_valid or not req.idempotency_key:
        return "reject"
    if req.tool not in allowed_tools:
        return "reject"
    if any(ts > req.decision_time for ts in req.evidence_times):
        return "reject"
    if req.amount_usd is not None and abs(req.amount_usd) > auto_limit_usd:
        return "escalate"
    return "allow"
```

The gate does not ask the model whether the evidence is current or whether the amount is large. It compares typed values. This design is less flexible than a free-form prompt and far more reliable.

## 6.3 Threat model, authorization, and least privilege for financial MCP deployments

The relevant attacker is not only an external network intruder. A threat can originate from a malicious document, a compromised server, excessive permissions, stale configuration, unsafe retry logic, an insider, a vendor update, or an ordinary implementation error. Indirect prompt injection is especially important because untrusted text retrieved as evidence can attempt to alter the model's tool behavior [Greshake et al., 2023].

A financial MCP deployment therefore needs a threat model that links each failure mode to a concrete control owner. The control should not depend on the model following an instruction. It should be enforced by the host, policy engine, server registry, identity system, validation layer, or execution adapter.
