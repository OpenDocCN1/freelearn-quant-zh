From a practitioner’s perspective, the main question is not which method is “best” in the abstract, but which method is appropriate under given constraints (data, compute, governance). The choice typically reduces to a few practical considerations: how much GPU memory is available, how many distinct tasks must be served from a single base model, and how stringent the latency and governance requirements are. Table 3.4 summarizes the trade-offs for typical institutional scenarios. The general recommendation that emerges is to use full fine-tuning only when very large curated datasets exist and maximum task accuracy is essential (for instance, a core credit-scoring model); to use LoRA as the default for most adapter-style tasks; and to reserve QLoRA for settings where 13B or larger models must run on a single GPU.

| Aspect | Full fine-tuning | LoRA | QLoRA | Best use cases |
| :--- | :--- | :--- | :--- | :--- |
| GPU memory | Very high (all params + optimizer) | Moderate (few %) | Low (4-bit base + adapters) | QLoRA for 13B+ models in banks |
| Data requirements | Higher (more capacity to fit) | Moderate | Moderate | Full FT for very large curated datasets |
| Inference changes | New checkpoint per task | Shares base, swaps adapters | Shares 4-bit base, swaps adapters | LoRA/QLoRA for many narrow tasks |
| Stability / risk | More risk of catastrophic forgetting | Safer if base frozen | Safer, but quantization artifacts | Full FT for domain pre-training; PEFT for tasks |
| Operational aspects | Heavy deployment rollback | Lightweight: adapter routing | Lightweight: quantization infra needed | PEFT for fast experimentation and A/B tests |

With these trade-offs in mind, we now turn to how fine-tuned models are trained for specific financial tasks, beginning with supervised fine-tuning and its application across common NLP problems such as entity recognition, question answering, and summarization.

## 3.6 Supervised fine-tuning

Supervised fine-tuning adapts models using labeled data for specific tasks. With the parameter-efficient strategies from the previous section in hand—LoRA or QLoRA to manage memory, a well-curated financial dataset, and a stable optimization setup—the next question is how to structure the training signal for different financial problems. This section walks through how supervised fine-tuning covers the most important task families: named entity recognition, question answering, and summarization. Each involves a different input-output format and calls for a different model architecture and loss function, but all share the same underlying fine-tuning workflow described earlier.

Before turning to specific tasks, it is worth addressing how tasks are actually expressed to modern generative models.

### 3.6.1 Instruction format for supervised fine-tuning

Encoder-based models like BERT consume a raw text sequence and produce a classification or span label, so the “task format” is implicit in the model architecture and loss function. Decoder-based generative models—Llama, Mistral, Falcon, and their derivatives—work differently: they generate free-form text token by token, and the model must be told, explicitly within the input, what task it is being asked to perform. This is done through a structured **instruction format** sometimes called a “chat template” or “prompt template,” which wraps every training and inference example in a consistent set of *roles*.

The three canonical roles are:

- System: A fixed preamble that describes the model's persona, capabilities, and constraints. In financial applications this is where compliance-relevant instructions live—for example, “You are a financial analyst assistant. Always include appropriate disclaimers for forward-looking statements.”
- User: The input turn containing the instruction or question.
- Assistant: The model's response, which is the only part supervised during fine-tuning. The loss is computed on assistant tokens only; system and user tokens are masked.

A concrete financial instruction example looks as follows:

```
<system>
You are a financial analyst assistant. Classify the sentiment of
the following financial text as Positive, Negative, or Neutral.
Provide only the label and a one-sentence justification.
</system>
<user>
"The company raised its full-year revenue guidance by 8 percent,
citing stronger-than-expected demand in enterprise software."
</user>
<assistant>
Positive. The guidance raise signals management confidence in
sustained demand, a bullish indicator for the stock.
</assistant>
```

The specific delimiter tokens (<system>, <user>, <assistant>) vary by model family—Llama 3 uses <start_header_id>system</end_header_id>, Mistral uses user / assistant, and so on—but the three-role structure is universal. When fine-tuning with the Hugging Face transformers library, the `apply_chat_template` method handles delimiter insertion automatically:

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Meta-Llama-3-8B-Instruct")

messages = [
    {"role": "system", "content": "You are a financial analyst assistant..."},
    {"role": "user",
     "content": "Classify sentiment: 'Revenue declined 12%...'"},
    {"role": "assistant", "content": "Negative. A 12% revenue decline ..."},
]

# apply_chat_template inserts correct delimiter tokens for this model family
formatted = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=False
)
```

Using `apply_chat_template` rather than hand-crafting delimiters is important for compatibility: a mismatch between the training-time and inference-time template produces systematically degraded outputs that can be difficult to diagnose. For multi-turn financial dialogues—for example, a model that must answer a follow-up question about a previously cited revenue figure—the conversation history is appended as alternating user/assistant turns, and the model learns to condition its responses on all prior context.

With this structure in place, we can now turn to specific financial tasks, starting with one of the most foundational: extracting structured information from text.

### 3.6.2 Named Entity Recognition (NER)

Named entity recognition is one of the most fundamental and practically valuable financial NLP tasks. In its raw form, NER answers the question: given a span of financial text, which tokens refer to a specific named entity, and what type of entity is it? In financial workflows this matters enormously—automatically extracting company names, monetary figures, dates, and financial instruments from earnings releases, regulatory filings, or news articles is a prerequisite for downstream tasks such as event detection, knowledge graph construction, and risk monitoring. A model that confuses a company name with a product name, or fails to recognize a financial metric like EBITDA as a distinct entity type, will propagate errors through every system that depends on its output.

Financial NER is harder than general NER for two reasons. First, the entity set is richer: finance introduces domain-specific categories such as financial instruments, metrics, and regulatory labels that do not appear in standard NER benchmarks. Second, many tokens are genuinely ambiguous: “Apple” is a company, but “apple” in a different context is a fruit; “margin” could be a financial metric or ordinary English; “10-year” could describe a Treasury bond or the tenure of a CEO. The entity types that a financial NER model must learn to distinguish include:

- **ORG**: Companies, institutions (Apple Inc., Federal Reserve, Goldman Sachs)
- **PERSON**: Executives, analysts (Tim Cook, Warren Buffett)
- **MONEY**: Monetary amounts ($1.2 billion, €500 million)
- **PERCENT**: Percentages, basis points (15.3%, 25bps)
- **DATE**: Dates and periods (Q3 2024, FY2023)
- **INSTRUMENT**: Financial products (AAPL stock, 10-year Treasury, S&P 500)
- **METRIC**: Financial metrics (EBITDA, P/E ratio, EPS)
