```
@dataclass(frozen=True)
class ToolResult:
    status: str
    payload: Mapping[str, Any]
    audit_message: str

def guarded_tool_call(
    call: ToolCall,
    state: Mapping[str, Any],
    is_authorized: Callable[[ToolCall, Mapping[str, Any]], bool],
    execute: Callable[[ToolCall], Mapping[str, Any]],
) -> ToolResult:
    if not is_authorized(call, state):
        return ToolResult(
            status="escalated",
            payload={},
            audit_message=f"unauthorized tool call rejected: {call.name}",
        )
    try:
        result = execute(call)
    except Exception as exc:  # fail closed and preserve the audit trail
        return ToolResult(
            status="failed_closed",
            payload={},
            audit_message=f"tool execution failed: {type(exc).__name__}",
        )
    return ToolResult(status="ok", payload=dict(result),
                      audit_message="executed")
```

This pattern is deliberately simple: the guard is outside the model, the tool execution is inside a try/except boundary, and the return type always records a status. In a bank, asset manager, or broker-dealer, the same logic would be expanded with entitlements, restricted lists, client suitability, trade limits, data-classification rules, maker-checker approvals, and immutable audit logging.
