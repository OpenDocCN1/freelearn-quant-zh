
Read the table again with that in mind. The random split did not inflate everyone equally. It inflated *the best model*, and it inflated it by a factor of two, while leaving the weak models almost exactly where they were. The reason is not mysterious: BERT and the LSTM were not good enough to exploit the temporal adjacency the split handed them, so they had nothing to lose when it was taken away. FinEAS was. The advantage a leak confers is not a constant added to every competitor's score — it accrues to whichever model has the capacity to notice it, which is to say, it accrues disproportionately to the model you are trying to sell.

This is the general form of the danger and it is why leakage is not a hygiene issue to be delegated to a data engineer. A leaky protocol does not merely make your numbers too good. It makes your *model comparison* wrong, in the specific direction of favouring the most powerful architecture in the bake-off — and powerful architectures are exactly what an LLM system is made of. Had FinEAS been compared against its baselines only out-of-time, it would still have won, and the paper's architectural claim would still have stood. It would simply have won by less, and honestly. The correct protocol was available, it was cheap, and we did not use it.

I am not asking the reader to discount that paper. I am asking the reader to notice how easy this was to do, in a paper written by people who knew better, and to build the protocol of Section 13.4 into the pipeline rather than trusting that they will remember.

## 13.4.4 Label leakage and target engineering

Label leakage occurs when the target definition or labeling process embeds future information in the input. For example, a binary label \( y_t = \mathbf{1}[r_{t+1:t+20} > 0] \) is valid only if no feature summarizes the next 20 days. But an LLM prompt might accidentally include a news summary written after the horizon, a final analyst interpretation, or a chart whose endpoint reveals the target. In supervised fine-tuning, label leakage can also occur through instruction text: "classify whether this event led to a positive reaction" is not equivalent to "forecast whether this event will lead to a positive reaction."

The safest practice is to separate event description from outcome description. A training example may contain the event as known at time \( t \), the market state as known at time \( t \), and the label computed after the horizon. It may not contain any language produced after the horizon that explains the outcome. This rule is particularly important when using LLM-generated synthetic labels or rationales. A synthetic rationale generated with knowledge of the label can teach the model hindsight reasoning rather than forecasting.

## 13.4.5 Feature leakage through revised filings, restatements, and alternative data

Financial databases are full of revisions. Accounting statements are restated, fundamentals are standardized by vendors after publication, macro series are revised, index memberships are reconstructed, and alternative-data vendors backfill improved estimates. A model trained on the final version of a database may appear to predict the future because the database itself has been rewritten by the future.

The solution is point-in-time data storage. Each record should have at least two timestamps: the economic timestamp and the availability timestamp. For document data, this means filing date, acceptance time, amendment status, and source version. For alternative data, it means collection time, vendor delivery time, correction time, and backfill flag. The feature store should answer the question: "What exact value would the model have seen at 10:00 a.m. New York time on this date?" If it cannot answer this question, it is not suitable for a trading or forecasting backtest.

Operationally, this means the feature store must support "as-of" queries and must treat vendor corrections as new versions, not as silent edits. The storage layer should preserve raw vendor files, parsed features, transformation code versions, entity-resolution tables, and validity intervals. The query layer should be able to reconstruct a training row from the perspective of any historical forecast origin. The governance layer should expose enough metadata for reviewers to see whether a feature came from a timely observation, a late arrival, a correction, or a backfill. These requirements increase cost and latency, but without them the backtest can become a test of the database revision process rather than a test of forecasting skill.

## 13.4.6 Pretraining contamination and benchmark leakage

LLMs introduce a failure mode that classical models do not have: the base model may have been trained on information from the evaluation period or even on the benchmark itself. For text-based finance tasks, this is serious. Public earnings-call transcripts, research articles, benchmark datasets, code repositories, and even discussion threads about benchmark answers may appear in pretraining corpora. A model may therefore perform well not because it forecasts, but because it has memorized or partially internalized the answer distribution.

This risk cannot always be eliminated, especially with closed pretrained models. It can, however, be bounded. Evaluation should prefer private, newly constructed, temporally recent, or institution-specific test sets that were not public during model pretraining. Contamination probes can ask the model to complete rare benchmark examples, identify exact document snippets, or answer questions whose answers should not be knowable without the test data. When the base model's training cutoff is known, the test period should lie after that cutoff whenever possible. When the cutoff is unknown, the evaluation should report this uncertainty explicitly.

A useful leakage-adjusted interpretation is to decompose observed performance as

$$
\widehat{P}_{\text{obs}} = P_{\text{forecast}} + P_{\text{contam}} + P_{\text{noise}},
$$

where \( P_{\text{contam}} \) is the unknown contribution from memorization, pretraining overlap, retrieval overlap, and benchmark exposure. The goal of robust evaluation is not to pretend \( P_{\text{contam}} = 0 \), but to design protocols that make it small, measurable, or at least openly acknowledged.

## 13.4.7 Prompt leakage and tool-access leakage

Prompts are part of the data. If a prompt includes future context, a post-hoc narrative, a chart extending beyond the forecast origin, or a summary generated from a current database, the model has leaked information. This can happen innocently. A researcher may ask: "Given the stock fell after earnings, explain whether the call was negative." That is an explanation task, not a forecasting task. The forecasting prompt must be phrased as it would have been phrased before the outcome was known.

Tool-access leakage is even more subtle. An agent equipped with retrieval, web search, market-data APIs, vector databases, or code execution may access current information while being evaluated on a historical date. A valid historical backtest must time-travel all tools. The retrieval index must contain only documents available at the forecast origin. Market-data APIs must be queried through point-in-time snapshots. Web search should be disabled unless a historical search index is available. Code tools should not load files produced after the origin.

## 13.4.8 Memory contamination in agentic backtests

Agentic systems add state. An agent may remember previous conversations, previous forecasts, previous errors, analyst feedback, tool outputs, or evaluation outcomes. This is useful in production but dangerous in backtesting. If the agent evaluates many historical dates sequentially and retains memory, it can learn from future test outcomes as the backtest progresses. The contamination is especially severe when the backtest order is chronological but the agent receives labels after each step; by the end, it has effectively been trained on the test set.

A valid agentic backtest must define a memory policy. For pure out-of-sample evaluation, memory should be reset at each forecast origin or restricted to information that would have been accumulated in a real live deployment up to that date. If the evaluation allows online learning, then the protocol must state exactly when labels become available and how updates occur. There is nothing wrong with online learning, but it must be simulated with realistic delays and without access to future labels.
