
The supervisor should not be treated as an all-powerful agent. Its authority should be limited to routing, synthesis, and packaging. It should not be able to bypass policy tools, suppress risk flags, or invent evidence when specialist outputs are incomplete. In the research workstation, the Orchestrator agent can decide that the Data Analyst agent must rerun a metric with a different horizon, but it should not remove a compliance flag without a logged reviewer decision.

## 5.4.12 Verifier and critic agents

For high-stakes workflows, a useful extension is to add a verifier or critic agent that reviews outputs before they reach the user. The verifier does not create the primary analysis. Instead, it asks whether the analysis is grounded, internally consistent, and ready for review. The pattern has a research lineage — Madaan et al. [2023] iterate on a draft using the model's own feedback, and Shinn et al. [2023] convert failures into verbal lessons carried into the next attempt — but financial deployment demands one departure from it. Self-critique shares the generator's blind spots: a model that misread its covenant will generally not notice that it misread the covenant. A verifier is therefore worth its latency only where it has *independent* purchase on the answer: a deterministic recomputation, a schema check, a policy lookup, an evidence-support test against the retrieved bundle. A critic agent that merely re-reads the draft with a sterner prompt is a second opinion from the same doctor. Typical verifier checks include:

- whether every material factual claim is linked to evidence;
- whether numerical values match the structured data returned by tools;
- whether uncertainty and missing data are clearly labeled;
- whether the recommendation language is stronger than the evidence supports;
- whether required policy or disclosure language is present.

In the ACME memo workflow, the verifier might flag a sentence such as "ACME has a strong balance sheet" if the Data Analyst agent has reported rising leverage or if the underlying data snapshot is stale. The goal is not to make the system adversarial for its own sake, but to create a disciplined review step that catches errors before human reviewers are asked to approve the final packet.

## 5.4.13 Structured outputs before prose

Many agent workflows fail because they ask the model to produce polished prose too early. In finance, it is usually better to produce structured outputs first and prose second. Research notes can be represented as claims, sources, and confidence labels. Data outputs can be represented as metrics, periods, units, and data-source identifiers. Risk outputs can be represented as flags, severities, policy references, and required actions. The final memo can then be generated from these artifacts.

This pattern has two advantages. First, structured outputs are easier to validate with software. Second, they make the final memo easier to audit because each paragraph can be linked back to a typed intermediate object. In the workstation, the memo is the last mile of the workflow, not the only artifact the workflow creates.

## 5.5 Implementation roadmap

The patterns above can be translated into an incremental implementation roadmap. A financial institution should not begin by deploying a fully autonomous multi-agent platform. A safer path is to increase scope and autonomy only after the workflow has demonstrated reliability under realistic tests.

## 5.5.1 Phase 1: Workflow discovery

Identify a narrow workflow with clear users, inputs, outputs, and review requirements. For the research workstation, the first workflow might be internal pre-investment memo drafting for one equity team. The design team should document the current human process, the sources analysts already trust, the approval path, and the failure modes that would be unacceptable.

## 5.5.2 Phase 2: Read-only prototype

Build the orchestrator and specialist agents with mocked or read-only tools. Require structured outputs, citations, and audit logs from the beginning. In this phase, the system is useful for learning how the workflow behaves, not for replacing analyst work.

## 5.5.3 Phase 3: Controlled pilot

Run the workstation in parallel with existing human workflows. Compare agent-assisted memos with analyst-written memos using a rubric for evidence quality, numerical accuracy, usefulness, risk identification, and clarity. Collect reviewer edits and use them to improve prompts, schemas, retrieval policies, and escalation rules.

## 5.5.4 Phase 4: Governed production

Deploy the workflow only after defining ownership, monitoring, incident response, prompt, and model versioning, benchmark tests, and human approval gates. Production use should begin with advisory outputs and internal documents before any client-facing or decision-triggering use case is considered.

This roadmap emphasizes that agentic finance systems are not merely model integrations. They are governed workflows that combine models, tools, data, software controls, and accountable human judgment.

## 5.6 Open problems and research directions

Although agentic systems are already useful in constrained settings, several open problems remain especially important for financial applications. These problems can be grouped into three areas: evaluation and benchmarking, control and coordination, and governance.

## 5.6.1 Evaluation and benchmarking

- **Evaluation of multi-step behavior:** Single-turn benchmarks are not enough for agentic workflows. General-purpose agent benchmarks have begun to close this gap — Liu et al. [2024b] evaluate LLMs as agents across interactive environments rather than on single-turn tasks — but none of them scores the properties a financial institution is actually accountable for. Institutions need evaluation methods that test tool use, memory, escalation behavior, robustness to missing data, and resistance to prompt injection across many-step workflows, and that report citation coverage, policy-flag recall, and escalation precision alongside task success. The regression suite outlined in the guided build is a starting point, but richer and more standardized methods are needed. This is a genuine gap in the literature and not merely an engineering chore: an agent that scores well on a public agent benchmark has demonstrated nothing about whether it would have escalated the one memo that mattered.

- **Grounded synthesis across heterogeneous evidence:** Financial reasoning often combines filings, transcripts, market data, portfolio constraints, and qualitative judgment. It is difficult to guarantee that a final memo accurately preserves the provenance and uncertainty of each input. Future systems need stronger methods for evidence-aware synthesis, especially when sources conflict or when some inputs are stale, missing, or lower quality than others.

- **Benchmarking realistic workflow quality:** Finance-specific benchmarks should measure more than final-answer fluency. They should include citation coverage, numerical accuracy, policy-flag recall, stale-data detection, escalation precision, latency, reviewer burden, and the rate at which unsupported claims are caught before approval. Open research is needed on benchmark suites that capture these workflow-level properties without exposing confidential institutional data.

## 5.6.2 Control and coordination

- **Reliable delegation and decomposition:** Current systems can decompose tasks, but they do not always choose the right subtasks or the right stopping point. In the workstation, the orchestrator must decide when evidence is sufficient, when disagreement among agents matters, and when to ask the human user for clarification. Better methods are needed for measuring and improving the quality of these control-flow decisions.

- **Conflict preservation and reconciliation:** Multi-agent systems can hide rather than expose disagreement. A research agent may identify a positive qualitative story, while a data agent finds deteriorating cash conversion and a risk agent flags portfolio concentration. The open problem is to design orchestrators that preserve material tensions, separate facts from judgments, and route unresolved conflicts to the right human reviewer instead of averaging them into bland prose.

- **Human-agent collaboration:** The most valuable deployments may not be those that remove humans from the loop, but those that make expert humans faster and more consistent. This raises design questions: When should the system interrupt a user? How should it present uncertainty? How can it avoid over-automation bias while still saving time? The research workstation provides a concrete setting for studying these questions because the human portfolio manager, analyst, and compliance reviewer all interact with the same workflow in different ways.

## 5.6.3 Governance

- **Governance of adaptive systems:** Agentic systems may change over time as models, prompts, retrieval indexes, and policy rules are updated. This creates a governance challenge: the system is not one static model but a moving workflow. Research and practice must converge on better methods for versioning, approval, monitoring, rollback, and incident response for complete agentic systems.

- **Auditable provenance and accountability:** Finance workflows require a record of who or what produced each material claim, which evidence supported it, which policy checks were run, and which human approved the final output. Future systems need better mechanisms for source hashing, evidence linkage, memory invalidation, approval logs, and reviewer-facing explanations that remain intelligible months after the output was generated.

- **Scope boundaries and residual-risk ownership:** Even well-controlled agents leave residual risk. Institutions still need to decide which business owner accepts that risk, which control function monitors it, which incidents trigger suspension, and which outputs are categorically outside the system's mandate.
