### Stage 2: Query processing and retrieval

This stage takes a user query, brings it into the same representational space as the indexed chunks, and surfaces the small set of passages that should ground the answer. Its job is to maximize the probability that the relevant evidence is among the retrieved set.

- Query understanding and reformulation [Ma et al., 2023]
- Query embedding generation
- Similarity search (dense, sparse, hybrid)
- Re-ranking and filtering [Nogueira and Cho, 2019]
- Metadata filtering

### Stage 3: Context augmentation

This stage turns the retrieved passages into a well-structured prompt that the language model can actually use. It is responsible for fitting evidence into the context window without losing attribution.

- Retrieved document formatting
- Context window management
- Prompt construction
- Citation management

### Stage 4: Generation and post-processing

This stage produces the final answer conditioned on the augmented context and verifies that the answer is faithful to the retrieved evidence. It is the user-facing layer where grounding becomes auditable.

- LLM generation with augmented context
- Response extraction
- Citation attribution
- Answer verification

Having established the system-level structure of RAG, we now turn to a formal view of how retrieval and generation interact.

## 4.3 Formal RAG framework

We now formalize the intuition behind RAG introduced in the previous section. While practitioners can build effective systems without this level of detail, the formulation helps clarify how retrieval and generation interact.

At a high level, RAG can be understood as conditioning generation not only on the query, but also on a set of retrieved documents that provide relevant context.

Given a query $q$ and a document corpus $\mathcal{D} = \{d_1, d_2, \dots, d_N\}$, we can contrast standard generation with RAG-augmented generation.

### 4.3.1 A production-grade mathematical contract for RAG

For financial use, a RAG system should be specified as a time-indexed evidence system rather than as a prompt trick. Let $\mathcal{D}_t = \{d_j : a_j \le t\}$ be the corpus of documents available at decision time $t$, where $a_j$ is the availability timestamp of document $d_j$. A retriever is a map

$$R_k(q, t) : \mathcal{Q} \times \mathbb{T} \rightarrow \mathcal{D}_t^k,$$

which returns at most $k$ evidence items from the time-valid corpus. A generator is a conditional distribution

$$G_\theta(y \mid q, R_k(q, t), \pi_{\text{policy}}),$$

where $\pi_{\text{policy}}$ contains deterministic instructions and policy constraints. A verifier maps the candidate answer and evidence into a structured decision:

$$V(y, q, R_k(q, t)) \in \{\text{accept, revise, escalate, reject}\}.$$

The deployed answer is not merely $y$; it is the tuple

$$A = (q, t, R_k(q, t), y, V, \text{hashes, approvals}),$$

where the hashes identify the model, prompt, index, retrieved documents, and output.

This formulation is useful because each major failure mode has a natural location. If the relevant document is absent from $R_k(q, t)$, the problem is retrieval. If the document is present but the answer contradicts it, the problem is generation or verification. If the answer is correct but unauthorized, the problem is policy. If the document timestamp is after $t$, the problem is leakage.

**Definition 4.3.1** (Claim-level faithfulness). Let $C(y) = \{c_1, \dots, c_m\}$ be the set of material claims extracted from an answer $y$. The definition is piecewise, and the $m = 0$ branch is stated *before* the formula rather than repaired after it. The fraction is undefined when an answer contains no material claims, and the tempting convention — score it 1, since an answer that asserts nothing cannot be unfaithful — is *wrong for a financial gate*, because it is fail-open: it rewards a system for saying nothing. The value is therefore $\bot$, and the admission rule must fail closed on $\bot$: an answer with no material claims is **not admitted** unless its task class is on an explicit allowlist (a refusal, a clarification request, a pure formatting operation). Vacuous truth is a fine convention in logic and a bad one in a control. Let \( E = R_k(q, t) \) be the retrieved evidence set. A claim \( c_j \) is evidence-supported if there exists \( e \in E \) such that \( e \vdash c_j \) under the institution's chosen entailment or reviewer standard. The claim-level faithfulness rate is

\[ \text{Faith}(y, E) = \begin{cases} \frac{1}{m} \sum_{j=1}^m \mathbf{1}\{\exists e \in E : e \vdash c_j\}, & m \ge 1, \\ \perp \text{ (undefined)}, & m = 0. \end{cases} \]

**Proposition 4.3.1** (Time-valid RAG prevents direct corpus lookahead). *Assume the index at decision time t is built only from* \(\mathcal{D}_t\)*, the retriever returns only elements of that index, and the generator prompt is a deterministic function of the query, the retrieved evidence, approved policy text, and model configuration available at t. Then the generated answer cannot directly condition on documents with availability time greater than t through the retrieval channel.*

*Proof.* The retriever's codomain is \(\mathcal{D}_t^k\), so every retrieved item has availability time at most \( t \). The prompt is a deterministic function of the query, retrieved items, approved policy text, and configuration available at \( t \). Therefore the retrieval-augmented context is measurable with respect to the information available at time \( t \). The proposition concerns the retrieval channel only; it does not eliminate all possible contamination from model pre-training, vendor backfills, prompt examples, or external tools. Those channels require separate controls. \(\square\)

In production, the proposition is implemented by three simple rules: index versions must have timestamps, retrieval logs must record document IDs and availability times, and the generation step must refuse to run if any retrieved artifact violates the decision timestamp. The reference code in the companion repository implements this rule with typed evidence objects and an explicit availability-time check.

A standard auto-regressive language model generates a response \( y = (y_1, \dots, y_T) \) according to:

\[ p(y \mid q) = \prod_{t=1}^T p(y_t \mid y_{<t}, q; \theta) \] (4.1)

where \(\theta\) represents the model parameters and \( y_{<t} = (y_1, \dots, y_{t-1}) \) denotes the previously generated tokens.

RAG, on the other hand, augments generation by marginalizing over retrieved documents:

\[ p(y \mid q) = \sum_{d \in \mathcal{D}} p(y \mid q, d; \theta) \cdot p(d \mid q) \] (4.2)

where \( p(d \mid q) \) represents the relevance distribution over documents.

In practice, we approximate this marginalization by retrieving the top-\( k \) documents:

\[ p(y \mid q) \approx \prod_{t=1}^T p(y_t \mid y_{<t}, q, d_1, \dots, d_k; \theta) \] (4.3)

where the retrieved set is selected by

\(\{d_1, \dots, d_k\} = \arg\max_{\{d_1, \dots, d_k\} \subset \mathcal{D}} \sum_{i=1}^k \log p(d_i \mid q).\)

We now examine one of the most critical components of RAG systems: embedding models.

## 4.4 Embedding models

Embedding models form the foundation of semantic retrieval in RAG systems. In the pipeline introduced earlier, they are responsible for representing both documents (during indexing) and queries (during retrieval) in a shared vector space, enabling the system to identify relevant context better.

We begin with the theoretical foundations of dense embeddings, then examine how modern models are trained and adapted for financial applications.

### 4.4.1 Dense embeddings

An embedding model is a function \(f : \mathcal{X} \to \mathbb{R}^d\) that maps text \(x \in \mathcal{X}\) to a dense vector representation in \(d\)-dimensional space [Reimers and Gurevych, 2019]. In this space, semantically similar inputs are positioned close together, allowing similarity to be measured using simple distance metrics.

In the real world, not all embeddings are equally useful for retrieval tasks. Effective embeddings must satisfy several properties:

- **Semantic similarity**: The similarity \(\text{sim}(f(x_1), f(x_2))\) should correlate with the semantic similarity of \(x_1\) and \(x_2\).
- **Task relevance**: Embeddings should capture features relevant to downstream retrieval tasks.
- **Computational efficiency**: Fast to compute and amenable to efficient similarity search.

Common similarity metrics for dense embeddings include:

- Cosine Similarity: \(\text{sim}_{\cos}(u, v) = \frac{u \cdot v}{\|u\|_2 \|v\|_2}\)
- Euclidean Distance: \(d_2(u, v) = \|u - v\|_2\)
- Dot Product: \(\text{sim}_{\text{dot}}(u, v) = u \cdot v\)

In practice, the quality of retrieval in RAG systems depends heavily on how well embeddings capture relevance, which is typically achieved through contrastive learning objectives.
