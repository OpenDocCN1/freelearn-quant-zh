### 12.1.4 FinGPT and parameter-efficient adaptation

Where BloombergGPT emphasizes large-scale pre-training, FinBERT emphasizes continued encoder pre-training, and FinEAS emphasizes supervised sentence embeddings for financial sentiment, FinGPT emphasizes a systems perspective. FinGPT [Yang et al., 2023] is best understood as a practical framework for assembling financial LLM applications from data pipelines, base models, adapters, and evaluation tools. Rather than a single monolithic model, it offers:

- Data pipelines for collecting, cleaning, and labeling financial text;
- Adapters for plugging in different base models (GPT, LLaMA, etc.);
- Parameter-efficient fine-tuning via LoRA and QLoRA; and
- Evaluation harnesses for financial tasks.

Let \( \phi \) denote frozen base-model parameters and \( \Delta \) the low-rank adapters, as in Chapter 3. FinGPT-style pipelines optimize the adapter parameters while leaving the underlying model unchanged:

```
\(\Delta^* = \arg \min_\Delta \mathbb{E}_{(x,y)\sim\mathcal{D}_\text{fin}}[\mathcal{L}(y, f(x; \phi, \Delta))],\) (12.7)
```

with a parameter budget far below the base model: for an adapted \(d_{out} \times d_{in}\) matrix, \(r(d_{in} + d_{out}) \ll d_{in}d_{out}\). The saving is one of _rank_, not sparsity: the factors themselves are dense. When \(\Delta\) is parameterized as \(\Delta W = BA\) with \(B \in \mathbb{R}^{d_{out} \times r}\), \(A \in \mathbb{R}^{r \times d_{in}}\) and \(r \ll \min(d_{in}, d_{out})\), the product has shape \(d_{out} \times d_{in}\) — the shape of _W_ itself, as it must — and we obtain a low-rank LoRA-style adapter.

A second layer of efficiency comes from quantization (QLoRA): the base parameters \(\phi\) are stored in low precision (e.g. 4-bit) while the adapters remain in higher precision. The combination allows full forward precision in critical paths at significantly reduced memory footprint.

Empirical reports highlight that:

- Substantial performance gains on financial tasks are possible with only millions of trainable parameters;
- Training and inference costs remain compatible with on-premise infrastructure; and
- Performance is heavily contingent on data quality and curation, underscoring the importance of the data layer, covered in Chapter 2.

The four model families illustrate a common design choice. One can spend capacity by training a financial model from scratch, adapt a general encoder to financial language, specialize sentence embeddings for financial sentiment, or use parameter-efficient adapters on top of a flexible base model. ## 12.2 Memory-augmented and multi-agent trading systems

We now turn from foundational models to systems that combine LLMs with explicit memory, tools, and multiple decision roles. This transition is important: a financial LLM used in isolation can summarize a report or classify sentiment, but many real financial workflows require a sequence of observations, intermediate decisions, critiques, risk checks, and updates. Memory-augmented and multi-agent systems attempt to give this sequential structure an explicit architecture, aligning closely with the agentic patterns of Chapter 5 and the RL methods of Chapter 9.

### 12.2.1 FinMem: Layered memory for single-agent trading

FinMem [Yu et al., 2023] is a performance-enhanced LLM trading agent built around layered memory and character design. The term “character design” refers to the persistent role, risk preference, and decision style assigned to the agent, so that it behaves less like a stateless prompt-response system and more like a trading assistant with a stable operating profile. The central idea is simple: a trading agent should not treat every market observation as an isolated prompt. It should maintain short-term context, remember relevant episodes, and store more durable knowledge about regimes and risk preferences.

The framework therefore proposes three layers of memory:

- \( M_{\text{work}} \) (working memory): short-horizon market context;
- \( M_{\text{epis}} \) (episodic memory): summaries of past trades;
- \( M_{\text{sem}} \) (semantic memory): stable knowledge about regimes, risk preferences, and patterns.

These layers separate provisional workflow state from more durable knowledge. For example, today’s earnings surprise may enter working memory, the summary of a completed trade may enter episodic memory, and a persistent rule such as “reduce exposure during liquidity stress” may enter semantic memory.

### Formalization as a POMDP with memory

A natural way to explain FinMem mathematically is as a partially observable Markov decision process (POMDP) with memory. A POMDP is a sequential decision problem in which the true state of the world is not fully observed. This is a reasonable abstraction for markets: the agent sees prices, news, and portfolio positions, but not the complete latent state that generates future returns.

Let \( (\mathcal{S}, \mathcal{A}, P, r, \gamma) \) be an MDP over latent market states \( s_t \in \mathcal{S} \), with actions \( a_t \in \mathcal{A} \), transition kernel \( P \), reward function \( r \), and discount factor \( \gamma \). Actions may be discrete position changes, such as buy, hold, reduce, or sell. The agent observes \( o_t = g(s_t) \), where \( g \) is a partial observation map that converts the latent state into the information available to the agent. The FinMem agent then maintains internal memory states:

```
\( M_t = (M_{\text{work},t}, M_{\text{epis},t}, M_{\text{sem},t}), \)
```

and implements a policy:

```
\( a_t \sim \pi_\theta(a \mid o_t, M_t), \quad (12.8) \)
```

which means that the action is sampled from a distribution conditioned not only on the current observation, but also on the agent’s memory. Memory is updated after each transition by

```
\( M_{t+1} = \mathcal{U}_\theta(M_t, o_t, a_t, r_t), \quad (12.9) \)
```

where \(\mathcal{U}_\theta\) may summarize recent observations, delete stale items, or write selected information into structured memory slots.

Training can be cast as policy-gradient RL on trajectories \(\tau = (o_{1:T}, a_{1:T}, r_{1:T})\):

```
\(\nabla_\theta J(\theta) = \mathbb{E}_{\tau \sim \pi_\theta} \left[ \sum_{t=1}^T \nabla_\theta \log \pi_\theta(a_t \mid o_t, M_t) \hat{A}_t \right], \quad (12.10)\)
```

where \(\hat{A}_t\) is an advantage estimate (discussed in more detail later, in Chapter 9). The memory update \(\mathcal{U}_\theta\) is typically implemented via LLM-based summarization and write operations into vector stores or structured memory slots.

### Implementation sketch

The full runnable version of this idea belongs in the companion repository; the compact sketch below is included only to show how the mathematical objects above map into a training loop. It combines an LLM-based policy with layered memory and policy-gradient updates:

```
for epoch in range(num.epochs):
    trajectories = []
    for episode in range(num_episodes_per_epoch):
        memory = init_memory()  # (M_work, M_epis, M_sem)
        obs = env.reset()
        episode_data = []

        done = False
        while not done:
            # Build prompt from observation + memory
            prompt = build_prompt(obs, memory)
            action, log_prob = policy_llm.sample_action(prompt)

            next_obs, reward, done, info = env.step(action)

            # Update memory using LLM-based summarization
            memory = update_memory(memory, obs, action, reward, info)

            episode_data.append((obs, memory, action, log_prob, reward))
            obs = next_obs

        trajectories.append(episode_data)

    # Compute returns / advantages
    advantages = compute_advantages(trajectories, gamma, lam)

    # Policy gradient update
    optimizer.zero_grad()
```
