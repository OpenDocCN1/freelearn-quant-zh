We begin with hardware architecture because accelerator choice, memory capacity, deployment location, and latency requirements shape many of the infrastructure decisions that follow.

## 10.1 Hardware architecture for financial LLMs

Hardware choices strongly influence cost, latency, throughput, and operational flexibility. The appropriate platform depends on whether the dominant workload is pre-training, fine-tuning, batch embedding, high-concurrency generation, low-latency classification, retrieval, or a combination of these tasks. Peak floating-point throughput alone is therefore an inadequate selection criterion.

Memory capacity and bandwidth, interconnect topology, supported numerical formats, serving software, availability, power density, and the ability to operate in the required jurisdiction can be equally important.

### 10.1.1 Comparative analysis of computing platforms

Selecting hardware for financial LLM deployments requires balancing compute performance with memory capacity, latency, security, availability, cost, and regulatory constraints.

In financial environments, the decision must also account for operational control, vendor concentration, portability, disaster recovery, and the ability to preserve evidence for internal and external audit. Hardware specifications and product availability change rapidly; the figures below are representative vendor-reported specifications available at the time of writing and should be revalidated before procurement.

### Graphics processing units (GPUs)

GPUs remain the most broadly supported accelerators for LLM training and serving because the CUDA ecosystem integrates mature compilers, kernels, communication libraries, profilers, and inference servers.

NVIDIA’s H100 SXM configuration provides 80 GB of HBM3 memory and approximately 3.35 TB/s of memory bandwidth [NVIDIA, 2026b]. Blackwell systems increase aggregate memory and bandwidth further: an eight-GPU DGX B200 is specified with 1.44 TB of total GPU memory and 64 TB/s of aggregate HBM3e bandwidth [NVIDIA, 2026a].

NVIDIA reported upper-bound speedups of up to nine times for training and up to thirty times for inference on selected large-language-model configurations relative to A100 systems [NVIDIA, 2022]. These figures are useful indicators of architectural potential, but they are vendor benchmarks rather than universal gains.

Realized performance depends on the model, precision, sequence lengths, batch size, concurrency, interconnect, software version, and latency constraint; a small financial classifier or a retrieval-heavy pipeline may obtain much smaller improvements.

GPU infrastructure offers three practical advantages for financial institutions. First, the software ecosystem supports both machine-learning workloads and conventional numerical computation. Second, the same cluster can be allocated across training, fine-tuning, embedding generation, and inference. Third, the broad cloud and original-equipment-manufacturer market provides multiple procurement routes.

The main disadvantages are power density, cooling requirements, specialized engineering effort, and vendor lock-in. An H100 SXM device can be configured up to roughly 700 W, while newer Blackwell devices can have still higher thermal design power; these figures exclude CPUs, memory, networking, storage, cooling overhead, and redundancy [NVIDIA, 2025]. Hourly GPU price is therefore not a sufficient cost measure.

### Tensor processing units (TPUs)

Google’s TPUs are application-specific integrated circuits designed for machine-learning matrix operations. A single TPU v5e chip provides 16 GB of high-bandwidth memory, 800 GiB/s of memory bandwidth, 197 TFLOPs of peak bfloat16 compute, and 393 TOPS of peak INT8 compute; the 393 figure is an integer-operation rate rather than bfloat16 floating-point performance [Google Cloud, 2026]. TPU v5e supports slices up to 256 chips, while larger TPU families target higher-scale training.

TPUs can be attractive when the workload maps efficiently to XLA and the institution is comfortable operating in Google Cloud. Their regular architecture and high-speed inter-chip interconnect can provide strong throughput for large, stable workloads. Nevertheless, performance-per-cost and tail latency must be measured on the institution’s own models.

Compilation overhead, input-pipeline behavior, host-to-device transfer, batching, and topology all affect realized performance. TPU access is cloud-based, which can be incompatible with deployment policies requiring customer-controlled physical infrastructure or a specific sovereign environment.

### Specialized and emerging AI accelerators

Specialized accelerators offer alternatives to conventional GPU and TPU execution, but they introduce migration and ecosystem risk. Cerebras’ current CS-3 system is based on the WSE-3 and is specified with 900,000 AI-optimized cores, 44 GB of on-chip SRAM, and 21 PB/s of on-chip memory bandwidth [Cerebras Systems, 2026].

The design can simplify the mapping of very large models by presenting a wafer-scale compute fabric, although its economics and software fit must be assessed at system rather than chip level.

SambaNova systems built around the SN40L use reconfigurable dataflow units. A representative 16-RDU configuration is specified with 1 TB of aggregate HBM and 10.2 PFLOPS of bfloat16 processing capability [SambaNova Systems, 2025]. The dataflow compiler can reduce manual kernel engineering for supported models, but model coverage, compiler behavior, observability, and integration with existing serving systems require validation.

Graphcore’s documented GC200 IPU provides 1,472 processor cores, 900 MB of in-processor memory, and 250 TFLOPS at supported FP16 formats [Graphcore, 2026]. Its fine-grained parallelism can suit irregular or sparse workloads, but the Poplar ecosystem is materially smaller than CUDA’s. Procurement availability, roadmap continuity, and cloud access should therefore be confirmed before an institution makes a long-lived platform commitment.

### 10.1.2 Cloud versus on-premises infrastructure

The cloud-versus-on-premises decision involves more than capital expenditure. Financial institutions must consider data classification, outsourcing risk, audit rights, jurisdiction, concentration risk, exit plans, encryption and key control, network predictability, skill availability, and expected utilization. European data-protection rules regulate processing and international transfers but do not, by themselves, impose a universal on-premises requirement; financial-sector outsourcing guidance instead emphasizes a risk-based assessment of data
